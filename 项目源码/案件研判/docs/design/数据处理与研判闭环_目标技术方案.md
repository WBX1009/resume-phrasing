# 数据处理与研判闭环：两阶段事实计算与双通道候选召回

> **实现定稿 · 2026-09-27**  
> 本文从业务目标出发确定后续实现方案，已有代码可按本方案调整或重构，不作为架构约束。本文替代此前将“确定性候选池 → LLM 分析”画成单一路径的版本。文中的“业务模型”指甲方上游业务分析模型，“LLM”指大语言模型。

## 1. 最终确定什么

系统采用**两阶段事实计算、两条初始候选召回通道、一个统一核验闭环**。

| 部分 | 确定的职责 |
| --- | --- |
| 输入 | 本案件、本批次授权范围内的上游业务模型结果。GaussDB 承担结果读取、筛选和聚合，公开学习版用脱敏快照替代 |
| 第一阶段：宽口径事实构建 | 后端策略库选择确定性算子，对各可处理模型生成轻量画像、可引用事实和跨模型关联摘要 |
| 召回通道 A：确定性召回 | 继承上游已明确命中的事件；仅在有新增判断时补充业务规则或关系分析 |
| 召回通道 B：LLM 语义召回 | 在逐候选补证循环之前，阅读全案的分层事实摘要，形成案件理解和待核验候选；不以命中 A 通道为前提 |
| 候选合并 | 校验、去重、保留来源，在统一候选数量预算下选出后续调查对象 |
| 第二阶段：细粒度补证 | 复用 Investigation Worker，围绕选中的候选调用窄口径工具，生成可复算的补充事实 |
| 集中核验 | 核对来源、主体、时间、反证和缺口；明确缺口转定向 Task，证据不足的事项保留待核验／转人工 |

**初步事实构建只有一套共同的数据基础，初始召回只有两条通道。** 上游模型命中、后端规则和关系分析属于确定性通道内部的处理方式，无须为它们各设计一套 Agent。宽口径画像是两条通道的共同输入，也不单独算一条召回通道。

## 2. 为什么需要这次修正

仅使用预定义阈值和关系条件的候选路径，只会检查已表达的条件。规则和关系查询当然可以发现此前没见过的具体事件，但未必能覆盖尚未编码的业务组合。限制来自条件与输入视野，而不是“确定性计算天然只能识别旧异常”。

LLM 适合补充的是：结合模型业务含义、多个实体和时间摘要，提出值得查证的组合性问题。它不保证发现未知异常，更不能从缺失数据中恢复事实；价值要用新增有效候选和固定预算下的质量实测。

上一版流程把确定性候选池放在 LLM 输入之前，容易形成下列错误：

~~~text
先用风险规则筛出候选 → 只给 LLM 看这些候选 → 声称 LLM 能召回规则漏掉的事件
~~~

最终改为**共享宽口径事实、分别发现、统一合并**。即使确定性通道没有命中，只要存在可处理、可引用的事实，LLM 通道仍可运行。LLM 的候选通过结构与引用校验即可进入待核验池，不必再次满足原先的风险阈值。

还有一条数据边界必须保留：如果某些原始记录已经被上游模型过滤，且在任何模型结果或授权工具可访问范围内都不存在，本系统的两个通道都无法凭空找回它们。“全案理解”指当前输入覆盖范围内的分析，不等于掌握案件全部客观事实。

## 3. 最终数据流

~~~mermaid
flowchart TD
    S["上游业务模型结果：案件 / 批次 / 授权范围"] --> P["第一阶段：策略库 + 确定性粗粒度算子"]
    P --> F["共同事实基础：模型画像 / 事实引用 / 关系与时间摘要"]
    F --> A["通道 A：确定性召回"]
    F --> C["全案上下文：各模型代表事实 + 未命中规则的摘要"]
    C --> B["通道 B：LLM 初始案件理解与候选提议"]
    A --> M["校验、去重、统一选择：最多 K 个候选"]
    B --> M
    M --> T["规划 Task：明确范围、依赖与预算"]
    T --> W["第二阶段：复用 Worker，独立状态，最多双并发"]
    W --> E["精细工具 → 补充事实与引用"]
    E --> V["集中核验"]
    V -->|"明确缺口且有预算"| T
    V -->|"满足交付或停止条件"| R["报告 / 待核验项 / 人工复核"]
~~~

通道 A 与 B 是逻辑上独立的发现路径，不要求物理上同时执行。初期可以顺序调用两者以简化运行；关键是 **B 的输入来自共同事实基础，不是 A 筛选后的子集**。

LLM 生成的“案件理解”是推理摘要，保存在运行状态中，不写入确定性 Fact，不作为额外证据。事实来源于数据与工具；候选表示值得调查；结论表示经过核验后的判断。这三者不能互相替代。

## 4. 第一阶段：后端生成粗粒度事实，LLM 负责阅读理解

### 4.1 处理范围与执行方式

读取当前案件、批次及授权模型范围，建立模型覆盖清单。对有数据且字段契约可处理的模型执行画像；空结果、不支持和失败的模型记录状态，不生成虚构事实。金额小、记录少、没有规则命中，都不是跳过整个模型的理由。

这一阶段由代码根据模型类型和字段角色选择算子，不逐模型询问 LLM“应该怎么算”。SQL 聚合、分批读取或流式统计应尽量靠近数据源执行。“粗粒度”指输出被压缩，并不意味着可以无标记地随便抽样，再把抽样统计冒充全量结果。

### 4.2 最小画像内容

| 内容 | 作用与约束 |
| --- | --- |
| 模型 ID、业务含义、字段角色与口径 | 让 LLM 知道每个指标表示什么；单位、时间范围和结果粒度不能省略 |
| 行数、字段可用性、空值和处理状态 | 描述覆盖情况，区分“未发现”“无数据”“未计算” |
| 金额、次数、类别和时间分布 | 由确定性算子计算；账号、手机号等标识符不能参与金额统计 |
| 实体与关系摘要 | 保留主体、对手方、方向、统计范围和 Fact 引用 |
| 必要的联合摘要 | 按策略生成实体×时间、关系×时间等摘要，减少只留全局 SUM／COUNT 导致的关联信息丢失 |
| 代表性事实与引用 | 覆盖典型分布、尾部／稀有现象和跨模型桥接，不只保留金额最大或已标异常的记录 |
| 已有命中标记 | 作为事实的一部分保留；未命中也允许进入画像与 LLM 输入 |

“字段画像”和“业务规则判断”都是代码计算，但目标不同。前者描述数据和供后续定位，后者决定是否符合某个候选条件。不能把描述性算子也变成“未满足风险阈值就不展示”的过滤器。

同一批模型结果可以同时形成宽口径事实和确定性候选，允许复用计算结果，无须为了流程图强制重复计算。

### 4.3 跨模型关系从哪里来

基于授权结果中的可用实体标识建立案件内关联索引，优先使用带类型的稳定 ID。关联索引不能只从各模型 Top-K 的展示样例构建，否则未展示实体之间的桥接会提前丢失。

按本案范围和时间、关系类型等限制产生关系摘要，不全量展开所有实体组合。只有名字相同、缺少可靠身份映射时，标记为“疑似同一主体待核验”，不能直接合并人物或账户。一个跨模型关联可能只是上下文事实，只有形成具体核验问题时才需要占用候选名额。

### 4.4 Fact 的最小契约

~~~text
Fact
  fact_id
  case_id / snapshot_id / model_id
  kind
  entities
  time_scope
  value + unit
  source_ref          # 源记录 ID 集合，或可恢复的查询范围
  computation_ref     # 算子 / 规则版本与参数
  aggregation_complete
  sample_or_truncation_note
~~~

实现需要表达以上字段语义，具体类名和存储结构可自由选择。若上游只给聚合结果、没有原始流水引用，系统只能追溯和复算到实际可访问的输入层，不能声称已具备原始流水级证据。

## 5. 两条初始召回通道分别做什么

### 5.1 通道 A：确定性召回

统一执行以下逻辑：

- 上游已经明确输出具体事件或可疑对象：接收、规范化和去重。
- 上游只输出统计结果：按必要的案件条件执行规则，形成可定位候选。
- 跨模型组合或关系连接形成新的核验问题：生成关系相关候选。

如果上游与后端检查的是同一条件、同一范围，就不重复计算成第二路发现。后端规则仅在加入新条件或新组合时保留。关系分析归入这个通道，因为它同样按确定的连接与筛选条件执行；无需再把“关系召回”提升为第三条顶层路径。

### 5.2 通道 B：LLM 语义召回

在逐候选补证前设置一个初始分析节点。输入是案件目标、模型业务含义和从共同 FactPack 组装的全案摘要；输出同时包含：

1. 简短的案件理解：目前可见的主要对象、联系、时间特征和信息缺口，引用已有 Fact。
2. 数量受限的待核验候选：具体对象、疑点、依据、需要确认的事项与建议查询范围。

两项通过同一次结构化调用产生，避免为了“概述”“找线索”“再规划一遍”连续调用多个功能重叠的 Agent。初始节点不调用精细工具，所需补证请求交给后续 Worker。

**这个通道必须允许未命中规则的事实进入视野。** 它寻找的是跨模型语义组合、时序疑点或值得对照的现象，不要求先有异常标签，也不要求每个模型都输出一个候选。没有足够依据时，返回空候选数组是有效结果。

### 5.3 两者如何互补

例如（仅作设计示意）：模型甲摘要显示 A 向 B 有若干交易，模型乙显示 B 向 C 有交易，时间摘要有先后关系，但均未达到现有金额／次数阈值。若这些事实被保留，LLM 可以提出“是否存在连续中转”的核验问题，精细工具再检查交易级时间、方向和金额是否真的对应。

这并不说明 LLM 必然优于关系规则：如果后端已实现相同路径条件，A 通道也能找到。新增价值以最终多覆盖了哪些有效事件衡量，不能因为使用了 LLM 就默认产生增量。

## 6. 初始 LLM 上下文与调用方式

### 6.1 从整个事实基础选摘，不从规则候选池裁剪

上下文包含三部分：

- 覆盖目录：哪些模型已处理、空缺或不支持，以及模型业务含义。
- 各可处理模型的紧凑事实摘要：保留稳定引用、实体、时间和关键指标。
- 补充卡片：跨模型桥接、分布变化、尾部与未命中规则的代表性事实。

先为各模型／模型类的基本事实及未命中规则的代表性内容预留空间，再分配剩余空间给重点卡片。不能让所有空间先被高风险标签和金额 Top-K 占完，再“有剩余才考虑探索”。

一期采用简单、可复现的选择方式：按模型类分层，各层内部轮流选取不同实体、时间段和事实类型；合并重复内容，保留桥接事实。无需立即引入跨模型加权评分、学习排序或向量检索。

字段高频 Top-K 只是描述分布；上下文选摘限制输入体积；最终候选 Top-K 控制调查数量。三者分别配置，不共用同一个“风险排序”。

### 6.2 “一次全案理解”的运行约定

默认一个案件做**一次初始分析逻辑阶段**。摘要能放入设定输入预算 B 时，只调用一次 LLM；B 按所用模型上下文容量扣除系统提示、结构化输出和余量设置，运行时实际检查。

若所有模型的必要摘要无法装入 B，按模型类确定性分包，每包生成带原始 Fact 引用的局部提议，再执行一次全案合并分析。合并输入必须同时携带覆盖目录和跨包桥接的原始事实摘要，不能只看局部 LLM 总结，否则容易再次漏掉跨类关联。

分包调用数和总 token 有上限，超过时记录哪些范围未被语义分析覆盖，并按预算降级。不能把“代码已经画像了全部模型”写成“LLM 已详细分析所有事实”。

该阶段是有界结构化推理，不开启自由工具循环。多次物理调用仅用于超长输入分包或有限重试，仍属于同一条 LLM 召回通道。初始分析结果按案件快照、画像／Prompt 版本和模型配置保存；Worker 的每轮补证不重新分析全案。

LLM 无配置、服务失败或输出不合法时，保留 A 通道结果并记录 B 通道状态。有效空结果不作为错误反复重试。

## 7. 候选契约、校验与固定预算选择

### 7.1 两个通道使用同一个候选结构

~~~text
Candidate
  candidate_id                  # 服务端生成
  case_id / snapshot_id
  entities
  event_type_or_question_key
  observed_time_scope           # 未知时显式为空，不编造事件时间
  verification_question
  basis_fact_ids
  requested_model_ids
  requested_time_scope          # 待查询范围，须在授权案件范围内
  origins                       # deterministic / llm，可同时存在
  reason
  status = unverified
~~~

LLM 的“案件理解”不追加进 basis_fact_ids。跨模型假设必须引用实际涉及的模型事实，不能把不存在的实体或关系描述为既知事实；待验证的关系要写成问题。

### 7.2 校验检查什么

代码检查结构、引用是否存在、来源是否在本案范围、已知实体是否有事实支撑、查询范围是否可执行，以及是否存在明确核验问题。机械校验通过只说明“可进入调查”，不说明假设成立。

**不要求 LLM 候选再次命中 A 通道的业务风险规则。** 否则 B 通道仍会被同一个规则边界挡住。缺少任何事实锚点的泛泛怀疑不进入候选；纯数据缺失问题进入覆盖记录，不能伪装成已发生的风险事件。

同一事件由两路提出时只保留一条，合并 origins 和依据。按对象、事件／核验问题和时间范围去重；对象相同但问题不同不能强行合并。多个引用如果来自同一上游记录，核验时不能按来源数量重复加权。

### 7.3 一期选择算法

配置全案候选数量上限 K，两路合并后统一应用，不能让每条通道各输出 K 个进入调查。

为避免语义候选始终被已有规则队列挤掉，一期设置**可配置的 LLM 新候选保留比例**，初始取约四分之一名额；这只是新实现的起始配置，不是已验证的最优比例。K 至少为 2 时，两路都有有效候选应能各保留名额；K 太小无法同时保证两路覆盖，需要显式记录实际选择。

选择步骤：

1. 校验并去重。两路共有的事件进入共同／确定性队列，LLM 独有的有效提议进入探索队列。
2. 确定性队列按明确配置的业务优先级排序；LLM 队列初期采用结构化返回的建议顺序作为可审计启发式，不把模型自报“置信度”当真实风险概率。
3. 分别取预算内的候选；某队列不足时把空余名额给另一队列。没有有效候选不强行凑满 K。
4. 保存两路原始提议、合并结果、入选／未入选原因，方便固定 K 的评测与回放。

召回提升、LLM 比例和排序是否合理，由第 11 节的对照决定。新增通道不应靠扩大总 K 才显得有效。

## 8. 第二阶段：围绕候选调用精细工具补证

你的“双阶段聚合”理解成立。两阶段都使用确定性计算，差别主要在触发方式、处理范围和产出粒度：

| 对比 | 第一阶段：宽口径事实构建 | 第二阶段：细粒度补证 |
| --- | --- | --- |
| 触发 | Runtime 按策略库固定执行 | Worker 根据候选与已获结果提出请求 |
| 范围 | 全部纳入范围、可处理的模型 | 指定实体、关系、时间窗和核验问题 |
| 目的 | 提供覆盖全面但紧凑的发现材料 | 判断某个具体假设的证据是否成立 |
| 算子示例 | 分布、聚合、实体／关系／时间摘要 | 定向切片、完整统计、交易时序与路径核对 |
| 输出 | 基础 FactPack | SupplementFact、引用、完整性状态 |
| LLM 职责 | 阅读摘要、提出候选 | 选择下一步证据、解释支持／削弱与缺口 |

精细工具可复用粗粒度阶段的底层查询和算子，不需要为每个模型重造一套 Runtime。工具参数包括任务身份、案件范围、目标实体和时间条件；后端执行白名单、权限、参数和预算校验。

每个 Task 复用同一 Worker 子图，独立保存状态；依赖满足后最多同时运行两个 Task。候选与 Task 不必一一对应：一个候选可能需要多个有依赖的核验步骤，多个候选也可能复用同一确定性查询结果。

工具输出须区分“统计完整但展示记录截断”“输入只是样本”“查询失败／无数据”。示例记录不能冒充全量证据。来源与计算口径进入追加式证据链，LLM 只据此判断支持、削弱、待核验或终止。

集中核验负责跨任务去重、主体／时间／口径一致性及反证检查。发现明确缺口时生成定向 Task；若发现新的跨组线索，也可加入同一个待核验池，但仍受全案预算和去重约束。这是调查过程的反馈，不额外命名第三条“初始召回通道”。

初始 LLM 分析、工具补证、重试和后续核验都计入全案资源预算；局部 Task 另有上限。预算耗尽时输出停止原因和未解决项，不能把强制停止写成“证据已经充分”。

## 9. Runtime 与最小模块接口

使用 LangGraph 编排目标流程。将初始发现放在“规划”阶段内部，不为每个业务模型创建独立 Agent。图上的阶段组织为：

~~~text
prepare_facts
  → initial_recall     # A 与 B 都执行，B 不依赖 A 的命中
  → merge_and_select
  → plan_tasks
  → investigation_worker / verify
  → summary
~~~

这是受控工作流与局部动态 Agent 的组合；LangGraph 官方文档提供工作流、结构化输出及 orchestrator-worker 等组织方式。具体采用上述业务边界是本项目设计决定。[LangGraph 官方说明](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

下面是职责接口示意，非可直接运行代码：

~~~python
facts, coverage = build_case_profiles(scope, strategy_registry)
det_candidates = recall_deterministic(scope, facts)

# 关键：从全部 scoped facts 打包，不能传 det_candidates 作为唯一素材
contexts = pack_initial_case_context(scope, facts, coverage, input_budget)
overview, llm_candidates = propose_case_candidates(contexts, llm_budget)

candidates = validate_merge_select(
    det_candidates, llm_candidates, facts, candidate_limit=K
)
tasks = build_investigation_tasks(candidates, scope, budgets)
results = run_investigation_tasks(tasks, max_active_tasks=2)
verified = verify_and_request_targeted_followups(results, scope, budgets)
report = render_report(verified)
~~~

接口函数按职责放入同一应用内的模块，不要求每个函数各建服务。每次运行至少保存 Fact 引用、覆盖清单、两路候选与状态、入选结果、Task 状态和证据引用。LLM overview 与 Fact 分开存储。

## 10. 实现时各模块交付什么

下面是目标模块的职责，不要求沿用旧代码的入口、类名或执行顺序。符合这些职责的代码可复用，不符合的应调整；是否重构取决于目标职责，不能为了保留旧结构牺牲召回覆盖。

| 模块 | 输入 | 交付与验收重点 |
| --- | --- | --- |
| 事实构建 | 案件范围、模型结果、字段与算子策略 | 可复算 FactPack、覆盖清单及关联索引；未命中风险条件的模型也有画像 |
| 初始召回 | 共同事实基础与案件目标 | 确定性候选、LLM 候选及两路状态；任一路没有命中，不阻断另一路 |
| 上下文组装 | 全范围事实、模型业务含义、输入预算 | 有引用的分层摘要、未展示范围；不能只摘录规则候选或全局金额 Top-K |
| 候选管理 | 两路提议及 Fact 索引 | 结构与范围校验、事件去重、固定 K 选择；不重复施加原风险阈值 |
| 任务执行 | 入选候选、查询权限、预算 | 有依赖的 Task、共享 Worker 实现、独立状态和精细工具结果 |
| 集中核验与报告 | Task 结果及原始事实引用 | 支持／削弱／未解决项、定向补证与人工复核入口、可追踪报告 |

这些模块在同一进程内即可实现，无须拆成微服务或多个自治 Agent。优先把数据契约、两路输入边界和核验闭环跑通，再按测量结果调整缓存、并发和排序。

## 11. 按这个顺序实现与验收

1. **固定事实契约与范围。** 在案件输入入口实现覆盖清单、完整性标记和稳定引用。用小样本核对每个算子输出及模型范围，建立全范围的粗粒度事实基础。
2. **抽出确定性候选。** 继承上游有效命中，消除重复规则，明确候选身份。保持 LLM 关闭时仍能运行完整链路。
3. **实现全案初始上下文与 LLM 提议。** 先用固定返回的测试替身验证 schema、引用和范围，再接实际模型；同时输出 overview 与候选。允许零候选、超限分包和失败降级。
4. **统一合并并接入 Task。** 总 K 固定，候选不重复，来源可追踪；只有入选任务进入精细补证。落实 Worker、证据链、核验与停止条件。
5. **离线对照后采用新路径。** 先保存 LLM 提议并与标签对照，再决定其排序／保留比例和进入真实调查的范围。不能直接把新增调用等同于质量提升。

必须覆盖的验收场景：

- A 通道零命中，但 FactPack 非空：B 仍运行，合法且有依据的候选可进入调查。
- 某模型没有异常标签：其代表性事实仍有机会进入初始上下文。
- 两路命中同一事件：候选只计一次，原始证据不重复算。
- 跨组桥接实体不是金额 Top-K：关联索引与相应摘要仍可保留它。
- LLM 引用虚构 Fact、越界实体或超范围时间：拒绝；仅仅“未触发风险阈值”不是拒绝理由。
- LLM 返回有效空数组、超时或非法结构：状态可区分，确定性路径可继续，重试不越预算。
- 输入超过上下文容量：可分包并保留跨包事实；未处理范围可见，不声称完成全量语义分析。
- 精细补证否定初始假设：结论被削弱／撤回，不因初始 LLM 提议而固定成风险事件。
- 暂停恢复后，初始分析结果可复用、证据不重复写入，全案与 Task 预算不被重置绕过。

评测至少比较“确定性通道单独运行”和“固定总 K 的双通道运行”。先比较候选 Recall@K 和 LLM 独有候选的有效率，再比较精细补证后的最终 Precision／Recall、token／工具成本及端到端时延。对上下文选择与新增规则／关系能力单独消融，避免把所有收益都归给 LLM。

案件快照、目标事件定义、标注集、总 K、模型／Prompt 版本和资源预算需要记录；按案件隔离调参与评测，防止同案泄漏。新增初始 LLM 调用可能增加时延，应同时测量候选增益与代价，再据此确定生产预算。

## 12. 学习时只记住这一条主线

**先由后端算出可靠且覆盖充分的粗粒度事实；再同时用确定性条件和 LLM 语义理解提出候选；最后围绕有限候选调用精细工具，把疑点核实成有来源的判断。**

其中：事实构建解决“把模型结果整理成可用信息”；双通道召回解决“哪些问题值得继续查”；精细补证与集中核验解决“这个判断究竟有没有证据”。LLM 初始分析与后续补证循环各有职责，前者发现问题，后者围绕问题取证。

补充参考：长上下文研究提示输入很长并不保证信息被均匀利用，因此本方案要求分层摘要、覆盖记录和必要时分包。具体效果仍须在部署模型上验证。[Lost in the Middle](https://arxiv.org/abs/2307.03172)
