# 上下文压缩策略详细设计

> 本文档是 Agent 系统中**上下文工程（Context Engineering）**的施工级设计说明。
> Codex 应基于此文档实现各级 LLM 调用的上下文压缩逻辑。
>
> 核心问题：LLM 没有记忆，每一次调用都是无状态的。Agent 循环中的所有信息传递——
> Baseline 事实、工具执行结果、前几轮的判断结论、可用的工具列表、预算状态——
> 都必须由我们在每次 API 调用时，精确地、压缩地放入上下文窗口。
> 放入什么、不放什么，直接决定了 LLM 的决策质量。
>
> 阅读前提：已理解 `模型级Investigation-Agent详细设计.md` 中的循环骨架，
> 以及 `专属工具详细设计.md` 中的工具产出结构。

## 一、当前上下文工程的诊断

### 1.1 当前各 LLM 调用的上下文尺寸（基于 run_audit.json 实测）

| LLM 角色 | 当前上下文大小 | 主要组成 | 问题 |
|---|---|---|---|
| Planner（模型类级，初始假设生成） | ~4,800 chars | ModelClassPack brief | 包含了过多模型的全部 Top5 实体，大量无关信息 |
| Planner（模型类级，循环内决策） | ~5,000 chars | class_context + hypothesis + previous_rounds | previous_rounds 未压缩，Judge assessment 原文照搬 |
| Judge（证据判断） | ~3,000 chars | hypothesis + supplement_facts | 工具产出的 summary 是全文，关键结构字段（anomaly_flags）未传 |
| Final Writer（断言生成） | ~18,000 chars | 3 条 evidence chain 的完整 payload | **过大**。base_facts 和 supplement_facts 的 evidence_values 包含了大量 LLM 不会用到的原始字段 |

### 1.2 核心问题总结

1. **压缩不够**：Final Writer 的 18k chars 中，约 60% 是冗余的原始记录引用和完整指标列表，LLM 实际上只需要摘要
2. **结构不对**：Judge 拿到的是工具的 free-text summary，而不是结构化 anomaly_flags
3. **信息不全**：Planner 的上下文中缺少"已调用工具指纹"，导致可能重复调用
4. **跨轮次信息衰减**：previous_rounds 使用原文截断（`[:200]`），关键判断依据可能被截掉
5. **没有分层压缩**：所有信息以同等密度呈现，没有区分"核心决策依据"和"背景参考信息"

## 二、压缩策略的总原则

### 原则 1：区分"决策层"和"参考层"

```
决策层（LLM 必须仔细阅读才能做决定的）
  - 当前假设的 statement
  - 上一轮 Judge 的状态和核心理由
  - 可用工具列表和参数 schema
  - 预算剩余（还能调用几次）
  → 放在 context 的前面，简洁明确

参考层（LLM 需要时可以查阅，但不需要逐字分析）
  - Baseline 的 TopK 实体列表
  - 工具的完整结构化产出
  - 已调用的工具指纹列表
  → 放在 context 的后面，结构化呈现
```

### 原则 2：基于角色的差异化压缩

不同的 LLM 角色需要看到不同的信息切片——它们不是同一个上下文的子集，而是**同一组底层数据的不同投影**。

```
Planner 的投影：   "有哪些值得调查的对象？有哪些可用的调查手段？之前查了什么？"
Judge 的投影：     "假设是什么？补证产出了什么结构化证据？有没有异常标记？"
Final Writer 的投影："有哪些已确认的断言？每条断言引用了哪些事实和补证？"
```

### 原则 3：稳定引用 + 摘要替代原文

- 事实和证据用 `fact_id` / `supplement_fact_id` 引用，不嵌入全文
- 工具产出的 `evidence_records`（原始数据行）不出现在 LLM 上下文中
- 前几轮的完整 chain_step 不传递，只传递压缩摘要

### 原则 4：渐进式上下文

Agent 循环中，第一轮的上下文仅包含 Baseline + 假设 + 工具列表。第二轮在上一轮的基础上追加"Round 1 摘要"。不是每次都重新构建完整上下文，而是增量追加。

## 三、各级 LLM 调用的上下文规格

### 3.1 模型级 Planner（Model Investigation Planner）

**调用时机**：模型级 Agent 的每一轮循环开始时。

**LLM 的任务**：在给定的模型上下文中，选择一个工具来调查当前假设，或决定停止。

**目标尺寸**：3,000 - 5,000 chars（最大不超过 6,000）。

**上下文结构**：

```python
def build_model_planner_context(
    model_id: int,
    model_baseline: dict[str, Any],     # 本模型 BaselinePack
    hypothesis: dict[str, Any],         # 当前假设
    previous_rounds: list[dict[str, Any]], # 前几轮摘要（压缩后）
    available_tools: list[dict[str, Any]], # 可用工具列表（含专属工具）
    already_called_fingerprints: list[str], # 已调用工具指纹
    budget: dict[str, int],            # 剩余预算
) -> dict[str, Any]:
    """
    构建模型级 Planner 的压缩上下文。

    压缩策略：
    - Baseline 420k 行 → 压缩到 ~1,500 chars（只给 Top3 实体 + 关键指标）
    - 前几轮 → 每轮压缩到 ~200 chars（工具名 + 参数 + Judge 状态 + 一句话理由）
    - 工具列表 → 每个工具 ~100 chars（名称 + 一句话描述 + 必需参数）
    """
    ctx = model_baseline.get("model_context", {})

    # ── 第 1 层：调查范围（~200 chars）──
    scope = {
        "model_id": model_id,
        "model_name": _clean_name(ctx.get("model_name")),
        "model_kind": ctx.get("model_kind"),
        "result_count": ctx.get("result_count"),
        "data_note": _data_scale_note(ctx.get("result_count", 0)),
        # "该模型在本次案例中共42万条记录。以下仅展示最值得关注的前3个主体。"
    }

    # ── 第 2 层：当前假设（~300 chars）──
    current_hypothesis = {
        "hypothesis_id": hypothesis.get("hypothesis_id"),
        "entity_name": hypothesis.get("entity_name"),
        "statement": hypothesis.get("statement"),
        "basis_fact_ids": hypothesis.get("basis_fact_ids", []),
    }

    # ── 第 3 层：Baseline 压缩快照（~1,500 chars）──
    # 只包含 Top3 实体和 Top2 关系——这是"菜单"，Planner 从中选择调查对象
    compressed_baseline = _compress_model_baseline_for_planner(
        model_baseline, max_entities=3, max_relations=2
    )

    # ── 第 4 层：前几轮调查摘要（每轮 ~200 chars，最多 3 轮）──
    compressed_history = _compress_investigation_history(previous_rounds, max_rounds=3)

    # ── 第 5 层：可用工具（每个 ~120 chars）──
    tool_list = _format_tools_for_planner(available_tools)

    # ── 第 6 层：约束和预算（~100 chars）──
    constraints = {
        "already_called": already_called_fingerprints[-5:],
        # ["relation_neighbor_subgraph(entity=示例主体A)",
        #  "entity_model_slice(model=86, entity=示例主体A)"]
        "budget": budget,
        # {"rounds_remaining": 2, "calls_remaining": 2}
        "rules": [
            "不要重复调用已使用的工具（除非参数不同且你有明确理由）",
            "如果上一轮 Judge=unresolved，先考虑是否需要用不同工具收窄调查范围",
            "不要使用 time_range 参数",
            "参数中的 entity_name 必须来自 baseline 或 previous_rounds",
        ],
    }

    return _assemble_context(
        scope=scope,
        hypothesis=current_hypothesis,
        baseline=compressed_baseline,
        history=compressed_history,
        tools=tool_list,
        constraints=constraints,
    )
```

**Baseline 压缩函数**：

```python
def _compress_model_baseline_for_planner(
    model_baseline: dict[str, Any],
    max_entities: int = 3,
    max_relations: int = 2,
) -> dict[str, Any]:
    """
    将完整的 ModelBaselinePack 压缩为 Planner 需要的"菜单"视图。

    压缩率：~50,000 chars → ~1,500 chars（约 30:1）

    包含内容：
    - Top K 实体的名称、fact_id、记录数、金额和、金额最大值、风险标签
    - Top K 关系的 source/target、fact_id、记录数、金额和
    - 关键全局指标（如总实体数、总金额量级）

    排除内容：
    - 实体的完整 metrics（中位数、分位数、金额分箱、时间桶）
    - evidence_records（原始数据行）
    - field_profile_summary
    - category_topk
    - 排名在 K 之后的实体/关系
    """
    entities = []
    for e in model_baseline.get("focus_entities", [])[:max_entities]:
        metrics = e.get("metrics", {})
        # 只提取 Planner 需要知道的字段
        entities.append({
            "entity_name": e.get("entity_name"),
            "entity_type": e.get("entity_type"),
            "fact_id": e.get("fact_id"),
            "rank": e.get("rank"),
            # 只保留最关键的 4 个数字
            "record_count": metrics.get("record_count"),
            "amount_sum": metrics.get("amount_sum"),
            "amount_max": metrics.get("amount_max"),
            "distinct_counterparty_count": metrics.get("distinct_counterparty_count"),
            # 风险标签（中文，方便 Planner 理解）
            "risk_signals": [
                _cn_risk_tag(f.get("risk_tag"))
                for f in e.get("anomaly_flags", [])
            ],
        })

    relations = []
    for r in model_baseline.get("relation_profiles", [])[:max_relations]:
        relations.append({
            "fact_id": r.get("fact_id"),
            "source": r.get("source"),
            "target": r.get("target"),
            "count": r.get("count"),
            "amount_sum": r.get("amount_sum"),
            "risk_signals": [
                _cn_risk_tag(f.get("risk_tag"))
                for f in r.get("anomaly_flags", [])
            ],
        })

    key_metrics = model_baseline.get("key_metrics", {})
    return {
        "focus_entities": entities,
        "key_relations": relations,
        "distinct_entity_count": key_metrics.get("distinct_entity_count"),
        "total_amount_magnitude": _amount_magnitude(key_metrics.get("total_amount")),
        # 不暴露具体值，只给量级："亿级" / "千万级" / "百万级"
    }
```

**调查历史压缩函数**：

```python
def _compress_investigation_history(
    previous_rounds: list[dict[str, Any]],
    max_rounds: int = 3,
) -> list[dict[str, Any]]:
    """
    将完整的 InvestigationRound 列表压缩为 Planner 需要的"决策日志"。

    压缩策略：
    - 只保留最近 max_rounds 轮
    - 每轮压缩为 ~200 chars 的结构化摘要
    - 工具产出的完整 structured 字段不传递
    - 只传递：工具名、参数、命中行数、Judge 状态、Judge 的一句话理由
    """
    compressed = []
    for r in previous_rounds[-max_rounds:]:
        compressed.append({
            "round": r.round_index if hasattr(r, 'round_index') else r.get("round"),
            "tool_used": r.tool_name if hasattr(r, 'tool_name') else r.get("tool_called"),
            "params": _summarize_params(
                r.params if hasattr(r, 'params') else r.get("params", {})
            ),
            "result": _summarize_tool_result_for_planner(r),
            # 示例："命中15,619条；enhanced。自转账占比76%，夜间48%，HHI极高"
            "judge_status": r.judge_status if hasattr(r, 'judge_status') else r.get("judge_status"),
            "judge_key_point": _extract_judge_key_point(
                r.judge_assessment if hasattr(r, 'judge_assessment') else r.get("judge_assessment", "")
            ),
            # 示例："自转账主导+夜间高频+资金循环 → 增强"
        })
    return compressed


def _extract_judge_key_point(assessment: str) -> str:
    """
    从 Judge 的 assessment 中提取最关键的一句话（≤80 chars）。

    策略：取第一句或包含"增强/削弱/未解决"关键信号的句子。
    """
    if not assessment:
        return ""
    # 若包含"增强"相关信号，提取它
    for keyword in ["证据增强", "形成同向支撑", "交叉印证", "实质支撑",
                     "证据削弱", "排除", "待进一步核查", "信息不足"]:
        if keyword in assessment:
            # 找到包含关键词的句子
            for sent in assessment.replace("；", "。").split("。"):
                if keyword in sent and len(sent) > 10:
                    return sent.strip()[:80]
    # fallback：取第一句
    first = assessment.split("。")[0].strip()
    return first[:80] if len(first) > 10 else assessment[:80]
```

### 3.2 模型类级 Planner（ModelClass Corroboration Planner）

**调用时机**：模型类级 Agent 的每一轮循环开始时。

**LLM 的任务**：验证同一主体在同类多个模型中是否形成交叉印证，选择跨模型调查工具。

**目标尺寸**：3,500 - 5,500 chars。

**与模型级 Planner 上下文的关键差异**：

| 维度 | 模型级 Planner | 模型类级 Planner |
|---|---|---|
| 调查范围 | 1 个模型 | 同一模型类内的多个模型 |
| 关注点 | 深挖一个模型内的主体行为 | 验证跨模型交叉印证 |
| 工具权限 | 只能选本模型的工具 | 可选本类内任意模型的工具 |
| 已有结论引用 | 无（模型级 Claim 正在形成中） | 可引用已形成的模型级 Claim |

**上下文结构**：

```python
def build_model_class_planner_context(
    class_name: str,
    class_pack: dict[str, Any],            # ModelClassPack
    model_baselines: dict[int, dict],      # 本类内各模型的压缩 Baseline
    model_claims: dict[int, list[dict]],   # 已形成的模型级 Claim（如有）
    hypothesis: dict[str, Any],            # 当前跨模型假设
    previous_rounds: list[dict],           # 前几轮摘要
    available_tools: list[dict],           # 可用工具（含各模型的专属工具）
    budget: dict[str, int],
) -> dict[str, Any]:
    """
    构建模型类级 Planner 的压缩上下文。

    核心思路：
    - 按"共享实体"组织信息——不是按模型列表组织
    - 突出跨模型出现的实体及其在各模型中的表现
    - 列出已形成的模型级 Claim（可以直接引用，不需要重复调查）
    - 工具列表按模型分组，标注每个工具属于哪个模型
    """

    # ── 第 1 层：本类概况（~300 chars）──
    class_scope = {
        "class_name": class_name,
        "models": [
            {"model_id": mid, "model_name": _clean_name(info.get("model_name")),
             "result_count": info.get("result_count")}
            for mid, info in _class_model_summaries(class_pack).items()
        ],
        "total_result_count": class_pack.get("total_result_count"),
    }

    # ── 第 2 层：跨模型共享实体（~1,500 chars）──
    # 这是模型类级 Planner 最重要的信息
    shared_entities = _compress_shared_entities_for_class_planner(class_pack)

    # ── 第 3 层：已有模型级 Claim（~500 chars）──
    existing_claims = _compress_model_claims_for_class_planner(model_claims)

    # ── 第 4 层：当前跨模型假设（~200 chars）──
    current_hypothesis = {...}

    # ── 第 5 层：工具（按模型分组，~1,200 chars）──
    tools_by_model = _format_tools_by_model(available_tools)

    # ── 第 6 层：历史和预算（~500 chars）──
    ...

    return _assemble_context(...)
```

### 3.3 Judge（证据判断器）

**调用时机**：每轮工具执行完毕后。

**LLM 的任务**：基于假设和补证事实的结构化产出，判断证据状态（enhanced / weakened / unresolved）。

**目标尺寸**：2,000 - 3,500 chars。

**上下文结构**（改进版）：

```python
def build_judge_context(
    hypothesis: dict[str, Any],
    supplement_facts: list[dict[str, Any]],   # 本假设下的所有补证
    prior_judge_assessments: list[dict],      # 前几轮的 Judge 结论（如有）
) -> dict[str, Any]:
    """
    构建 Judge 的压缩上下文。

    关键改进（vs 当前 _build_judge_brief）：
    1. 传递工具的 structured 字段和 anomaly_flags（不是只有 summary 文本）
    2. 传递"判断提示"：给出基于 anomaly_flags 的判定建议
    3. 区分"本轮新证据"和"历史证据"
    """

    # ── 第 1 层：假设（~200 chars）──
    hypothesis_view = {
        "entity_name": hypothesis.get("entity_name"),
        "statement": hypothesis.get("statement"),
        "basis_fact_ids": hypothesis.get("basis_fact_ids", []),
    }

    # ── 第 2 层：本轮补证的结构化证据（~1,500 chars）──
    evidence_items = []
    for fact in supplement_facts:
        output = fact.get("output", {})
        evidence_items.append({
            "source": f"{_cn_tool_name(fact.get('tool_name'))}",
            "params": _summarize_params(fact.get("params", {})),
            # ── 关键改进：传递 structured 和 anomaly_flags ──
            "structured_findings": output.get("structured", {}),
            #   如：{"self_transfer_ratio": 0.76, "night_ratio": 0.48,
            #        "counterparty_hhi": 3200, "fund_cycle_count": 3}
            "anomaly_flags": output.get("anomaly_flags", []),
            #   如：["self_transfer_dominant", "night_intensive",
            #        "high_concentration", "fund_cycle_detected"]
            "summary": output.get("summary", ""),
            # 保留文本 summary 作为辅助参考
            "data_quality": {
                "rows_read": output.get("rows_read"),
                "truncated": bool(output.get("truncated")),
                "aggregation_complete": output.get("aggregation_complete", True),
            },
        })

    # ── 第 3 层：前几轮判断摘要（如有，~300 chars）──
    prior_summary = []
    for prior in prior_judge_assessments[-2:]:
        prior_summary.append({
            "round": prior.get("round"),
            "status": prior.get("status"),
            "key_point": _extract_judge_key_point(prior.get("assessment", "")),
        })

    # ── 第 4 层：判断规则提示（~300 chars）──
    judge_guidance = {
        "decision_rules": [
            "如果 anomaly_flags 包含 >= 2 个独立标记 → 应判断为 enhanced",
            "如果 anomaly_flags 包含 'self_transfer_dominant'、'fund_cycle_detected'、'suspected_split_transfer'、'structured_in_scattered_out' 中的任意一个 → 应判断为 enhanced（这些是关键标记）",
            "如果 truncated=true 或 aggregation_complete=false → 必须判断为 unresolved",
            "如果补证仅说明有记录命中但 anomaly_flags 为空 → 判断为 unresolved",
            "如果补证返回 0 条记录 → 判断为 weakened",
        ],
        "assessment_requirements": [
            "使用自然中文，不出现内部字段名（如 top_outgoing、row_count 等）",
            "先给出结论（增强/削弱/未解决），再说明依据",
            "明确指出支撑判断的具体 anomaly_flags 或数据特征",
            "最多 200 字",
        ],
    }

    return _assemble_context(
        hypothesis=hypothesis_view,
        evidence=evidence_items,
        prior=prior_summary,
        guidance=judge_guidance,
    )
```

**为什么给 Judge 传递 anomaly_flags 而不是让它自己从 summary 文本中推断？**

```
# 当前方式：Judge 读 summary 文本 → 自己推断
summary: "示例主体A在关系模型中共若干条记录，自转账占比X%，夜间占比Y%..."
Judge 需要：理解"76%自转账"意味着什么 → 判断是否异常 → 判断是否增强假设
结果：依赖 LLM 的世界知识和推理能力，不一致性高

# 改进方式：Judge 接收 anomaly_flags + 规则提示
anomaly_flags: ["self_transfer_dominant", "night_intensive", "high_concentration", "fund_cycle_detected"]
guidance: ">= 2 个独立标记 → enhanced"
Judge 需要：确认 anomaly_flags 是否 ≥ 2 → 撰写中文 assessment 解释为什么增强
结果：LLM 做它擅长的事（自然语言表达），确定性规则做它擅长的事（判断逻辑）
```

### 3.4 Final Writer（结构化断言生成器）

**调用时机**：所有 Agent 循环完成后，生成最终断言列表。

**LLM 的任务**：将每条 evidence chain 转化为一条结构化断言（assertion）。

**目标尺寸**：6,000 - 10,000 chars（当前 ~18,000 chars，需要压缩 ~40%）。

**上下文结构**（改进版）：

```python
def build_final_writer_context_v2(
    case_id: int,
    evidence_chains: list[dict[str, Any]],
    model_names: dict[int, str],
) -> dict[str, Any]:
    """
    构建 Final Writer 的压缩上下文。

    关键改进（vs 当前 _build_final_writer_context）：
    1. 不传递 base_facts 的完整 evidence_values（~4,000 chars 冗余）
    2. 不传递 supplement_facts 的完整 evidence_values（~6,000 chars 冗余）
    3. 每条 chain 压缩到 ~1,500 chars（当前 ~4,000 chars）
    4. 增加 known_entities 和 known_fact_ids 的校验清单（仅用于 LLM 知道自己不能创造什么）
    """

    chains = []
    for chain in evidence_chains:
        hypothesis = chain.get("hypothesis", {})
        supplements = _get_supplements_for_chain(chain)

        chains.append({
            "evidence_chain_id": chain.get("chain_id"),
            "model_ids": _extract_model_ids(chain),
            "model_class": _extract_model_class(chain),

            # 假设（~200 chars）
            "hypothesis": {
                "entity_name": hypothesis.get("entity_name"),
                "statement": hypothesis.get("statement"),
                "basis_fact_ids": hypothesis.get("basis_fact_ids", []),
            },

            # 最终状态和 Judge 结论（~300 chars）
            "final_status": chain.get("final_status"),
            "judge_assessment": _last_judge_assessment(chain),

            # 补证摘要（每个 ~250 chars，不含 evidence_values）
            "supplement_summaries": [
                {
                    "supplement_fact_id": s.get("supplement_fact_id"),
                    "tool_name": s.get("tool_name"),
                    "summary": s.get("output", {}).get("summary", ""),
                    "anomaly_flags": s.get("output", {}).get("anomaly_flags", []),
                    "rows_read": s.get("output", {}).get("rows_read"),
                    "truncated": bool(s.get("output", {}).get("truncated")),
                }
                for s in supplements
            ],

            # 允许的数字 token 列表（用于校验，~100 chars）
            "allowed_numeric_tokens": sorted(
                _allowed_numeric_tokens(_compress_chain_for_tokens(chain))
            )[:30],
        })

    return {
        "case_id": case_id,
        "total_result_count": _get_total_count(),
        "known_entities": _get_all_entity_names()[:50],
        "known_fact_ids": _get_all_fact_ids()[:50],
        "known_supplement_fact_ids": _get_all_supplement_ids()[:30],
        "chains": chains,
    }
```

### 4.2 传递什么、不传递什么

| 信息类型 | 是否入 Planner 上下文 | 是否入 Judge 上下文 | 是否入 Final Writer 上下文 |
|---|---|---|---|
| 原始数据行（evidence_records） | ❌ 不入 | ❌ 不入 | ❌ 不入 |
| 工具的完整 structured 字段 | ❌ 不入（只给 anomaly_flags） | ✅ 入（核心决策依据） | ❌ 不入 |
| 工具的 anomaly_flags | ✅ 入（作为上轮结果摘要） | ✅ 入（核心决策依据） | ❌ 不入（Judge 已消费） |
| 工具的 human-readable summary | ✅ 入 | ✅ 入（辅助参考） | ✅ 入 |
| 完整 metrics（中位数/分位数/分箱） | ❌ 不入 | ❌ 不入 | ❌ 不入 |
| fact_id / supplement_fact_id 引用 | ✅ 入（用于追溯） | ✅ 入 | ✅ 入（必须） |
| Judge 的完整 assessment | ❌ 不入（只给 key_point） | N/A | ✅ 入 |
| Judge 的 key_point（一句话） | ✅ 入 | ✅ 入（前几轮） | N/A |
| 已调用工具指纹 | ✅ 入（防重复） | ❌ 不入 | ❌ 不入 |
| 预算剩余 | ✅ 入 | ❌ 不入 | ❌ 不入 |
| 判断规则提示 | ❌ 不入 | ✅ 入 | ❌ 不入 |

## 五、压缩技术工具箱

### 5.1 实体级截断（Entity Truncation）

```
策略：只保留 Top K 个实体/关系。K 的取值：
  - Planner: K=3（实体）, K=2（关系）
  - Judge: 不适用（Judge 只看本轮工具产出，不是全量 Baseline）
  - Final Writer: 不适用（Final Writer 只消费已形成的 Chain）

理由：Planner 只需要知道"谁最值得调查"，不需要看到排第 15 的实体。
```

### 5.2 指标精简化（Metric Simplification）

```
策略：只保留 LLM 决策相关的指标，删除"背景统计"指标。

保留（Planner 需要）：
  - record_count（规模判断）
  - amount_sum（金额量级判断）
  - amount_max（极端值判断）
  - distinct_counterparty_count（关系复杂度判断）
  - anomaly_flags / risk_signals（风险信号，最重要）

删除（Planner 不需要）：
  - amount_p50, amount_p95（中位数/分位数）
  - amount_bins（金额分箱）
  - night_count（绝对数——night_ratio 已包含信息）
  - hourly_counts（具体到小时的计数）
  - amount_avg（平均值——在极端偏态下误导性大）
```

### 5.3 时间窗口摘要（Time Window Summarization）

```
策略：不传递具体日期列表，只传递"时间特征"。

不是：
  dates: ["2024-03-15", "2024-03-16", "2024-03-17", ...]（共 200 个日期）

而是：
  time_summary: "交易时间跨度19年（2007-2026），近3年活跃度明显上升，
                主要集中在3-6月和9-12月"
```

### 5.4 对手方摘要（Counterparty Summarization）

```
策略：不传递完整对手方列表，只传递分类统计和 TopK。

不是：
  counterparties: ["示例机构A", "示例业务类型", "示例对手方B", ...]（共 N 个）

而是：
  counterparty_summary: "共792个对手方。主要流出对象：基金认申购账户（864笔）、
                       示例对手方B（N笔/N元）等。主要流入来源：示例业务类型（N笔）、
                       示例现金来源（N笔）、示例对手方C（N笔）等。个人对手方占比X%，企业占比Y%。"
```

### 5.5 调查历史压缩（Investigation History Compression）

```
策略：每轮调查摘要 ≤ 200 chars，最多保留 3 轮。

压缩模板：
  Round {N}: {tool_name}({params_summary})
  → 命中 {row_count} 条。{key_finding_1}；{key_finding_2}。
  Judge: {status}（{reason_summary}）

示例：
  Round 1: transfer_structure_analyzer(entity=示例主体A)
  → 命中 15,619 条。自转账占比76%异常高；夜间48%；HHI极高；3组资金循环。
  Judge: enhanced（4项异常标记 → 交叉支撑）

  Round 2: counterparty_identity_profiler(entity=示例主体A)
  → 对手方792个。金融机构对手方资金占比最高；检测到2个可疑过桥账户。
  Judge: enhanced（过桥账户+机构集中 → 增加一层证据）
```

### 5.6 分层标记（Tiered Signaling）

```
策略：用视觉标记区分信息的重要性层级，帮助 LLM 快速定位关键信息。

在 system prompt 中使用标记：
  【必须遵守】  → 硬约束（如"不要创造新实体"）
  【关键证据】  → 本轮最重要的发现（如 anomaly_flags）
  【背景参考】  → 辅助信息（如模型基本信息）
  【历史摘要】  → 前几轮的调查记录
  【可用工具】  → 工具列表

在 user message（JSON context）中使用字段命名：
  "key_finding":     → 最重要的发现（放在最前面）
  "supporting_data": → 支撑数据
  "context":         → 背景信息
  "constraints":     → 约束条件
```

- 移除 evidence_values 中的冗余字段
- 目标：从 ~18k chars 压缩到 ~8k chars
- 验证：不影响断言质量

### 6.2 上下文尺寸监控

每个 LLM 调用后，在 audit 中记录 `context_chars`。当前已在 `_build_final_writer_context` 中有 `context_chars` 字段。应扩展到 Planner 和 Judge：

```python
# 在 planner_audit 和 judge_audit 中增加
"context_chars": len(json.dumps(context, ensure_ascii=False, default=str))
```

### 6.3 压缩效果的验证方法

不是精确的 A/B 测试，而是定性检查：

1. **Planner**：是否选择了最合适的工具（而非总选第一个）？是否在 unresolved 后选择了不同的收窄方向？
2. **Judge**：有了 anomaly_flags 后，判断是否更一致（相同的 anomaly_flags 组合在不同的 hypothesis 下是否产生一致的判断）？
3. **Final Writer**：压缩后的 context 是否仍能生成完整的 assertions（3 条 chain → 3 条 assertion，无遗漏）？
