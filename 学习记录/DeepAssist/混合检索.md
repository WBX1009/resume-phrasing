# DeepAssist｜混合检索

## 简历条目

> **混合检索：**用 **LangChain Runnable** 组合检索链路，以 **BGE-M3** 编码，结合 **Chroma** 向量检索与 **Elasticsearch** 关键词检索；经 **RRF** 融合后用 **Cross-Encoder** 重排，生成回答后校验引用对应关系。

## 第一阶段：本条理解

> **确认状态：已确认。** 按用户确认的主线整理，并对齐当前实现的长度预算与引用检查范围。

**这条工作的核心，是结合语义匹配与关键词匹配找到相关资料，经融合、重排筛选后交给模型生成回答，并让回答中的引用能够追溯到具体资料。**

在 DeepAssist 的知识库问答功能中，用户的提问和文档可能意思接近、表达方式不同，也可能包含需要精确匹配的专业术语或名称。因此，需要结合**语义检索和关键词检索各自的优势，尽量找到与问题相关的资料，减少遗漏**；找到候选内容后，还要进一步判断哪些更适合回答问题，再整理给模型。

### 1. 文档入库时，为同一批文本块建立两类索引

先将文档拆成适合检索的文本块，每个文本块包含**正文、唯一标识（ID）以及来源等元数据**。同一文本块在两路使用相同的 ID，便于后续合并候选。

一方面，用 **BGE-M3** 将文本块正文编码为向量，再由 **Chroma** 保存向量及其关联的正文、标识和元数据，并建立向量索引，方便后续快速查找语义相近的文本块。

另一方面，将文本块正文、标识和元数据写入 **Elasticsearch**。Elasticsearch 通过文本分析器将正文拆分为词项，并建立**从词项到包含该词项的文本块的倒排索引**，方便后续根据查询中的关键词快速找到相关文本块。

这里，**BGE-M3 负责把文本转换成向量，Chroma 负责存储和检索这些向量**。

### 2. 用户提问后，通过向量和关键词两路检索，分别找出候选文本块

向量检索这一路，用同一个 **BGE-M3** 模型将问题编码为**查询向量**，再由 **Chroma** 查找语义相近的文本块，侧重发现**意思接近、表达方式可能不同**的内容。

关键词检索这一路，将查询文本交给 **Elasticsearch**，通过文本分析器将其处理为词项，再利用倒排索引进行匹配和相关性排序，侧重发现**包含专业术语、名称等特定表达**的内容。

两路各自返回一组排好序的候选文本块，供后续融合与重排。

### 3. RRF 根据文本块在两路结果中的排名，将候选结果合并排序

两种检索方式的原始分数计算方式和取值范围不同，缺乏直接可比性，不适合简单相加。

**RRF 不直接使用原始分数，而是根据每个文本块在各路结果中的排名计算贡献，排名越靠前，贡献越大。** 如果同一文本块被两路检索到，就根据 ID 合并为一个候选，并累加两路贡献；只被一路检索到的，则保留该路贡献，最后根据融合分数统一排序。

采用**加权 RRF** 时，还可以为两路设置不同权重，调整它们对融合结果的影响。

### 4. Cross-Encoder 结合问题和候选正文，进一步判断相关性并重新排序

RRF 主要根据两路检索的已有排名融合候选；Cross-Encoder 则将“问题＋一个候选文本块”一起输入模型，计算相关性分数，再据此重新排序，选出靠前的内容供回答使用。

**这里采用的是先召回、后精排的两阶段检索方案。** 在文档入库阶段，提前完成文本块的向量编码、文本分析和索引构建。虽然这些预处理需要消耗时间和计算资源，但建立的索引可以反复使用，避免每次查询都重新处理整个知识库。查询文本本身的向量编码和文本分析，仍在查询时进行。

用户提问后，向量检索和关键词检索利用已建立的索引，较快地从大量资料中找出可能相关的文本块，再通过 RRF 融合候选。Cross-Encoder 虽然能更细致地比较问题与文本内容，但需要逐对进行模型计算，成本更高，如果与知识库中的所有文本块逐一比较，会消耗大量计算资源和时间。因此，只对前面筛选出的有限候选进行精排，**在计算成本、执行效率和排序质量之间取得平衡。**

**两个阶段的作用不同，也相互影响。** 召回阶段需要尽量找回相关资料，为后续精排提供足够好的候选；精排则从已有候选中筛选更相关的内容，无法找回前面遗漏的资料。因此，还需要关注召回阶段的 **Recall@K** 等指标，评估相关资料是否进入候选集，为后续精排提供基础。

### 5. 将最终筛选的文本块整理成模型输入的上下文，生成回答后校验引用

系统将筛选后的文本块正文、来源信息和引用标识整理成上下文，并根据长度预算控制输入长度。模型根据这些资料生成回答，并被要求在相关结论后标注引用，以便追溯到对应的资料来源。

**生成回答后，系统按约定格式提取引用编号，主要检查回答是否使用了本轮提供的有效引用、是否出现未知编号。** 发现异常时，记录问题并给出重新生成等处理建议；没有检索资料时，还会检查回答是否说明资料不足。

这里的“缺少引用”指回答整体没有使用有效引用，当前检查不能逐条判断哪些结论应当引用却没有引用，也没有独立、完整的引用格式校验。**引用编号有效，只说明能找到对应资料，不能证明资料确实支持该结论。**

另外，在开发评测阶段，可以进一步检查**回答的事实正确性、依据支持性和回答相关性**，从而评价生成质量，并根据评测结果调整检索和生成策略。

### LangChain Runnable 怎样组织上述处理

**LangChain Runnable 提供统一的步骤调用与组合方式，用来衔接检索链路中的处理步骤及其结果传递。**

检索器或自定义处理函数可以封装成 Runnable，再按照输入输出关系组合。具体怎样编码、检索、融合和重排，仍由相应组件或处理函数完成。

### 这条工作说明了什么

这条简历能够说明，项目实现了从**检索资料、筛选排序到生成回答和检查引用**的完整处理链路。两路检索着重减少资料遗漏，融合与重排着重改善候选选择，来源信息与引用检查支持回答追溯。

当前条目没有提供量化评测结果，因此可以说明这些已实现能力；实际准确率提高多少、各环节贡献多大，需要对照评测才能确定。

## 第二阶段：面试问答

Q01 借用 STAR 提示整条工作的主线，四段分别对应场景、任务、行动和结果；R 说明已实现能力。其余题按照各自的机制、选择理由或评测逻辑组织，每题的“回答顺序”用于记忆，口述时不必念出。

Q07、Q08 使用“可以怎样评测”的方法口径，不表示已经完成相应对照实验，也不据此补充量化提升。

```text
Q01. 介绍一下你在 DeepAssist 中做的混合检索。

回答顺序：S 场景 → T 我的任务与目标 → A 关键做法 → R 已实现能力

答：这部分主要服务于知识库问答。用户的提问与文档可能意思接近、表达不同，也可能包含需要准确匹配的专业术语，因此需要结合语义检索和关键词检索的优势。

我负责把资料检索、候选筛选、上下文整理和引用检查衔接起来，尽量找到相关资料、减少遗漏，再筛选适合回答问题的内容，并保留资料来源。

实现上，用 LangChain Runnable 组织检索链路，用 BGE-M3 编码，结合 Chroma 向量检索和 Elasticsearch 关键词检索。两路结果先经过 RRF 融合，再用 Cross-Encoder 重排；选中的文本块连同来源和引用编号，按长度预算整理成上下文，交给模型生成回答，之后检查引用编号是否有效。

最终实现了从资料检索、候选筛选到回答生成和引用检查的完整链路。回答中的有效引用能够追溯到本轮提供的文本块和来源，系统也能发现回答整体缺少有效引用、使用未知引用编号等问题。


Q02. LangChain Runnable 在这条链路中起什么作用？

回答顺序：作用 → 怎样衔接步骤 → 职责边界

答：Runnable 提供统一的调用和组合方式，用来衔接检索链路中的处理步骤与结果传递。

检索器或自定义处理函数可以封装成 Runnable，再按照输入输出关系组合，让前一步的结果交给后一步处理。

具体怎样编码、检索、融合和重排，仍由相应组件或处理函数完成；Runnable 负责把这些处理衔接起来。


Q03. 文档入库和用户查询时，向量检索与关键词检索分别怎样处理？

回答顺序：入库准备 → 查询处理 → 两路输出与互补作用

答：两路都需要先在入库时建立索引，查询时再利用索引找出候选文本块。

入库时，先把文档拆成文本块，保留正文、唯一标识和来源信息，同一文本块在两路使用相同的 ID。向量这一路，用 BGE-M3 将正文编码为向量，由 Chroma 保存向量及关联的文本信息，并建立向量索引。关键词这一路，将正文和相关信息写入 Elasticsearch，通过文本分析得到词项，建立从词项到文本块的倒排索引。

查询时，用同一个 BGE-M3 模型将问题编码为查询向量，由 Chroma 查找向量相近的文本块；同时，将查询文本交给 Elasticsearch，经过文本分析后利用倒排索引匹配并排序。

前者侧重意思接近、表达可能不同的内容，后者补充对专业术语、名称等具体表达的匹配。两路分别返回排好序的候选文本块，供后续融合。


Q04. RRF 怎样融合两路结果？为什么不直接把原始分数相加？

回答顺序：原始分数的问题 → 排名贡献 → 按 ID 合并累加 → 统一排序

答：两路原始分数的计算方式和取值范围不同，缺乏直接可比性，所以采用 RRF，根据各自的排名计算贡献，再合并排序。

具体来说，文本块在某一路排名越靠前，该路贡献就越大。根据文本块 ID 合并候选后，同一文本块被两路找到，就累加两路贡献；只被一路找到，就保留该路贡献，最后按融合分数统一排序。

采用加权 RRF 时，还可以给两路设置不同权重，调整它们对融合结果的影响。


Q05. 已经经过 RRF 排序，为什么还要用 Cross-Encoder 重排？

回答顺序：两者区别 → 重排计算 → 有限候选与成本 → 能力边界

答：RRF 根据两路已有排名整合结果，Cross-Encoder 则直接结合问题和候选正文，进一步判断相关性。

它把“问题和一个候选文本块”一起输入模型，计算相关性分数，再据此重新排序，选出靠前的内容供回答使用。

这里采用先召回、后精排的两阶段方案。文档文本块的向量编码和索引构建在入库时完成，查询时仍需编码问题，但可以利用已有索引较快地找到候选。Cross-Encoder 需要对问题与候选逐对进行模型计算，成本更高，因此只处理数量有限的候选，以平衡计算成本、执行效率和排序质量。

精排只能在已有候选中重新排序和筛选，无法找回召回阶段遗漏的资料，所以前面的召回质量仍然很重要。


Q06. 生成回答后，引用对应关系具体怎样校验？能保证回答正确吗？

回答顺序：检查范围 → 建立对应关系 → 提取并核对 → 检查边界

答：当前主要检查回答是否使用了本轮资料中的有效引用、是否出现未知引用编号，不能据此保证回答正确。

生成前，系统为实际送入模型的文本块分配引用编号，并保留编号与文本块、来源信息的对应关系。生成后，按约定格式提取回答中的引用编号，再与本轮可用编号核对。

如果提供了资料，但回答没有使用任何有效引用，或者出现本轮不存在的编号，就记录问题，并给出重新生成等处理建议。没有检索资料时，还会检查回答是否说明资料不足。

这里能识别的是回答整体缺少有效引用，不能逐条判断哪些结论应该引用却没有引用。引用编号有效，也只说明能找到对应资料；资料是否真正支持该结论，还需要进一步判断。


Q07. 怎样验证混合检索和重排是否有效？

回答顺序：测试数据与同 K 对照 → 召回指标 → 固定候选评估重排 → 耗时与结论

答：可以用固定的测试问题和相关文本块标注，分别比较召回结果与重排结果，并同时记录耗时。

评估召回时，在相同知识库、测试问题和最终候选数 K 下，分别比较向量单路、关键词单路和两路融合后的 Recall@K。它表示前 K 个候选中找回的相关文本块，占该问题全部标注相关文本块的比例，用来判断相关资料是否遗漏。

单独评估重排时，应固定同一批输入候选，再比较重排前后的 nDCG@K，判断相关资料是否排到更靠前的位置。

同时记录各方案耗时，判断召回和排序的改善是否值得新增的计算成本。这样可以分别判断两路融合对召回的影响，以及重排对候选排序的影响。


Q08. 除了引用编号检查，最终回答还应该评测哪些方面？

回答顺序：三个方面 → 分别衡量什么 → 区别示例 → 评价办法

答：可以重点看事实正确性、依据支持性和回答相关性。

事实正确性，看回答是否符合可信参考答案或已核实的事实；依据支持性，看回答中的结论能否得到提供给模型的资料支持；回答相关性，看回答是否回应了用户的问题，有没有明显偏题或无关内容。

这三项需要分开判断。例如，回答忠实复述了错误资料，可能有依据支持，但事实仍然不正确。

开发评测时，可以结合参考答案、检索资料和用户问题进行人工核查，也可以用模型辅助评价，再通过人工抽查确认评分是否可靠。
```

### 当前实现边界

- [加权 RRF 实现](../../项目源码/DeepAssist/backend/domain/services/rag/fusion.py)：按文本块 ID 合并候选，累加各路基于排名与权重计算的贡献。

- [引用检查实现](../../项目源码/DeepAssist/backend/domain/services/rag/answer_guard.py)：按约定格式提取引用编号，检查是否使用本轮引用、是否出现未知编号，并在没有资料时检查资料不足提示；检查结果提供处理建议，不能据此声称已自动修复引用或证明结论有依据。
