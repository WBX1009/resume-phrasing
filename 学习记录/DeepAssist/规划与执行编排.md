# DeepAssist｜规划与执行编排

## 前置学习知识

### 1. LangGraph 中，图、节点、状态和边分别是什么

LangGraph 用图描述处理流程，再按照这张图运行程序。开发者需要定义每一步做什么、哪些数据需要传递，以及怎样决定下一步。

| 核心概念 | 通用解释 |
|---|---|
| **`StateGraph` 图构建器** | 用来定义工作流。先指定 State 的结构，再添加节点和连接关系，最后通过 `compile()` 得到可以运行的图。 |
| **State Schema（状态结构定义）** | 约定 State 包含哪些字段及其类型，例如目标、计划、任务结果和检查反馈。 |
| **State（工作流状态）** | 保存当前流程需要使用和传递的数据，例如任务计划、各子任务的执行状态与结果。 |
| **节点（Node）** | 承担一个处理步骤的函数或对象方法。读取状态，执行处理，再返回需要更新的数据；内部可以调用模型、工具或子图。 |
| **普通边（Normal Edge）** | 定义固定的后续连接关系。例如 `A → B`，表示 A 完成后进入 B。 |
| **条件边（Conditional Edge）** | 接入路由函数，根据当前状态选择后续节点，也可以决定结束。条件路由就是这个判断和选择过程。 |
| **Reducer（状态合并函数）** | 规定某个字段收到更新后，怎样与原值合并，例如替换原值、追加消息或汇集任务结果。 |
| **`START`、`END`** | 表示当前图的入口和结束位置，本身不承担业务处理。 |

普通边也可以连接多个后续节点；条件路由也可以返回多个目标。因此，区别在于**连接是否预先固定，还是需要运行时判断**，不能简单理解成“普通边只能串行，条件边才能并发”。路由函数需要由开发者定义；如果让模型参与判断，也需要将模型输出接入路由逻辑。[^graph-api]

**State 和任务状态不是同一个概念。** State 是工作流使用的数据结构；“待执行、执行中、已完成”等任务状态，只是其中的一部分信息。某个子任务已完成时，整体任务仍可能处于执行或检查阶段。

节点与 State 的关系，可以通过下面这个片段理解。它演示的是节点函数内部的返回语句，不是可独立运行的完整程序：

```python
# 检查节点返回需要更新的字段
return {"feedback": "缺少复利公式及其来源"}
```

框架将这个更新合并到 State，后续重规划节点就能读取 `feedback`。节点通常不必返回整份 State；没有更新的字段继续保留。多个并发任务需要写入同一个结果字段时，应为该字段设计合适的 Reducer。

**Reducer 是框架应用状态更新时使用的合并规则，不必另外创建一个“Reducer 节点”。**[^use-graph-api]

### 2. 子任务和图节点不是同一个概念

**子任务说明要完成什么，图节点说明用哪段处理逻辑完成工作。**

例如，“读取方案 A”和“读取方案 B”是两个子任务，但可以复用同一个“执行子任务”节点，只是传入的任务目标和文件不同。

因此，任务计划从三项变成五项，不意味着必须重新编写五个节点。常见做法是保留已有图结构，更新 State 中的任务计划，再多次调用相应执行节点。

### 3. 外层主图与内层子图怎样配合

子图也是一张可以运行的图，只是被另一张图调用，用来组织某个步骤内部的处理过程。

| 层次 | 主要保存什么 | 主要负责什么 |
|---|---|---|
| **外层主图** | 整体目标、任务计划、各任务状态与结果、检查反馈 | 规划、安排、检查和汇总整体任务 |
| **内层子图** | 当前子任务目标、相关输入、模型消息、工具反馈 | 完成当前子任务内部的具体操作 |

如果两层使用不同的 State 结构，可以在外层执行节点中准备子图输入，调用子图，再把子图结果转换成外层需要的更新。两层具有共同字段时，也可以把编译后的子图直接接入主图节点。

**内层到达自己的 `END`，表示本次子任务执行结束，结果返回外层，不代表整体任务结束。**[^subgraphs]

### 4. State、运行时和检查点分别解决什么问题

**运行时（runtime，指图执行引擎）负责实际执行工作流，按照图的连接关系和路由结果安排节点运行，接收节点返回的更新，并推进后续执行。** LangGraph 的这部分执行机制由 Pregel 实现。[^pregel]

这些概念可以按下面的关系理解：

| 概念 | 作用 |
|---|---|
| `StateGraph` | 定义图的节点、连接关系和状态结构 |
| `compile()` | 将图定义编译成可执行的图 |
| 图执行引擎 | 在调用 `invoke()`、`ainvoke()` 等运行接口后，组织实际执行 |
| State | 保存流程需要使用和传递的数据 |
| Checkpointer | 保存和读取执行检查点，支持后续恢复 |

这里说的图执行引擎，与节点参数中可能出现的 **`langgraph.runtime.Runtime` 对象**要区分：后者供节点访问运行上下文、Store 等信息，不是另一个需要开发者启动的调度引擎。[^runtime-context]

检查点保存执行过程中的状态快照及继续执行所需的信息。需要在进程重启后恢复，还要使用持久化存储。**State 的存在本身不等于数据已经持久化。**[^persistence]

还要区分：**重规划是在正常运行中，根据反馈改变后续任务；中断恢复是在流程停止后，从保存的进度继续执行。**

## 简历条目

> **规划与执行编排：**基于 LangGraph 构建双层流程：外层借鉴 **Plan-and-Solve** 规划任务，以 **Reflection** 检查结果，针对缺口重规划；内层通过 **ReAct** 根据工具反馈推进执行。

## 第一阶段：本条理解

> **确认状态：已确认。** 本条前置知识与两阶段内容按用户已确认的通用实现方案整理。

**这条工作的核心是：将整体任务的规划与子任务的具体执行分开。外层负责拆分和安排子任务、检查执行结果，并在需要时补充或调整计划；内层 ReAct 围绕当前子任务的目标，通过模型推理和工具调用完成具体工作。**

DeepAssist 面向知识库问答和多步工具调用。一个请求可能需要读取文件、检索资料、执行计算，最后汇总回答。这类任务既需要明确各项工作及其依赖关系，也需要根据执行中取得的信息决定下一步操作。

### 1. 外层先规划，明确需要完成哪些子任务

外层借鉴 Plan-and-Solve 的思路，先将整体目标拆成较小的子任务，再按照计划完成。这里借鉴的是“先规划、再执行”，重规划和工具调用等工程机制需要另外组织。[^plan-and-solve]

一个可执行的计划，需要说明各项任务要完成什么、需要哪些输入，以及预期取得什么结果。后端据此检查执行条件：输入已经准备好的任务可以执行，依赖上游结果的任务需要等待。

例如，计算投资到期金额，需要先取得投资参数和适用公式。**规划负责明确这些工作及其关系，执行时再检查所需输入是否已经取得且符合要求。**

### 2. 内层通过 ReAct，根据工具反馈推进当前子任务

需要根据执行反馈动态选择后续工具操作的子任务，可以交给内层 ReAct 子图处理。

**ReAct 的核心是让模型交替进行推理与行动，并根据行动反馈决定下一步操作。** 在工具调用场景中，模型负责提出操作，后端实际执行工具，再把结果提供给模型。[^react]

具体过程是：

1. 模型根据当前子任务的目标和已有信息，判断下一步需要做什么；需要调用工具时，确定工具及参数。
2. 后端校验工具调用，执行工具，并将结果加入后续模型输入。
3. 模型根据工具反馈继续推理，决定继续调用工具，还是在满足当前子任务的完成条件后返回结果。

这里用**“满足完成条件”**比“信息足够”更通用：查询任务可能要求信息齐全，计算任务要求得到有效计算结果，文件操作任务则需要确认操作确实完成。

如果无法继续完成，或者达到执行限制，内层也应返回已有结果和未解决的问题，交给外层处理。

因此，内层的职责可以表述为：

> **内层围绕当前子任务的目标，通过推理和工具调用完成具体工作，并根据工具反馈决定下一步操作。**

不必每次都改变原来的操作安排。反馈符合预期时，正常推进即可。

### 3. 外层检查执行结果，再针对缺口补充或调整计划

Reflection 在这里指：**对照任务目标和完成要求检查结果，找出尚未解决的问题，并形成能够指导后续执行的反馈。**

检查环节可以结合规则校验和模型评估：

- **规则适合检查明确条件：**必填参数是否齐全、数值单位是否一致、工具是否执行成功。
- **模型适合参与内容判断：**结果是否回答了任务要求、公式是否适用、所引用资料能否支持相关说明。

检查结果需要指出具体问题，例如“缺少计息频率，无法确定适用公式”，而不只是笼统地给出“不通过”。模型评估也可能出错，有明确校验方法的内容应尽量采用可验证的检查。

发现缺口后，外层根据反馈补充或调整计划，再执行相关任务并重新检查。这对应评估、反馈、改进的循环。[^effective-agents]

正常情况下，保留已经完成且仍然有效的结果；如果补充信息改变了原先依据，还需要重新检查受影响的下游结果。例如，后来确认计息方式不同，原计算结果也需要重算。

检查可以放在关键子任务完成后，也可以检查最终汇总结果。**下游缺少必要输入时，应先处理这个缺口，再继续执行。**

例如：

> **计算理财收益时，如果内层在允许的尝试范围内仍未检索到适用公式，就将缺口返回外层。外层安排补充检索，取得并确认公式后，再继续计算。**

如果只是原查询再次执行一次，更接近重试；根据反馈改变检索范围、补充新的查找任务，才更能体现计划调整。重规划、补充执行及其中产生的模型和工具调用，都需要受到整体预算和相应次数限制。

### 4. LangGraph 通过哪些原生机制组织这套双层流程

三个参考范式与官方工作流模式，可以这样对应：

| 参考范式 | 对应的官方工作流模式 | 在这套方案中的作用 |
|---|---|---|
| **Plan-and-Solve：先规划，再执行** | **Orchestrator-Worker（编排器—执行者）** | 组织子任务的分配、执行和结果汇总 |
| **Reflection：检查结果、形成反馈** | **Evaluator-Optimizer（评估—优化）** | 组织评估、反馈、改进和再次评估的循环 |
| **ReAct：推理、行动与反馈交替** | **Agent 工具调用循环** | 根据工具反馈决定下一次操作或返回子任务结果 |

这些是**思路与实现模式之间的对应关系，不是完全等价的概念，也不是三个开箱即用的完整组件。**[^workflows-agents]

#### Orchestrator-Worker：怎样持续执行动态任务计划

> **外层借鉴 Plan-and-Solve 的先规划、再执行思路，通过 Orchestrator-Worker 模式组织子任务的分配、执行和结果汇总。**

在这套方案中，可以按批次组织任务执行：

规划节点将子任务计划保存到 State。执行时，后端根据任务所需输入和已有结果，选出当前可以执行的任务，再通过条件路由和 `Send` 分配给 Worker。不同任务可以复用同一执行节点或子图，各自接收任务输入。

本批执行结果通过 Reducer 汇集到 State，后端据此继续安排剩余任务；本轮任务均已结束，或已没有正在执行的任务但仍存在阻碍后续执行的缺口时，再进入检查与重规划环节。

**“当前没有可执行任务”需要结合任务记录判断：**任务可能已经完成，也可能因为缺少输入而无法继续；如果还有任务正在执行，则需要等待其结果。

这里的持续分发和依赖检查，是开发者利用 LangGraph 机制设计的执行策略。`Send` 负责分发任务，不会自动理解业务依赖。

下面用一个简短片段说明条件路由怎样返回 `Send`。假设 `Dispatch` 节点已经完成执行条件检查，并将本批任务的输入保存为 `ready_inputs`：

```python
from langgraph.types import Send

def route_dispatch(state):
    if state["ready_inputs"]:
        return [
            Send("worker", task_input)
            for task_input in state["ready_inputs"]
        ]

    return "reflect"

builder.add_conditional_edges("dispatch", route_dispatch)
```

这是路由示意片段，不是完整程序。它采用“等待本批任务结果汇集后，再次分发”的组织方式，因此进入这次判断时，没有上一批仍在运行的 Worker。

`Send("worker", task_input)` 表示：**使用这份任务输入，运行一次已经定义好的 `worker` 节点。** 动态变化的是任务数量和输入，通常不需要因此重新构建整张图。[^use-graph-api]

外层可以根据子任务类型选择相应执行方式：**需要根据反馈动态选择工具操作的任务，可以交给 ReAct 子图；固定流程的任务，则可以直接调用相应处理节点或链路。** 例如，参数和公式已经确定的计算，可以直接调用计算函数。

#### Evaluator-Optimizer：怎样把检查反馈变成下一轮改进

> **外层借鉴 Reflection 检查任务结果，通过 Evaluator-Optimizer 模式组织评估与反馈循环，发现缺口时补充或调整计划，再执行相关任务并重新检查。**

Evaluator 负责根据要求评估结果，输出判断和具体反馈；Optimizer 使用反馈修改已有产物或执行方案，然后再次提交检查。

放到你的双层方案中，可以具体化为：

- `Reflect` 节点读取目标、结果和依据，生成检查反馈。
- 条件路由根据反馈和执行限制，决定正常推进、进入 `Replan`，或停止。
- `Replan` 节点补充或调整 State 中的计划。
- 执行节点完成相关任务，再交给检查节点评估。

**这里的“优化”是根据反馈改进任务结果，不是训练模型或更新模型参数。** 将改进过程具体化为“调整计划并补充执行”，是本方案对该模式的应用，不代表框架自动提供了重规划算法。[^effective-agents]

重规划通常只需要更新 State 中的计划和执行记录，继续复用已有的规划、执行和检查节点。

#### Agent 工具调用循环：怎样实现内层 ReAct

> **内层借鉴 ReAct 的推理与行动交替机制，通过模型节点、工具节点和条件路由构成循环，根据工具反馈决定继续执行还是返回子任务结果。**

内层可以这样组织：

- 模型节点读取子任务目标、已有消息和工具反馈，返回工具调用请求或子任务结果。
- 条件路由检查模型输出：存在工具调用请求时进入工具节点，否则进入结果返回步骤。
- 工具节点执行调用，将反馈写入消息状态，再回到模型节点。

这种运行结构不要求把完整推理过程显式输出给用户。理解时，重点关注**模型决策、工具执行和反馈返回模型之间的联系**。

LangGraph 官方快速入门展示了这种模型与工具交替运行的结构。**“模型不再请求工具”是常见的循环结束信号，但不等于已经通过任务质量检查；返回结果仍可由外层核验。**[^quickstart]

工具执行部分可以复用 `ToolNode`；需要标准 Agent 循环时，也可以使用 LangChain 的 `create_agent` 封装，再接入外层工作流。具体工具、任务指令、权限和预算规则仍需配置。[^tools][^agents]

**开发者实现任务规划、结果检查和重规划等具体策略；LangGraph 通过节点、状态更新、普通边、条件路由和子图组织执行，并提供动态任务分发、循环和检查点等通用机制。**

### 5. 用一个完整的复利计算示例，把两层流程连接起来

假设用户提出：

> 根据我上传的理财方案，计算到期后的本息合计，并说明参数和公式依据。

这是用于理解流程的假设示例。假设方案约定本金 10 万元、固定年利率 5%、期限 2 年、按年复利，期间没有追加或提取资金，计算中不考虑费用和税费。

**外层先安排任务及其依赖：**

| 子任务 | 要取得的结果 | 执行条件 |
|---|---|---|
| T1：读取理财方案 | 本金、利率、期限、计息方式及文件依据 | 能访问用户指定文件 |
| T2：检索适用公式 | 公式、适用条件及来源 | 已明确方案的计息方式 |
| T3：执行计算 | 本息合计与收益 | 投资参数和适用公式均已取得并检查 |
| 汇总回答 | 金额、计算过程、参数与公式依据 | 必要结果齐备且检查通过 |

这里按照用户要求，将取得公式依据作为计算前置条件。

**内层执行 T1 时，根据文件返回内容决定后续操作：**

第一次读取方案摘要，得到本金、利率和期限，但没有计息方式。模型发现参数尚不齐全，于是继续读取文件中的计息说明。取得“每年计息一次，利息并入本金”后，返回完整参数及对应来源。

这说明：**外层给定“取得投资参数”这个子任务，内层根据读取反馈决定还需要查看哪部分内容。**

随后，T2 检索并确认按年复利公式：

$$
FV=PV(1+r)^n
$$

T3 使用参数和公式调用计算工具：

$$
FV=100000\times(1+0.05)^2=110250
$$

得到本息合计 **110,250 元**，收益 **10,250 元**。这一步的参数和计算方式已经确定，可以直接执行计算，不必再组织一轮 ReAct 决策。

外层检查参数是否与文件一致、公式是否匹配按年复利、计算中的单位和期数是否正确，以及回答是否包含所需依据；检查通过后汇总回答。

**如果 T2 没有取得适用公式，流程怎样变化：**

采用 ReAct 执行 T2 时，内层可以先在当前子任务范围内调整检索词；仍无法取得结果时，返回“缺少公式依据”的反馈。外层保持 T3 等待，根据反馈补充查找任务或调整资料范围。取得适用公式并检查后，再执行 T3。

如果最终仍无法补齐，就说明缺少的依据和未完成部分，不在缺少必要前提时先输出计算结果。

这套通用方案所支持的能力，可以表述为：

> **系统能够先规划并组织多步任务，对需要动态工具交互的子任务，根据工具反馈推进执行；外层对照目标检查结果，发现信息缺失、依据不足或结果不符合要求时，在执行限制内补充或调整计划，并重新检查相关结果。**

## 第二阶段：面试问答

以下按已确认的通用实现方案组织。Q01 借用 STAR 提示主线，R 说明方案能力；其余题按各自考察点安排回答顺序。回答顺序用于记忆，不必在口述时念出。

```text
Q01. 介绍一下 DeepAssist 的规划与执行编排方案。

回答顺序：S 场景 → T 我的任务 → A 双层设计 → R 方案能力

答：DeepAssist 面向知识库问答和多步工具调用，一个请求可能需要读取文件、检索资料、执行计算，再汇总回答。

我负责设计这部分编排流程，安排各项工作的依赖关系，并根据执行反馈处理缺口。

设计上采用双层流程：外层借鉴 Plan-and-Solve，先拆分和安排子任务，再通过 Reflection 检查结果，必要时补充或调整计划；需要动态选择工具操作的子任务，则交给内层 ReAct，根据工具反馈推进执行。两层通过 LangGraph 的节点、状态和条件路由连接起来。

这套方案让任务既能按计划推进，也能在信息缺失、依据不足或结果不符合要求时，在执行限制内补充处理。


Q02. Plan-and-Solve、Reflection、ReAct，与 LangGraph 官方工作流模式是什么关系？

回答顺序：总体关系 → 三组对应 → 开发者职责

答：它们是参考思路与工作流模式的对应关系，不是完全等价的概念，也不是三个开箱即用的完整组件。

外层借鉴 Plan-and-Solve 的先规划、再执行思路，通过 Orchestrator-Worker 模式组织子任务的分配、执行和结果汇总。

Reflection 用来检查结果、形成反馈；Evaluator-Optimizer 组织评估、反馈、改进和再次评估的循环。本方案把改进过程具体化为补充或调整计划，再执行相关任务。

内层借鉴 ReAct，通过模型节点、工具节点和条件路由构成循环，根据工具反馈决定下一步操作。

这些模式说明流程怎样组织，具体怎样规划、检查和调整任务，仍需要开发者实现。


Q03. 怎样把双层流程组织成 LangGraph 工作流？

回答顺序：定义状态 → 编写节点与连边 → 接入子图 → 编译运行

答：先定义 State，保存整体目标、任务计划、各任务的执行状态与结果，以及检查反馈。

再把规划、执行、检查和重规划写成节点函数，用 StateGraph 注册节点，通过普通边连接固定步骤，通过条件路由根据当前状态选择下一步。节点返回需要更新的数据，由框架合并到 State。

需要 ReAct 的任务，可以在外层执行节点中调用内层子图：先准备子图输入，等待执行结束，再把结果转换成外层需要的状态更新。子图结束后，外层继续运行。

图定义完成后，通过 compile() 得到可执行的图，再调用 invoke() 或 ainvoke() 启动。具体策略和执行规则由开发者实现，节点运行、状态更新和流程流转由 LangGraph 组织。


Q04. 任务数量和计划会变化，外层怎样持续安排执行？

回答顺序：计划入状态 → 检查并分发 → 汇集并继续 → 判断完成或缺口

答：把任务计划和执行记录保存在 State 中，通过分发、执行和结果汇集的循环推进任务，通常不必随任务数量变化重新构建图。

以按批次执行为例，分发节点根据任务所需输入、已有结果和执行记录，选出当前可以执行的任务，再由条件路由返回 Send，把各项任务的输入交给执行节点。不同任务可以复用同一个节点或子图。

本批结果通过 Reducer，也就是状态合并函数，汇集到 State 后，分发节点再检查剩余任务，安排下一批执行。

本轮任务均已结束，或剩余任务因缺少输入、依赖无法满足而不能继续时，再进入检查环节。因此，没有可执行任务不一定代表全部完成。Send 负责分发，执行条件仍由后端检查。


Q05. 内层 ReAct 怎样运行？所有子任务都需要使用它吗？

回答顺序：适用任务 → 模型决策 → 工具执行与反馈 → 返回与检查

答：不需要。需要根据工具反馈动态选择后续操作的任务，适合使用 ReAct；参数和步骤已经确定的计算或检索，可以直接调用相应函数或固定链路。

ReAct 执行时，模型根据当前子任务目标和已有信息，提出工具及参数；后端校验并执行，将结果加入后续模型输入；模型再根据反馈决定继续调用工具，还是返回子任务结果。

满足完成条件时返回结果；无法继续完成或达到限制时，返回已有结果和未解决的问题。

模型不再请求工具，只是常见的循环结束信号，不代表结果已经通过质量检查，外层仍可继续核验。


Q06. Reflection 怎样发现缺口，并推动重规划？

回答顺序：对照要求 → 形成反馈 → 调整并执行 → 重新检查

答：检查节点对照任务目标和完成要求，读取执行结果及其依据。参数是否齐全、单位是否一致等明确条件，可以通过规则校验；内容是否符合要求、依据是否充分，可以结合模型评估。

反馈需要说明缺少什么、影响哪项任务。例如，“缺少计息频率，无法确定适用公式”，就能指导后续补充读取。

外层据此补充或调整计划，再执行相关任务并重新检查。已经完成且仍然有效的结果继续保留；如果新信息改变了原先依据，就重新处理受影响的下游任务。

原操作再次执行，更接近重试；根据反馈改变查找范围、增加任务或修改执行安排，才体现了重规划。


Q07. 怎样避免工具循环和重规划反复执行？

回答顺序：限制什么 → 何时检查 → 到限怎样处理 → 区分成功与停止

答：后端需要同时限制整体用量和局部尝试。

整体任务设置模型调用次数、工具调用次数和 Token 预算上限，重试、补充执行和重规划产生的消耗也计入其中。局部则限制单个 ReAct 的循环次数，以及重试和重规划次数。

后端累计用量，并在继续调用或进入下一轮前检查剩余预算。局部尝试达到上限时，返回已有结果和未解决的问题，由外层在剩余整体预算内决定后续处理；整体预算用尽时，停止发起相应调用并说明未完成部分。

完成条件和停止条件需要分别判断，不能把“达到限制而结束”记录成“任务成功完成”。


Q08. 能用一个例子说明外层规划、内层执行和结果检查怎样配合吗？

回答顺序：用户要求 → 任务依赖 → 执行反馈 → 检查与输出 → 缺口分支

答：以“根据上传的理财方案计算到期本息，并说明依据”为例，这是一个假设任务。

外层安排读取投资参数、检索适用公式、执行计算和汇总回答，计算需要等待参数和公式齐备。读取文件时，内层第一次取得本金、利率和期限，但缺少计息方式，就继续读取计息说明，体现根据工具反馈决定下一步操作。

假设确认本金 10 万元、年利率 5%、期限 2 年、按年复利，期间没有追加或提取资金，也不计费用税费。取得适用公式后，调用计算工具，再由外层核对参数、公式、计算过程和来源。检查通过后，输出本息合计 110,250 元及相应计算过程和依据。

如果公式检索仍有缺口，内层返回未解决的问题，外层让计算任务等待，并安排补充查找。取得并确认公式后再计算；最终仍无法补齐，就说明缺少的依据和未完成部分。
```
