# DeepAssist｜架构设计与组件解耦

## 简历条目

> **架构设计与组件解耦：**按 **Clean Architecture** 分层，以 **Port/Adapter** 落实依赖倒置，隔离业务逻辑与模型、检索、存储及 Runtime 的具体实现，便于组件替换、扩展与独立测试。

## 第一阶段：本条理解

**这项设计的核心是：让应用层按照领域层声明的端口使用外部组件，由适配器处理不同组件在调用方式和数据格式上的差异。** 这样更换组件时，尽量不需要修改应用层原有的处理逻辑，也方便单独测试应用层。

DeepAssist 需要调用模型、检索知识库、保存状态，还要执行 Agent 任务。不同组件有各自的调用方法、参数要求和返回数据格式。如果应用层直接处理这些差异，更换组件时就可能需要修改多处应用层代码；而单独测试应用层的处理逻辑时，也容易依赖真实模型、数据库或执行框架，增加测试的复杂度。

Clean Architecture 用来划分职责，在本项目中，各层可以这样理解：

| 层次 | 主要职责 |
| --- | --- |
| 接口层 | 接收并校验外部请求，调用应用层提供的业务功能，将结果返回给客户端。 |
| 应用层 | 组织一次问答或 Agent 任务的处理流程，按需要协调上下文准备、记忆读写、知识检索和 Agent 执行等环节。 |
| 领域层 | 定义相对稳定的核心业务对象、业务规则与处理策略，以及应用层使用相关组件时依赖的端口。 |
| 基础设施层 | 通过适配器接入具体模型、检索组件、数据库和执行框架，处理调用方式和数据格式的差异。 |

领域层的内容可以归纳为三类：**业务对象、业务规则与处理策略、端口声明**。“相对稳定”指它们尽量不受具体模型、数据库或执行框架变化的影响，仍然可以随业务需求调整。

这张表描述的是各层的职责划分，而不是固定的调用顺序。一次请求进入后，FastAPI 根据请求路径和 HTTP 方法找到对应的路由函数；路由函数接收经过解析和校验的请求参数，调用应用层对象的方法。

应用层根据任务需要，使用领域层定义的业务对象、规则与策略组织处理流程；需要调用模型、数据库或执行框架等组件时，则按照领域层声明的端口调用相应的适配器，由适配器完成具体组件的调用和必要的数据转换。

**端口只负责声明调用约定，本身不执行具体操作。运行时，应用层按照端口约定，调用实际传入的适配器对象。**

为统一术语，后文使用：

- **应用层**：负责组织问答或 Agent 任务处理流程的代码。
- **端口（Port）**：定义应用层使用某类组件时需要的操作、输入输出及必要的行为约定。
- **适配器（Adapter）**：基础设施层中按照端口约定接入具体组件，处理调用方式和数据格式差异的实现。

本项目在领域层通过程序接口声明端口，规定调用方法、输入输出及必要的行为要求，例如怎样表示任务完成或失败。适配器负责实现这些方法；内部怎样调用模型 SDK、数据库驱动或执行框架，由适配器处理。**本节所说的适配器是基础设施层的一部分，不再另设“适配器层”。**

以 Runtime（负责推进 Agent 任务执行的机制）为例，项目使用 Python 的 `Protocol` 声明端口：

```python
class AgentRuntimePort(Protocol):
    def stream_run(
        self,
        request: AgentRuntimeRequest,
    ) -> Iterator[StreamEvent]:
        ...
```

这段代码要求适配器提供 `stream_run` 实例方法，接收 `AgentRuntimeRequest`，并通过迭代器逐条返回 `StreamEvent`。自定义 Runtime 和 LangGraph 的适配器都按照这项约定实现，因此应用层可以使用相同的方法调用它们、读取执行事件。模型、存储等其他类型的组件使用各自的端口。

`Protocol` 主要用于声明方法要求，配合类型检查工具使用；具体执行逻辑由适配器实现。统一的事件数据类型不代表两种 Runtime 的所有行为完全相同，实际产生的事件、完成和失败时的状态含义，仍需按照业务要求通过测试验证。

如果应用层直接使用具体组件，就需要了解它的调用方法和数据格式，更换组件时可能需要修改应用层代码。

采用 Port/Adapter 后，**应用层依赖领域层声明的端口，基础设施层的适配器也依赖这个端口，并按照约定实现。** 原本由应用层直接依赖具体实现，现在变成由领域层根据业务需要规定调用约定，具体实现反过来适应这项约定，这就是这里的**依赖倒置**。

它遵循的原则是：高层业务代码和具体实现都依赖抽象，抽象不依赖具体实现细节。**依赖倒置是设计原则，Port/Adapter 是落实它的方式，减少应用层与具体组件之间的耦合是达到的效果。** 这里改变的是代码依赖关系，运行时仍由应用层调用适配器对象。

因此，需要先创建适配器对象，再通过构造参数将其传给应用层。创建相关对象并建立它们之间依赖关系的过程称为**装配**；通过构造参数传入应用层所需对象，是**依赖注入**的一种方式。

本项目的对象创建与装配代码主要位于 `backend/api/dependencies.py`。例如：

```python
def get_agent_app() -> AgentApplication:
    return AgentApplication(
        agent_engine=get_agent_engine(),
        session_manager=get_session_manager(),
        context_engine=get_context_engine(),
        profile_extractor=get_profile_extractor(),
        supervisor=get_agent_supervisor(),
        agent_runtime=get_agent_runtime(),
    )
```

其中，`get_agent_runtime()` 根据配置创建自定义 Runtime 或 LangGraph 适配器对象，`get_agent_app()` 将它作为 `agent_runtime` 参数传给 `AgentApplication`。构造函数用 `self.agent_runtime = agent_runtime` 保存对象，处理任务时再调用它的 `stream_run` 方法，读取并处理返回的事件。

这项设计已经具备以下能力：

- **组件切换：**两种 Runtime 共用端口，可以根据配置选择。当新组件满足现有端口约定时，主要调整适配器及其创建代码，应用层原有的调用逻辑可以继续使用。是否扩展端口，取决于应用层是否有现有端口无法满足的调用需求。
- **独立测试：**测试代码编写 `FakeRuntime` 代替真实 Runtime，让它返回事先写好的事件和回答片段，再将这个对象交给应用层，检查应用层怎样处理这些数据。现有测试还通过 `FakeMemoryStore` 在内存中保存消息，核对用户输入和助手回复是否按预期保存。

这项设计的主要代价，是需要维护端口声明、适配器，以及创建和连接对象的代码。适配器内部仍需要处理具体组件的差异，端口声明也不能代替实现验证。

**实现备注（供理解和追问时查阅）：**以上以使用 Runtime 适配器的路径为例。兼容旧执行路径的部分配置会使 `get_agent_runtime()` 返回 `None`，应用层仍保留相应处理。另外，LLM 非流式调用仍返回 SDK 消息对象，应用层也保留了 SSE 辅助类引用和回退分支中的具体适配器创建。当前成果应理解为关键组件已建立端口与适配器的接入方式，各处的隔离程度仍有差异。

```text
Q01. 能介绍一下你在 DeepAssist 中的架构设计与组件解耦工作吗？

答：DeepAssist 需要调用模型、检索知识库、保存状态和执行 Agent 任务。不同组件有各自的调用方法和数据格式，如果应用层直接处理这些差异，更换组件和单独测试应用层都会比较麻烦。

这部分我负责划分各层职责、声明端口并接入适配器，目标是减少组件变化对应用层代码的影响，并支持单独测试。

我按 Clean Architecture 分成接口、应用、领域和基础设施四层。领域层声明应用层需要的端口，基础设施层的适配器负责接入具体组件；创建应用层对象时，再通过构造参数把适配器对象传给它。

项目中的自定义 Runtime 和 LangGraph 已通过同一个端口接入，可以根据配置选择。现有测试也使用假 Runtime 和内存中的假存储，检查应用层的事件处理与会话保存，为替换和独立测试提供了具体依据。


Q02. 一次请求进入后，四层怎样配合？依赖解耦体现在哪里？

答：请求到达后，FastAPI 根据请求路径和 HTTP 方法找到接口层的路由函数。路由函数接收经过解析和校验的参数，调用应用层对象的方法。应用层组织问答或 Agent 任务的处理流程，按需要协调上下文准备、记忆读写、知识检索和 Agent 执行等环节。

应用层根据需要使用领域层定义的业务对象、规则与策略；需要调用相关组件时，则按照领域层声明的端口，调用已经传入的适配器对象。适配器完成具体组件的调用和必要的数据转换，再把结果交给应用层处理。

解耦体现在应用层按照端口使用组件，具体调用差异主要由适配器处理。这四层是职责划分，端口声明本身不执行具体操作，因此请求不需要依次经过表中的四层。


Q03. 什么是依赖倒置？Port/Adapter 怎样落实它？

答：依赖倒置要求高层业务代码与具体实现都依赖抽象，抽象不依赖具体实现细节。

如果应用层直接使用具体组件，就需要依赖它的调用方法和数据格式，更换组件时可能需要修改应用层代码。为减少这种影响，我在领域层声明端口，规定应用层需要的操作及输入输出；应用层按照端口编写调用代码，基础设施层的适配器负责接入具体组件，并满足端口约定。

这样，原来由应用层直接依赖具体实现的关系，变成应用层和适配器都依赖领域层声明的端口。具体实现反过来适应领域层根据业务需要规定的约定，这就是这里的依赖倒置。运行时仍由应用层调用适配器，改变的是代码依赖关系。


Q04. Python 中怎样实现端口、适配器和依赖注入？

答：项目先用 Protocol 声明 AgentRuntimePort，约定 stream_run 方法的参数和返回类型，再由自定义 Runtime 和 LangGraph 的适配器类实现这个方法。

dependencies.py 中的 get_agent_runtime 根据配置创建适配器对象。get_agent_app 创建 AgentApplication 时，通过 agent_runtime 参数把这个对象传进去；构造函数将它保存为 self.agent_runtime，处理任务时再调用它的 stream_run 方法。

这段创建并连接对象的代码负责装配，其中通过构造参数从外部提供对象，属于依赖注入。

路由通过 Depends(get_conversation_app) 声明依赖，由 FastAPI 调用该函数并将返回的对象交给路由参数。前面创建和连接对象的函数都是普通 Python 函数，可以直接调用。


Q05. 更换组件时要修改什么？什么情况下还需要调整端口？

答：先检查新组件能否满足现有端口约定，包括提供的方法、输入输出，以及结果和状态的含义。如果能够满足，主要调整适配器和创建对象的代码，将新适配器传给应用层；已有配置支持选择的，就通过配置切换。接入后，再验证事件、状态和处理结果是否符合预期。

是否扩展端口取决于应用层的需求。新组件自带更多功能，但应用层不需要使用时，原端口可以保持不变。

例如，假设应用层新增了通过 Runtime 端口主动调用 cancel(task_id) 的需求，而原端口只有 stream_run，就需要考虑补充取消方法，由适配器实现，并增加应用层的调用与结果处理。


Q06. 怎样单独测试应用层？项目里有什么具体例子？

答：先写一个代替真实组件的简化程序，让它提供应用层需要调用的方法，并返回测试代码事先指定的数据。创建应用层对象时，把这个替代对象传给它，再输入固定的用户问题，检查应用层的处理结果。

例如，项目测试中的 FakeRuntime 提供 stream_run 方法，依次产生节点事件、固定的回答片段和结束事件；FakeMemoryStore 则把会话消息保存在内存中。测试调用应用层后，通过断言检查预期事件是否返回，以及用户输入和助手回复是否按预期保存。

这条测试检查的是应用层的事件处理和会话保存，无需调用真实模型或读写真实数据库。真实适配器与组件连接后的交互是否正确，再通过集成测试验证。


Q07. 为什么采用这种架构？主要代价是什么？

答：DeepAssist 使用多种模型、检索、存储和执行组件，存在替换、扩展和单独测试应用层的需求。分层明确各部分的职责，Port/Adapter 则让应用层按照端口使用组件，把具体调用方式和数据格式的差异集中在适配器中处理，减少更换组件时需要修改的应用层代码。

代价是需要维护端口声明、适配器，以及创建和连接对象的代码，排查问题时也可能需要跨层追踪。因此，主要在应用层使用这些具体组件的位置建立端口，简单、稳定的内部处理不必每个函数都增加一层抽象。
```
