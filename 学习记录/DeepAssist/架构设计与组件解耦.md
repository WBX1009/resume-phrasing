## 前置学习知识

### 1. 业务对象、业务规则与处理策略

| 概念 | 核心含义 | 直观理解 | 例子 |
| --- | --- | --- | --- |
| 业务对象 | 描述系统需要处理的业务数据及其含义，可以通过数据模型表示其结构。 | 处理的是什么。 | Agent 运行状态记录任务状态、迭代次数和执行结果；消息对象记录角色与正文。 |
| 业务规则 | 规定业务处理需要遵守的条件、判断和约束。 | 什么情况下允许、禁止或必须怎样处理。 | 达到迭代次数上限后，不再继续下一轮 Agent 循环；启用审批时，高风险工具必须先获批再执行。 |
| 处理策略 | 说明为完成某个处理目标采用什么方法。 | 具体采用什么方法解决问题。 | 知识库检索采用向量与关键词双路召回，再经过 RRF 融合和重排，选取相关文档。 |

**业务对象表达业务含义及其数据，Schema（数据结构约定）描述字段类型、枚举取值、必填项、默认值等要求。** 例如，`AgentRunState` 中的 `status` 使用状态枚举（如 `running`、`completed`），`iterations` 是整数且默认值为 0，`final_answer` 保存最终回答。Pydantic（Python 的数据建模与校验库）可以表达和校验这些数据约束；达到次数上限后怎样处理，则需要执行代码落实相应规则。

**规则与策略可以结合使用：规则决定什么情况下允许或需要采取某种处理，策略决定采用什么方法完成处理。应用层则负责组织整体业务流程，协调这些处理环节。** 程序中的条件分支可以用来落实规则，但并不是每一个 `if` 都代表业务规则。

**端口是另一部分内容**，负责定义应用层使用相关组件时需要哪些操作，以及输入输出和必要的行为约定；具体组件的调用由适配器实现。业务对象、规则与策略用于表达和处理系统自身的业务，端口则约定系统怎样使用相关组件。

### 2. 从服务启动到处理一次请求

下面采用常见的 FastAPI 后端组织方式说明。FastAPI 定义 HTTP 接口及其处理函数；Uvicorn 等 **ASGI 服务器**（负责接收网络请求并调用 FastAPI 应用的服务器程序）使这些接口能够通过网络访问。

| 阶段 | 发生的事 |
| --- | --- |
| 服务启动准备 | 程序创建 FastAPI 应用，注册 HTTP 方法、请求路径与路由函数的对应关系，记录参数和依赖声明，并按需要准备配置与共享资源。服务器完成启动准备后，在配置的地址与网络端口上处理请求。 |
| 接收请求并匹配路由 | 客户端向服务地址发送 HTTP 请求。Uvicorn 接收请求并交给 FastAPI，FastAPI 根据 HTTP 方法和路径匹配路由函数。 |
| 准备路由函数所需参数 | 参数准备包含两部分：解析请求数据，按声明的类型及 Pydantic 模型校验字段和约束；解析 `Depends` 声明的依赖，取得路由需要的应用层对象。对象装配（创建相关对象并建立依赖关系）可以发生在依赖准备过程中。 |
| 执行路由函数与应用层逻辑 | 数据和依赖准备成功后，FastAPI 调用路由函数，将参数和所需对象交给它。路由函数调用应用层的方法，应用层使用业务对象表示数据，依据规则与策略组织相应处理。 |
| 调用具体组件 | 应用层按照端口约定调用适配器对象；适配器接入模型服务、检索组件、数据库或执行框架，完成具体调用和必要的数据转换，再将结果交给应用层处理。 |
| 返回结果 | 普通接口将处理结果作为 HTTP 响应返回；采用 SSE 时，可以在任务执行过程中逐步推送事件和回答片段。 |

这里的网络端口用于网络通信，与架构中的 Port（程序调用约定）含义不同。

**顺序需要这样理解：先匹配路由，再为该路由准备请求参数和依赖，准备成功后才执行路由函数。** 数据校验与依赖获取都属于参数准备过程，不能固定理解为“所有 Pydantic 校验都通过后，才执行任何依赖函数”。校验或依赖准备失败时，不会进入该路由的正常业务处理。表中将两项准备工作并列说明，不表示固定先后或并行执行。

**路由匹配确定的是处理函数；应用层对象通过该函数声明的依赖取得。** `Depends` 负责声明由哪个函数提供对象，Pydantic 负责按模型解析和校验数据；具体组件如何选择、对象如何创建和连接，仍由装配代码完成。

### 3. 对象究竟什么时候创建

**声明 `Depends` 不会自动在服务启动时创建所有适配器。** 依赖函数可以创建新对象，也可以返回已经存在的对象，具体时机由代码决定：

| 创建方式 | 什么时候创建 | 后续请求怎样使用 |
| --- | --- | --- |
| 启动时准备 | 在 `lifespan`（管理应用启动初始化和结束清理的机制）等启动代码中创建，例如准备共享模型客户端或数据库连接池。 | 依赖函数取出已准备好的对象并提供给调用方。 |
| 首次使用时创建并缓存 | 第一次调用创建函数时创建对象，并通过额外的缓存机制保存。 | 后续请求可复用当前进程中已缓存的对象。 |
| 按请求创建 | 请求到来、执行依赖函数时创建相应对象。 | 每个请求可以取得新对象；同一请求内，同一依赖的结果默认可以复用。 |

FastAPI 默认的依赖缓存主要在**同一次请求内**复用结果，跨请求复用需要启动初始化或额外缓存代码配合。应用层对象和它使用的组件也可以采用不同的生命周期，例如每个请求创建应用层对象，同时复用模型客户端或数据库连接池。

配置也可以在启动或首次使用时读取并缓存，装配函数随后取得配置，选择需要的适配器。**取得依赖对象，不等于每次都重新读取配置、重新创建全部组件。**

## 第一阶段：本条理解

**这项设计的核心是：让应用层按照领域层声明的端口使用外部组件，由适配器处理不同组件在调用方式和数据格式上的差异。** 这样更换组件时，尽量不需要修改应用层原有的处理逻辑，也方便单独测试应用层。

DeepAssist 面向知识库问答和多步 Agent 任务，需要使用模型服务、知识检索、工具执行模块、记忆模块和 Agent Runtime 等。不同组件有各自的调用方法、参数要求和返回数据格式。如果应用层直接处理这些差异，更换组件时就可能需要修改多处应用层代码；而单独测试应用层的处理逻辑时，也容易依赖真实模型、数据库或执行框架，增加测试的复杂度。

Clean Architecture 用来划分职责，在本项目中，各层可以这样理解：

| 层次 | 主要职责 |
| --- | --- |
| 接口层 | 接收并校验外部请求，调用应用层提供的业务功能，将结果返回给客户端。 |
| 应用层 | 组织业务处理流程，例如知识库问答或 Agent 任务，并协调上下文准备、知识检索、记忆读写和 Agent 执行等环节。 |
| 领域层 | 定义相对稳定的核心业务对象、业务规则与处理策略，以及应用层使用相关组件时依赖的端口。 |
| 基础设施层 | 通过适配器接入具体模型、检索组件、数据库和执行框架，处理调用方式和数据格式的差异。 |

按用途理解，本节将领域层的内容分为两部分：**业务对象、业务规则与处理策略**用于表达和处理系统自身的业务；**端口声明**用于约定怎样使用相关组件。“相对稳定”指它们尽量不受具体模型、数据库或执行框架变化的影响，仍然可以随业务需求调整。

这张表描述的是各层的职责划分，而不是固定的调用顺序。请求处理的完整链路见前置学习知识；路由函数取得所需参数和应用层对象后，调用应用层的方法。

**应用层负责组织业务处理流程，并根据任务需要使用领域层提供的两类内容：**一方面，使用领域层定义的业务对象来表示和传递业务数据，并根据业务规则与处理策略安排相应的处理；另一方面，需要调用模型、数据库或执行框架等组件时，则按照领域层声明的端口调用相应的适配器，由适配器完成具体组件的调用和必要的数据转换。

**端口只负责声明调用约定，本身不执行具体操作。运行时，应用层按照端口约定，调用实际传入的适配器对象。**

为统一术语，后文使用：

- **应用层**：负责组织业务处理流程的代码，例如知识库问答或 Agent 任务。
- **端口（Port）**：定义应用层调用某类组件时，适配器需要提供的方法、输入输出的数据结构，以及必要的执行行为约定。
- **适配器（Adapter）**：基础设施层中按照端口约定实现相应方法，负责接入具体的外部组件，封装其调用方式并进行必要的数据转换。

本项目在领域层通过程序接口声明端口，约定应用层需要调用的方法及输入输出。Python 中可以使用 `Protocol` 或抽象基类等方式表达这些约定。端口不规定外部组件具体怎样调用，而是由基础设施层的适配器负责接入相应组件，封装对 HTTP API、SDK 或数据库驱动的具体调用，并进行必要的数据转换。

**适配器属于基础设施层的一部分，不需要另外划分“适配器层”。**

以 Runtime（负责推进 Agent 任务执行的机制）为例，项目使用 Python 的 `Protocol` 声明端口：

```python
class AgentRuntimePort(Protocol):
    def stream_run(
        self,
        request: AgentRuntimeRequest,
    ) -> Iterator[StreamEvent]:
        ...
```

这段代码要求适配器提供 `stream_run` 实例方法，接收 `AgentRuntimeRequest`，并通过迭代器逐条返回 `StreamEvent`。

**无论是自行编写 Agent 执行逻辑，还是基于 LangGraph 框架实现，都通过各自的适配器，按照 `AgentRuntimePort` 的约定提供相同的 `stream_run(request)` 实例方法，并以统一的 `StreamEvent` 格式返回执行事件。** 这样，应用层可以按照同一个端口调用，而不需要针对具体的执行方式编写不同的调用代码。模型、存储等其他类型的组件使用各自的端口。

`Protocol` 是 Python 提供的**协议类基类**，用于声明接口需要提供的方法及其输入输出类型。它主要配合静态类型检查工具使用：适配器可以显式继承协议类，也可以不继承，只要提供类型兼容的方法，就可以被识别为符合约定。这里的 `AgentRuntimePort` 是继承 `Protocol` 定义的协议类，在架构中承担 Runtime 端口的作用。

另一种方式是使用 `ABC` 配合 `@abstractmethod` 声明抽象方法，通常由子类继承并实现；仍有未实现抽象方法的类不能实例化。两种方式都可以表达程序接口，但检查方式不同。

**`Protocol` 负责声明接口要求，类型检查工具可以检查方法签名是否兼容，但不能保证实际执行行为和结果正确，因此仍需要测试验证是否符合业务预期。**

如果应用层直接使用具体组件，就需要了解它的调用方法和数据格式，更换组件时可能需要修改应用层代码。

采用 Port/Adapter 后，**应用层依赖领域层声明的端口，基础设施层的适配器也依赖该端口，并按照端口约定实现相应方法。** 与应用层直接依赖具体组件不同，现在由领域层根据业务需要定义端口，具体适配器反过来需要满足端口约定，这就是这里的**依赖倒置**。

它遵循的原则是：高层业务代码和具体实现都依赖抽象，抽象不依赖具体实现细节。**依赖倒置是设计原则，Port/Adapter 是落实它的方式，减少应用层与具体组件之间的耦合是达到的效果。**

**依赖倒置改变的是代码依赖关系，而不是运行时的调用方向。** 运行时，应用层仍然调用具体适配器对象的方法，需要先取得对象并建立调用关系。

结合前置学习知识中的请求链路，在路由参数准备阶段，FastAPI 按 Pydantic 模型解析和校验请求数据，并按照 **`Depends`**（声明所需依赖，由框架调用指定函数并提供返回对象）获取应用层对象。

负责提供应用层对象的依赖函数，可以放在后端入口附近的**装配模块**（负责创建相关对象，并建立它们之间依赖关系的代码，例如 `dependencies.py`）中。需要新建对象时，通过**工厂函数**（负责创建并返回对象的普通函数）根据配置选择并创建适配器，也可以直接创建指定的适配器对象；需要复用时，则取得已经准备好的对象。

需要创建应用层对象时，再通过**构造参数**（创建类实例时传给 `__init__()` 方法的参数）将已准备好的适配器对象传入，由构造函数保存该对象。这种从外部提供所需对象的方式，称为**构造函数依赖注入**。创建对象并连接这些依赖关系的整段代码，负责完成装配。

FastAPI 将取得的应用层对象交给路由参数。路由函数调用应用层的方法后，应用层使用已保存的适配器，按照端口约定调用其方法，例如 `stream_run(request)`，读取执行事件并继续处理。对象何时创建与复用，按前置知识中的生命周期安排；FastAPI 依据 `Depends` 声明获取依赖，具体对象怎样选择、创建和连接由装配代码决定。

这样，当需要更换 Runtime 时，只要新适配器能够满足原有端口约定，通常只需要调整适配器及其创建代码，应用层原有的调用逻辑就可以保持不变。是否扩展端口，取决于应用层是否有原有端口无法满足的调用需求。

在 DeepAssist 中，这套架构主要体现出两个好处：

- **便于组件替换：**项目提供了自定义 Runtime 和基于 LangGraph 的 Runtime，两者通过各自的适配器实现相同的端口约定。因此，可以通过更换传入应用层的适配器来选择 Runtime 实现，而不需要修改应用层原有的调用逻辑。
- **便于独立测试：**测试应用层时，可以使用 `FakeRuntime` 作为测试替身（为测试编写的简化实现），按照事先设定的内容返回执行事件和回答，再检查应用层能否正确处理。同时，使用 `FakeMemoryStore` 代替真实存储实现，将消息保存在内存中，检查应用层是否将正确的用户输入和助手回复交给存储并保存。这验证的是应用层的处理与保存逻辑，不代表已经验证了真实数据库的持久化行为。

**这项设计需要额外编写和维护端口、适配器及装配代码，增加了一定的前期实现成本。** 后续更换外部组件或调整具体实现时，只要端口约定不变、且新适配器仍满足约定，通常只需要修改对应适配器及相关装配代码，而不必改动应用层原有的处理逻辑，从而缩小修改范围，有助于降低后续维护成本。

```text
Q01. 能介绍一下你在 DeepAssist 中的架构设计与组件解耦工作吗？

答：DeepAssist 面向知识库问答和多步 Agent 任务，需要使用模型服务、知识检索、工具执行、记忆和 Agent Runtime 等组件。如果应用层直接处理这些组件在调用方式和数据格式上的差异，更换组件和单独测试应用层都会比较麻烦。

这部分我负责划分各层职责、声明端口并接入适配器，目标是减少组件变化对应用层代码的影响，并支持单独测试。

我按 Clean Architecture 分成接口、应用、领域和基础设施四层。领域层声明应用层需要的端口，基础设施层的适配器负责接入具体组件；创建应用层对象时，再通过构造参数把适配器对象传给它。

项目中的自定义 Runtime 和基于 LangGraph 的 Runtime，通过各自的适配器实现相同的端口约定，可以根据配置选择。现有测试也使用 Runtime 和存储的测试替身，检查应用层的事件处理与会话保存，为替换和独立测试提供了具体依据。


Q02. 一次请求进入后，四层怎样配合？依赖解耦体现在哪里？

答：请求由 Uvicorn 等 ASGI 服务器接收并交给 FastAPI。FastAPI 先根据 HTTP 方法和路径匹配路由，再准备路由参数：按声明的类型和 Pydantic 模型解析、校验数据，并通过 Depends 获取应用层对象。准备成功后，路由函数调用应用层的方法。

应用层组织知识库问答或 Agent 任务，使用领域层的业务对象表示和传递数据，依据规则与策略安排处理；需要使用相关组件时，则按照领域层声明的端口调用已传入的适配器。适配器完成具体调用和必要的数据转换，应用层继续处理结果，最后通过普通 HTTP 响应或 SSE 返回。

解耦体现在应用层按照端口使用组件，具体调用差异由适配器处理。这四层是职责划分，端口声明本身不执行操作，请求不需要机械地依次经过四层。


Q03. 什么是依赖倒置？Port/Adapter 怎样落实它？

答：依赖倒置要求高层业务代码与具体实现都依赖抽象，抽象不依赖具体实现细节。

如果应用层直接使用具体组件，就需要依赖它的调用方法和数据格式，更换组件时可能需要修改应用层代码。为减少这种影响，我在领域层声明端口，规定应用层需要的操作及输入输出；应用层按照端口编写调用代码，基础设施层的适配器负责接入具体组件，并满足端口约定。

采用 Port/Adapter 后，应用层依赖领域层声明的端口，基础设施层的适配器也依赖该端口，并实现相应方法。与应用层直接依赖具体组件不同，现在由领域层根据业务需要定义端口，具体适配器需要满足端口约定，这就是这里的依赖倒置。运行时仍由应用层调用适配器，改变的是代码依赖关系。


Q04. Python 中怎样实现端口、适配器和依赖注入？

答：先用 Protocol，或用 ABC 配合 abstractmethod 声明端口需要的方法及输入输出，再在基础设施层编写适配器类，实现相应方法，完成具体组件的调用和数据转换。例如，AgentRuntimePort 声明 stream_run 方法，适配器按约定提供执行事件。

后端的装配模块负责准备相关对象。可以通过工厂函数根据配置选择、创建适配器，也可以取出已有对象；创建应用层对象时，再通过构造参数将适配器传进去并保存。这种从外部提供所需对象的方式，就是构造函数依赖注入。

在 FastAPI 中，路由通过 Depends 声明提供应用层对象的依赖函数。框架在准备路由参数时调用该函数，并将返回的对象交给路由；路由再调用应用层的方法。对象可以在启动时准备、首次使用时缓存或按请求创建，具体时机由装配代码决定。


Q05. 更换组件时要修改什么？什么情况下还需要调整端口？

答：先检查新组件经适配后，能否满足现有端口约定，包括提供的方法、输入输出，以及结果和状态的含义。如果能够满足，主要调整适配器和装配代码，将新适配器传给应用层；已有配置支持选择的，就通过配置切换。接入后，再验证事件、状态和处理结果是否符合预期。

是否扩展端口取决于应用层的需求。新组件自带更多功能，但应用层不需要使用时，原端口可以保持不变。

例如，假设应用层新增了通过 Runtime 端口主动调用 cancel(task_id) 的需求，而原端口只有 stream_run，就需要考虑补充取消方法，由适配器实现，并增加应用层的调用与结果处理。


Q06. 怎样单独测试应用层？项目里有什么具体例子？

答：先用一个为测试编写的简化实现，替代应用层所依赖的真实组件，让它按设定返回数据。把这个测试替身传给应用层，再输入固定的用户问题，检查应用层如何处理。

例如，项目测试中的 FakeRuntime 提供 stream_run 方法，依次产生节点事件、固定的回答片段和结束事件；FakeMemoryStore 则把会话消息保存在内存中。调用应用层后，通过断言检查预期事件是否返回，以及用户输入和助手回复是否正确保存在内存中。

这条测试检查的是应用层的事件处理与存储调用，无需调用真实模型或读写真实数据库。真实适配器与组件的实际配合及数据库持久化行为，需要另外通过相应的集成测试检查。


Q07. 为什么采用这种架构？主要代价是什么？

答：DeepAssist 使用多种模型、检索、存储和执行组件，存在替换、扩展和单独测试应用层的需求。分层明确各部分的职责，Port/Adapter 则让应用层按照端口使用组件，把具体调用方式和数据格式的差异集中在适配器中处理，减少更换组件时需要修改的应用层代码。

代价是需要额外编写和持续维护端口、适配器及装配代码，增加前期实现成本。后续更换组件时，只要端口约定不变、新适配器仍满足约定，通常就能将修改集中在适配器及装配代码中，缩小修改范围，有助于降低后续维护成本。

因此，端口应优先用于隔离可能变化的外部组件，简单、稳定的内部处理不必每个函数都增加一层抽象。
```
