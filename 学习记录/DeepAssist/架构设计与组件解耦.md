# DeepAssist｜架构设计与组件解耦

## 简历条目

> **架构设计与组件解耦：**按 **Clean Architecture** 分层，以 **Port/Adapter** 落实依赖倒置，隔离业务逻辑与模型、检索、存储及 Runtime 的具体实现，便于组件替换、扩展与独立测试。

本条理解状态：**已确认**。用户于 2026-10-18 确认理解并进入第二阶段；本次按用户要求核对实现依据、精简表达并保存两阶段定稿。

## 第一阶段：本条理解

**这条工作的核心是：把业务处理与外部组件的具体用法分开，让组件发生变化时，尽量少改业务代码，也方便单独测试业务逻辑。**

DeepAssist 需要调用模型、检索知识库、保存状态，还要推进 Agent 任务。如果业务流程直接使用各个组件特有的调用方式和数据格式，更换一个组件就可能牵连多个业务模块；测试业务逻辑时，也容易依赖真实模型和数据库。

Clean Architecture 用来划分职责，各层可以这样理解：

| 层次 | 主要职责 |
| --- | --- |
| 接口层 | 接收外部请求，调用应用功能，将结果返回给客户端。 |
| 应用层 | 组织一次问答或任务处理，协调会话、上下文和任务执行。 |
| 领域层 | 定义核心业务对象、处理规则，以及业务需要的能力接口。 |
| 基础设施层 | 接入具体模型、检索组件、数据库和执行框架。 |

要把分层落实为解耦，还需要明确业务代码怎样使用外部能力：

1. **业务侧定义 Port。** Port 是程序中的能力接口，规定需要哪些操作、接收什么输入、返回什么结果。
2. **Adapter 接入具体组件。** 适配器按照接口约定调用组件，并按需要转换参数和返回结果。
3. **装配代码传入实现。** 在创建业务模块时，选择具体适配器并传给它。这样，业务模块可以通过同一个接口使用不同实现。

业务代码依赖自己需要的接口，适配器也按照这个接口实现。**由业务侧规定需要什么能力，外部实现负责满足约定，这就是这里的依赖倒置。** 运行时，业务代码仍然调用具体适配器；倒置的是代码依赖关系，使核心流程不必直接围绕某个组件的用法编写。

项目中的 Runtime 是一个具体例子。Runtime 在这里指负责推进 Agent 任务执行的机制。领域层定义 `AgentRuntimePort`，通过 `stream_run(request)` 接收任务请求，持续返回统一的执行事件。自定义 Runtime 和 LangGraph 分别通过适配器实现这套接口，装配入口根据配置选择实现并传给应用层，应用层再发起执行、处理返回的事件。

因此，“便于组件替换、扩展与独立测试”分别对应：

- **替换与扩展：**新组件能够满足现有接口和行为约定时，主要调整适配器及装配代码，复用已有业务流程。
- **独立测试：**传入返回预设结果的假实现，检查业务逻辑的处理结果。现有测试使用 `FakeRuntime` 和 `FakeMemoryStore`，检查应用层能否返回执行事件，以及用户输入和助手回复是否按预期保存。

这项设计的代价是需要维护额外的接口、适配器和装配代码。如果新能力超出了现有接口，也需要调整接口及相关业务代码。

**实现备注（供理解和追问时查阅）：**当前各处的隔离程度仍有差异。LLM 的非流式调用直接返回 SDK 消息对象；应用层也保留了 SSE 辅助类引用，以及回退分支中的具体适配器创建。现有成果可以概括为：关键组件已通过接口接入，降低了业务对具体实现的依赖。

```text
Q01. 能介绍一下你在 DeepAssist 中的架构设计与组件解耦工作吗？

答：DeepAssist 需要调用模型、检索知识库、保存状态和执行 Agent 任务。如果业务流程直接绑定这些组件的具体用法，更换组件和单独测试业务逻辑都会比较麻烦。

这部分我负责划分职责、设计接口，目标是减少组件变化对业务流程的影响，并支持单独测试。

我按 Clean Architecture 分成接口、应用、领域和基础设施四层。在业务与外部组件之间使用 Port/Adapter：业务侧定义能力接口，适配器接入具体实现，再由装配代码把选定的实现传给业务模块。

项目中的自定义 Runtime 和 LangGraph 已通过同一个执行接口接入，可以按配置选择。现有测试也使用假 Runtime 和假存储，检查应用层的事件处理和会话保存，为可测试性提供了具体依据。


Q02. Port/Adapter 怎样落实依赖倒置？能结合项目举例吗？

答：Port 是业务侧定义的能力接口，Adapter 是满足这个接口的具体实现。业务代码依赖接口，适配器也按照这个接口实现，让外部组件适应业务需要。

例如，领域层定义 AgentRuntimePort，约定通过 stream_run 接收任务请求、返回统一的执行事件。装配入口根据配置选择自定义 Runtime 或 LangGraph 适配器，并传给应用层。应用层按照接口发起执行、处理事件，具体执行方式由适配器负责。

运行时，应用层仍然调用具体适配器；倒置的是代码依赖关系，使主执行流程不必直接围绕某个框架的调用方式编写。


Q03. 接入或替换一个组件时，具体需要调整哪些地方？

答：新组件能够满足现有接口时，主要调整适配器和装配代码。首先要检查输入输出和业务所需的行为是否兼容，例如 Runtime 的执行事件和结束状态是否符合约定。

然后实现适配器，完成具体调用和必要的数据转换，再在创建业务模块时传入新的实现。已有配置支持选择的，就通过配置切换。

接入后，需要验证事件、状态和业务结果是否符合预期。如果新能力超出了原有接口，就需要调整接口及相关业务代码。因此，这套设计主要是缩小修改范围。


Q04. 这种设计怎样支持独立测试？项目里有什么具体例子？

答：业务模块通过接口使用外部能力，测试时就可以传入符合接口约定的假实现，用预设结果检查业务逻辑。

项目有一条应用层测试，使用 FakeRuntime 返回预设的运行事件、回答片段和结束事件，并用 FakeMemoryStore 保存会话消息。测试检查事件能否返回，以及用户输入和助手回复是否按预期保存，执行这条路径无需调用真实模型或读写真实数据库。

这条测试验证的是应用层如何处理执行结果。真实适配器能否正确调用外部组件、转换数据，还需要另外验证，并通过集成测试检查实际接入。


Q05. 为什么采用这种设计？主要代价是什么？

答：DeepAssist 依赖多种外部组件，存在替换、扩展和单独测试的需求。分层明确各部分的职责，Port/Adapter 则让业务通过接口使用外部能力，把具体接入方式的变化集中到适配器和装配代码中。

代价是需要维护更多接口、数据转换和装配代码，排查问题时也可能需要跨层追踪。因此，主要在业务与外部组件之间建立这些接口；对于简单、稳定的内部处理，不必每个函数都增加一层抽象。
```
