# 案件研判｜效果评测

## 对应简历条目

> **效果评测：**基于脱敏案件与专家标注构建事件级评测集，按案件划分开发集、测试集，统一系统输出与标注事件的匹配规则；在相同候选风险疑点上限与调用预算下开展**基线对比与策略消融**，用 LangSmith 记录结果；**候选风险疑点召回率 86.5%→92.4%**。

> 本文件先保存用户指定的前置学习知识，供后续理解本条时使用；尚未进入本条的正式理解和面试问答阶段。条目沿用当前简历中的“候选风险疑点上限”和“候选风险疑点召回率”。

## 前置学习知识

### 1. 功能正确性：系统有没有按照要求执行

功能正确性关注程序功能和执行流程是否符合预期。例如，在案件研判系统中：

- 工具调用失败时，能否正确记录错误并处理后续任务？
- 有依赖的任务，是否等到所需结果返回后才执行？
- 中断后恢复，是否会重复提交已经保存的结果？

这些问题可以通过功能测试、单元测试、集成测试和回归测试检查。单元测试通常检查一个函数或组件，集成测试检查组件之间怎样配合，回归测试检查改动后原有行为是否仍然符合要求。它们的划分角度不同，可以相互交叉。

通过测试说明系统在所覆盖的场景下符合要求，并不意味着所有未知情况都已经得到验证。

### 2. 系统性能：完成任务需要多长时间，能处理多少工作

这里统一使用**“系统性能”**。它通常包括耗时、吞吐量和资源使用情况。“效率”可以描述单位时间或单位资源完成多少工作，但不适合作为这些指标的统一替代词。

| 观察角度 | 在本项目中看什么 |
| --- | --- |
| 响应时间或端到端耗时 | 从接收请求到完整研判结束需要多久，包括平均耗时、p95 等。 |
| 吞吐量 | 单位时间能完成多少案件或核查任务，统计时说明采用哪种单位。 |
| 资源占用与消耗 | CPU 使用情况、内存峰值、数据库连接占用等，是否接近运行环境的承受范围。 |

模型调用次数、工具调用次数和 Token 用量也应一起记录，它们反映调用用量，并可能影响费用。**Token 用量不等于本机 CPU 或内存占用；费用还取决于相应服务的计费方式。** 因此，性能、调用用量和成本有关联，但不能只用其中一个代替其他指标。

例如，提高并发可能缩短一批任务的完成时间，却增加同一时间的连接和内存占用；也可能因为数据库或模型服务拥堵，反而增加单次耗时。性能优化需要结合实际负载验证。

衡量性能时，要一起确认任务完成情况。请求很快失败，或省略必要核查后提前返回，都不能直接算作有效提速。

### 3. 结果质量：疑点有没有覆盖风险，最终判断有没有依据

系统正常运行，不代表业务结果一定正确。案件研判还要检查：候选风险疑点有没有遗漏应当识别的问题，最终风险事件有没有误判，以及报告中的判断是否有证据支持。

这里沿用[研判策略](研判策略.md)的定义：查询和统计结果整理成结构化事实；业务规则或大模型根据事实提出候选风险疑点；补证核验后，有证据支持的风险判断才作为最终风险事件输出。正文中的“疑点”均指候选风险疑点。

#### 为什么仍然叫“事件级评测集”

**事件级说明评测单位，不是给尚未核验的输出另起一个名称。** 专家按具体风险行为进行标注，说明主体、时间范围、行为类型和相关依据；一个案件可以包含多条标注事件。

候选阶段看系统提出的疑点覆盖了多少标注事件，最终阶段看核验后保留的风险事件是否与标注对应。两种输出都需要按主体、时间范围、风险行为等约定规则匹配，不能用一个宽泛问题匹配所有相关事件。现有评测函数执行一对一匹配，避免同一标注被重复计分。

| 指标 | 看什么 |
| --- | --- |
| 候选风险疑点召回率 | 专家标出的风险事件中，有多少已被候选风险疑点覆盖；此时不要求完成风险核验。 |
| 最终风险事件精确率（Precision） | 系统最终保留的风险事件中，有多少与专家标注对应得上。 |
| 最终风险事件召回率（Recall） | 专家标出的风险事件中，有多少被系统最终正确识别。 |

简历中的 86.5%→92.4% 使用“候选风险疑点召回率”这一名称，与最终阶段的精确率、召回率分别统计。它的分母是专家标注的风险事件数，不是系统自己提出的疑点数。

匹配标准、标注质量和评测集范围都会影响指标含义。报告的证据是否充分，还需要检查证据与判断的对应关系，不能只看精确率和召回率。

### 4. 测试和评测是什么关系

可以按评价目标理解这三类工作：

| 关注方向 | 核心问题 | 常见方法 |
| --- | --- | --- |
| 功能正确性 | 系统有没有按照要求执行？ | 功能测试、单元测试、集成测试、回归测试。 |
| 系统性能 | 完成任务需要多久，能处理多少工作，资源使用怎样？ | 性能测试、负载测试、基准对照。 |
| 结果质量 | 最终输出是否正确、完整、有依据？ | 离线评测、与专家标注对比、人工审核。 |

**这是按评价目标分类，不是把“测试”和“评测”划成互不相交的两类工作。** 测试常用明确条件检查是否符合要求；评测常在固定样本和标准下衡量表现。性能可以通过测试衡量，质量指标也可以设置通过标准，作为回归检查的一部分。

三类工作可以结合进行。例如，同一次对照既记录耗时和调用用量，也检查是否漏掉必要步骤、输出质量是否达标；性能测试还可能发现高负载下的执行错误。

#### 性能对照与策略对照，要固定的条件不同

比较串行与并发的耗时时，要确认两组完成可比的核查工作：必要步骤都已完成，核查内容基本一致，报告质量符合要求。这样才能说明提速不是靠少做工作换来的。这里检查质量，是为了保证耗时对比可信，并不代表并发本身提高了精确率或召回率。

比较研判策略的识别质量时，则固定评测案件、标注、匹配规则、候选风险疑点上限和调用预算，再改变待检验的策略。例如，去掉一条疑点发现通道后，查询内容和输出可能随之变化；这是需要观察的结果，不要求两组执行完全相同的核查任务。

“基线对比”是将改进流程与作为参照的流程比较；“策略消融”是在其他条件尽量一致时，去掉某项策略，观察效果如何变化。具体实验组合和结果在本条正式理解阶段再展开。

### 5. LangSmith 在项目中负责什么

**LangGraph 负责组织和运行研判流程；LangSmith 在这里主要用于记录运行过程、组织评测实验，以及比较不同版本的结果。** 业务上的事件匹配规则和评分标准仍由开发者与领域人员确定，再写成评测逻辑交给平台调用。

这里需要讲清的是：保存哪些数据和结果、何时评分、怎样比较，以及这些记录怎样帮助检查效果。

#### 先分清数据、程序和实验结果

| 对象 | 在本项目中是什么 |
| --- | --- |
| 评测数据集 Dataset | 一组案件输入与对应的专家标注。输入供研判流程使用，标注作为评分依据。 |
| 待评测流程 Target | 接收案件输入、运行研判、返回候选风险疑点和最终风险事件的函数。 |
| 评测器 Evaluator | 按约定规则比较系统输出与专家标注，计算指标的函数。 |
| 实验 Experiment | 某个流程版本在指定数据集上的一组运行及评测记录，关联输出、分数和配置。 |

本项目采用有专家标注的离线评测。标注供评测器使用，不作为研判流程的输入。[LangSmith 评测概念](https://docs.langchain.com/langsmith/evaluation-concepts)

#### 按什么顺序运行、保存和比较

可以按下面顺序理解本项目的评测流程：

1. **准备并保存评测数据。** 整理脱敏案件输入和专家标注，按案件划分开发集、测试集，确定本次使用的数据版本。
2. **确定评测规则和实验配置。** 固定事件匹配规则、候选风险疑点上限和调用预算，记录模型、提示词、代码及策略版本；接入对应的评测函数。
3. **运行待评测流程，记录实际输出。** 对数据集中的案件逐个运行研判，记录候选风险疑点、最终风险事件、耗时和调用用量。接入追踪后，还可以查看具体调用的过程与错误。
4. **计算并记录分数。** 评测器将实际输出与专家标注比较，返回相应分数；再把分数关联到该次运行，并汇总整个实验的结果。
5. **比较多个实验。** 基线、改进方案及消融版本分别运行后，查看已记录的指标差异，并回看具体案件，分析哪些问题多找到了、漏掉了或判断错了。

这里有两种不同的“比较”：**评分时比较系统输出与专家标注；分析时比较不同实验的结果。** 前一种比较产生分数，分数随后被记录；后一种比较利用已记录的结果。保存也不是一个发生在最后的动作：数据集先准备，运行输出和评分随后产生并记录。[LangSmith 评测流程](https://docs.langchain.com/langsmith/evaluation)

上述顺序说明数据之间的依赖，不要求整批案件全部运行完才开始评分；可以对已经完成的案件先评分，最后汇总。

#### 调用追踪和评测记录怎样配合

接入追踪后，可以查看一次研判中的模型请求、工具调用、输入输出、耗时和错误。一次具体调用可以记录为一个 Run，相关调用组成一次完整操作的 Trace（调用轨迹）。这些记录有助于定位“哪一步慢了”“哪个工具失败了”。[LangSmith 运行追踪概念](https://docs.langchain.com/langsmith/observability-concepts)

评测记录则帮助回答“这个版本的识别效果怎样”。发现某个案件的分数下降后，可以再查看对应输出和调用轨迹，分析问题来自疑点发现、工具执行还是核验。这些记录支持分析，具体业务原因仍需要结合案件内容判断。

衡量端到端耗时时，仍以报告完成为计时终点；之后的离线评分不计入报告生成耗时。串行和并发两组保持相同的追踪配置，运行过程中已造成的开销不从计时中人为扣除。

#### 仓库中怎样接入

当前 [langsmith_event_evaluation.py](../../项目源码/案件研判/src/langsmith_event_evaluation.py) 提供了评测接入位置：

- `run_langsmith_event_experiment` 把待评测函数、数据集、评测器和实验配置交给 `client.evaluate`，运行实验。
- `build_event_evaluators` 分别评价候选风险疑点和最终风险事件，并提供实验汇总函数。系统输出与专家标注是否对应，由项目自己的匹配逻辑判断。
- 实验配置记录数据、匹配规则、模型、提示词、代码和策略版本，以及候选风险疑点上限和调用预算，便于判断不同实验是否具有可比性。

#### 源码标识怎样对应业务对象

现有接口沿用以下英文标识，它们用于定位代码，不增加新的业务对象：

| 源码标识 | 统一业务含义 |
| --- | --- |
| `candidate_events`、`candidate_limit`、`candidate_recall` | 候选风险疑点列表、数量上限和召回率。 |
| `final_events`、`final_precision`、`final_recall` | 最终风险事件及其精确率、召回率。 |

`candidate_events.py` 生成的是带风险描述和事实引用的待核查判断，不是工具的原始查询结果。查询、统计事实仍需与疑点判断分开保存；不能凭字段里有 `event` 就把尚待验证的判断当成事实。

当前主图在核查任务执行后、集中核验前汇总候选列表。若要单独衡量两条通道最初发现疑点的能力，应在合并去重后、补证前另外保存该列表。对照实验必须使用同一统计位置，不能用补证后的疑点扩充结果替代初始召回结果。本次术语统一不改变运行顺序或既有指标数值，原始实验的具体取值位置仍需在正式评测说明中确认。

因此，这部分工作的重点是**准备可比的数据与规则、实现评分逻辑、组织对照并分析结果**；LangSmith 为这些工作提供运行记录和实验管理能力。
