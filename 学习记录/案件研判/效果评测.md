# 案件研判｜效果评测

## 对应简历条目

> **效果评测：**基于脱敏案件与专家标注构建事件级评测集，按案件划分开发集、测试集，统一系统输出与标注事件的匹配规则；在相同候选风险疑点上限与调用预算下开展**基线对比与策略消融**，用 LangSmith 记录结果；**候选风险疑点召回率 86.5%→92.4%**。

> 本条理解状态：已确认主线。依据本轮会话确认的理解，结合研判策略、任务编排及评测实现整理。前置学习知识第 1—4 节保留用户已确认的原文；第一阶段与第二阶段已补充，尚未明确的实验细节集中列在文末。

## 前置学习知识

### 1. 功能正确性：系统有没有按照要求执行

功能正确性关注程序功能和执行流程是否符合预期。例如，在案件研判系统中：

- 工具调用失败时，能否正确记录错误并处理后续任务？
- 有依赖的任务，是否等到所需结果返回后才执行？
- 中断后恢复，是否会重复提交已经保存的结果？

这些问题可以通过功能测试、单元测试、集成测试和回归测试检查。单元测试通常检查一个函数或组件，集成测试检查组件之间怎样配合，回归测试检查改动后原有行为是否仍然符合要求。它们的划分角度不同，可以相互交叉。

通过测试说明系统在所覆盖的场景下符合要求，并不意味着所有未知情况都已经得到验证。

### 2. 系统性能：完成任务需要多长时间，能处理多少工作

这里统一使用**“系统性能”**。它通常包括耗时、吞吐量和资源使用情况。“效率”可以描述单位时间或单位资源完成多少工作，但不适合作为这些指标的统一替代词。

| 观察角度 | 在本项目中看什么 |
| --- | --- |
| 响应时间或端到端耗时 | 从接收请求到完整研判结束需要多久，包括平均耗时、p95 等。 |
| 吞吐量 | 单位时间能完成多少案件或核查任务，统计时说明采用哪种单位。 |
| 资源占用与消耗 | CPU 使用情况、内存峰值、数据库连接占用等，是否接近运行环境的承受范围。 |

模型调用次数、工具调用次数和 Token 用量也应一起记录，它们反映调用用量，并可能影响费用。**Token 用量不等于本机 CPU 或内存占用；费用还取决于相应服务的计费方式。** 因此，性能、调用用量和成本有关联，但不能只用其中一个代替其他指标。

例如，提高并发可能缩短一批任务的完成时间，却增加同一时间的连接和内存占用；也可能因为数据库或模型服务拥堵，反而增加单次耗时。性能优化需要结合实际负载验证。

衡量性能时，要一起确认任务完成情况。请求很快失败，或省略必要核查后提前返回，都不能直接算作有效提速。

### 3. 结果质量：疑点有没有覆盖风险，最终判断有没有依据

系统正常运行，不代表业务结果一定正确。案件研判还要检查：候选风险疑点有没有遗漏应当识别的问题，最终风险事件有没有误判，以及报告中的判断是否有证据支持。

这里沿用[研判策略](研判策略.md)的定义：查询和统计结果整理成结构化事实；业务规则或大模型根据事实提出候选风险疑点；补证核验后，有证据支持的风险判断才作为最终风险事件输出。正文中的“疑点”均指候选风险疑点。

#### 为什么仍然叫“事件级评测集”

**事件级说明评测单位，不是给尚未核验的输出另起一个名称。** 专家按具体风险行为进行标注，说明主体、时间范围、行为类型和相关依据；一个案件可以包含多条标注事件。

候选阶段看系统提出的疑点覆盖了多少标注事件，最终阶段看核验后保留的风险事件是否与标注对应。两种输出都需要按主体、时间范围、风险行为等约定规则匹配，不能用一个宽泛问题匹配所有相关事件。现有评测函数执行一对一匹配，避免同一标注被重复计分。

| 指标 | 看什么 |
| --- | --- |
| 候选风险疑点召回率 | 专家标出的风险事件中，有多少已被候选风险疑点覆盖；此时不要求完成风险核验。 |
| 最终风险事件精确率（Precision） | 系统最终保留的风险事件中，有多少与专家标注对应得上。 |
| 最终风险事件召回率（Recall） | 专家标出的风险事件中，有多少被系统最终正确识别。 |

简历中的 86.5%→92.4% 使用“候选风险疑点召回率”这一名称，与最终阶段的精确率、召回率分别统计。它的分母是专家标注的风险事件数，不是系统自己提出的疑点数。

匹配标准、标注质量和评测集范围都会影响指标含义。报告的证据是否充分，还需要检查证据与判断的对应关系，不能只看精确率和召回率。

### 4. 测试和评测是什么关系

可以按评价目标理解这三类工作：

| 关注方向 | 核心问题 | 常见方法 |
| --- | --- | --- |
| 功能正确性 | 系统有没有按照要求执行？ | 功能测试、单元测试、集成测试、回归测试。 |
| 系统性能 | 完成任务需要多久，能处理多少工作，资源使用怎样？ | 性能测试、负载测试、基准对照。 |
| 结果质量 | 最终输出是否正确、完整、有依据？ | 离线评测、与专家标注对比、人工审核。 |

**这是按评价目标分类，不是把“测试”和“评测”划成互不相交的两类工作。** 测试常用明确条件检查是否符合要求；评测常在固定样本和标准下衡量表现。性能可以通过测试衡量，质量指标也可以设置通过标准，作为回归检查的一部分。

三类工作可以结合进行。例如，同一次对照既记录耗时和调用用量，也检查是否漏掉必要步骤、输出质量是否达标；性能测试还可能发现高负载下的执行错误。

#### 性能对照与策略对照，要固定的条件不同

比较串行与并发的耗时时，要确认两组完成可比的核查工作：必要步骤都已完成，核查内容基本一致，报告质量符合要求。这样才能说明提速不是靠少做工作换来的。这里检查质量，是为了保证耗时对比可信，并不代表并发本身提高了精确率或召回率。

比较研判策略的识别质量时，则固定评测案件、标注、匹配规则、候选风险疑点上限和调用预算，再改变待检验的策略。例如，去掉一条疑点发现通道后，查询内容和输出可能随之变化；这是需要观察的结果，不要求两组执行完全相同的核查任务。

“基线对比”是将改进流程与作为参照的流程比较；“策略消融”是在其他条件尽量一致时，去掉某项策略，观察效果如何变化。具体实验组合和结果在本条正式理解阶段再展开。

## 第一阶段：本条理解

这条工作的核心是：**用统一的评测数据、匹配规则和对照条件，判断研判策略能否减少风险遗漏，并分析哪些策略对结果有帮助。**

系统先整理结构化事实，通过业务规则通道和大模型分析通道发现候选风险疑点，再规划并执行核查任务，对证据集中核验，必要时继续定向补证。候选疑点说明有什么值得查，最终风险事件说明本次流程中哪些风险判断得到了证据支持。

本条评测对应这条业务主线：候选阶段检查疑点覆盖了多少标注事件，最终阶段检查保留的风险事件是否与标注对应。[研判策略](研判策略.md)负责设计怎样识别和核查，[任务编排](任务编排.md)负责安排任务执行，本条负责衡量和比较识别效果。

### 1. 用案件数据和专家标注，明确评价对象

脱敏案件提供系统分析所需的数据，专家标注提供评分依据，包括涉及的主体、时间范围、风险行为和相关依据。专家标注供评测程序使用，不作为研判流程的输入。

“事件级”说明以一项具体风险行为为评测单位。一个案件可以包含多条标注事件，需要逐条检查是否被系统覆盖，不能只看整个案件是否被判为有风险。候选疑点仍是待核查问题；将它与标注事件匹配，是评价它是否覆盖了应当识别的风险。

数据按案件整体划分：开发集用于分析遗漏、调整规则或提示词，测试集用于在方案确定后检验效果。同一案件中的人员、交易和事件相互关联，整体划分可以减少开发与测试之间的信息泄漏。测试结果用于评价，不能反复据此调整方案后，仍把同一批测试案件当作未参与调试的数据。

### 2. 统一匹配规则，明确怎样才算找到了

系统输出与专家标注的文字可能不同，需要围绕主体、时间范围、风险行为和关键事实等条件，判断是否对应同一件事。具体比较哪些字段、时间范围允许多大差异，要由评测协议确定，并在对照中保持一致。

例如，专家标注的是某人在特定时间内的一项具体风险行为，系统只提出“此人可能存在资金问题”，描述过于宽泛，就不能据此覆盖所有相关事件。

当前评测实现按约定字段进行比较，并执行一对一匹配：一条系统输出最多匹配一条标注事件，一条标注事件也最多被匹配一次，避免重复疑点抬高召回率。缺少必要匹配信息的输出，不能直接计为匹配成功。

### 3. 固定对照条件，区分整体改善与策略贡献

比较识别质量时，固定评测案件、专家标注、匹配规则、候选风险疑点上限和调用预算，并在流程的同一位置保存用于评分的候选列表。未参与本次比较的模型、提示词等设置也要保持一致。

多输出疑点、多调用工具，都可能增加覆盖风险的机会。因此，需要控制允许使用的额度，同时记录实际疑点数量和调用消耗。两组的实际疑点数量和查询内容可以随策略变化；相同上限不代表实际消耗完全相同。

| 比较方式 | 具体做法 | 判断什么 |
| --- | --- | --- |
| 基线对比 | 将改进方案与作为参照的流程比较。 | 整体方案有没有改善。 |
| 策略消融 | 在完整方案中去掉某项策略，其他条件尽量保持一致。 | 这项策略在当前方案和评测条件下有什么贡献。 |

消融需要结合受影响的阶段解释。若初始候选列表保存在补证前，后续定向补证的收益就应通过最终阶段等相应指标观察，不能归因成这份初始列表的召回提升。原始实验实际采用哪个统计位置，见文末待补事项。

质量对照允许策略改变查询内容；串行与并发的耗时对照则要确认必要核查工作具有可比性。两种对照目的不同，不能把并发提速直接解释为识别效果提高。

### 4. 用 LangSmith 记录运行和评分，支持比较与复查

研判流程接收案件输入，返回候选风险疑点和最终风险事件；评测程序按统一规则，将这些输出与专家标注匹配，计算相应指标。LangSmith 记录输出、评分和实验配置，将它们关联到对应的运行。

随后比较基线、改进方案和消融版本的结果，并回看具体案件，分析哪些风险多覆盖了、哪些仍然遗漏，以及最终输出中哪些判断没有与标注匹配。评分时比较的是“系统输出与专家标注”，分析实验时比较的是“不同方案的评测结果”。

业务上的匹配规则和评分逻辑由项目确定。LangSmith 支持实验运行、记录与比较，必要时结合对应调用记录进一步分析原因。

### 5. 候选召回率的结果说明什么

候选风险疑点召回率，衡量专家标注的风险事件中，有多少已经被系统提出的疑点覆盖：

> 候选风险疑点召回率 = 被候选疑点匹配覆盖的标注事件数 ÷ 专家标注的风险事件总数。

当前评测实现先分别匹配各个案件，再汇总匹配数和标注数计算整体召回率，避免跨案件匹配。候选与最终输出分别评分。

**86.5%→92.4%，表示提高了 5.9 个百分点。**在所用评测数据和约定条件下，被比较方案的候选疑点覆盖了更多标注事件，遗漏有所减少。评测方法和 LangSmith 用于测量、记录和分析这项变化。

进入候选范围不代表已经完成核验。最终风险事件的精确率衡量最终输出中有多少与标注匹配，最终召回率衡量标注事件中有多少被最终输出覆盖。这两个指标与候选召回率分别统计；整套策略的收益也需要结合具体消融结果分析，不能直接归给某个组件。

## 第二阶段：面试问答

沿用本轮 Q01—Q07。每题的“考察重点”“回答顺序”和 Q01 的方括号用于提示记忆，口述时不需要念出来。

Q01 按 STAR 组织整条工作；其他题按各自的核心考察内容安排先后顺序。回答顺序负责提示，答案保留完整句子，避免只背关键词。

```text
Q01. 你是怎样做案件研判效果评测的？

考察重点：能否讲清评测需求、个人职责、主要做法和结果。
回答顺序：S 为什么需要评测 → T 我负责什么 → A 怎样评测 → R 对照结果

答：
[S] 系统通过业务规则和大模型分析发现疑点，再经过补证核验形成最终风险事件。调整策略后，需要用统一标准判断是否减少了风险遗漏。

[T] 我负责建立这部分离线评测流程，让不同方案能够按同一标准比较，并回查具体结果。

[A] 我基于脱敏案件和专家标注构建事件级评测集，按案件划分开发集和测试集，统一系统输出与标注事件的匹配规则。然后，在相同候选风险疑点上限和调用预算下，开展基线对比与策略消融，用 LangSmith 记录输出、评分和实验配置，再结合具体案件分析差异。

[R] 对照结果是，候选风险疑点召回率从 86.5% 提升到 92.4%，提高了 5.9 个百分点，说明在这组评测条件下，疑点覆盖了更多标注事件，遗漏有所减少。


Q02. 事件级评测集是怎样准备和划分的？

考察重点：评价对象是否明确，开发与测试是否分开。
回答顺序：案件输入与标注 → 事件级单位 → 按案件划分及原因

答：评测集包含脱敏案件数据和对应的专家标注。案件数据供系统分析，专家标注说明应当识别的风险事件，包括主体、时间范围、风险行为和相关依据，只用于后续评分。

“事件级”表示以一项具体风险行为为评测单位。一个案件可以包含多条标注事件，需要逐条判断系统是否覆盖。

数据按案件整体划分：开发集用于调整规则、提示词和策略，测试集用于检验确定后的方案。同一案件中的记录关联较强，整体划分可以减少信息泄漏。测试集不参与反复调试，避免对测试数据越调越好，却无法反映新案件上的效果。


Q03. 系统输出与专家标注表述不同，怎样判断是否匹配？

考察重点：匹配标准是否明确，能否避免宽泛或重复输出抬高分数。
回答顺序：确定比较条件 → 判断是否为同一事件 → 一对一计分

答：按照事先约定的主体、时间范围、风险行为和关键事实等条件，判断是否对应同一件事，不要求文字完全一致。具体匹配字段和时间范围允许的差异，需要在评测前确定。

例如，专家标注的是某人在特定时间内的一项具体风险行为，系统只提出“此人可能存在资金问题”，描述过于宽泛，就不能算作有效覆盖。

计分时采用一对一匹配：一条输出最多匹配一条标注，一条标注也最多被匹配一次，避免重复疑点抬高召回率。不同方案使用同一套规则。


Q04. 候选风险疑点召回率怎样计算？它与最终风险事件的指标有什么区别？

考察重点：是否清楚指标的分母、统计阶段和结论范围。
回答顺序：候选指标怎样计算 → 数值变化说明什么 → 与最终指标的区别

答：候选风险疑点召回率，等于被候选疑点匹配覆盖的标注事件数，除以专家标注的风险事件总数。计算时先分别匹配各个案件，再汇总事件数量，衡量应当识别的风险有多少已经进入待核查范围。

86.5% 提升到 92.4%，说明覆盖率提高了 5.9 个百分点，但进入候选范围并不代表已经完成核验。

最终精确率看最终输出的风险事件中，有多少与专家标注匹配；最终召回率看专家标注的风险事件中，有多少被最终输出覆盖。因此，候选召回率和最终阶段的指标需要分别统计。


Q05. 怎样保证不同研判策略的对照具有可比性？

考察重点：能否控制其他影响因素，区分相同上限与实际消耗。
回答顺序：固定数据、标准和统计位置 → 控制额度并记录消耗 → 改变待比较的策略

答：固定评测案件、专家标注、匹配规则，并在流程的同一位置统计候选列表，避免把补证前后的结果混在一起比较。

同时，固定候选风险疑点上限和调用预算，并记录实际疑点数量与调用消耗。这样比较的是相同额度约束下的识别效果，也能看出效果改善伴随多少实际消耗。

在这些条件下改变需要检验的策略，其他模型、提示词等设置保持一致。固定的是允许使用的额度，实际查询内容、疑点数量和调用量可以随策略变化。


Q06. 基线对比和策略消融分别用来判断什么？

考察重点：能否区分整体改善与单项策略的作用，并按对应阶段解释结果。
回答顺序：基线看整体 → 消融看策略 → 结合统计阶段解释

答：基线对比是把改进方案与作为参照的流程比较，判断整体方案有没有改善。

策略消融是在完整方案中去掉某项策略，其他条件尽量保持一致，观察指标怎样变化，用来分析这项策略在当前方案中的作用。

解释结果时，还要看策略影响哪个阶段。例如，如果初始候选列表在补证前保存，后续定向补证就应重点通过最终风险事件的指标评价，不能用它解释这份初始列表的召回提升。


Q07. LangSmith 在这套评测中具体负责什么？

考察重点：能否讲清谁负责评分、平台记录什么，以及记录怎样用于分析。
回答顺序：平台负责什么 → 输出怎样评分和记录 → 怎样比较与复查

答：LangSmith 主要用于记录各个方案的运行输出、评分和实验配置，并支持比较结果；具体的事件匹配规则和评分逻辑由项目实现。

研判流程接收案件输入，返回候选风险疑点和最终风险事件。评测程序将输出与专家标注匹配，计算指标，LangSmith 将输出、分数和配置关联到对应的运行记录。

比较不同方案时，先看指标变化，再回到具体案件，检查哪些风险新增覆盖、哪些仍然遗漏，以及最终输出中哪些判断没有与标注匹配；必要时结合调用记录分析原因。
```
