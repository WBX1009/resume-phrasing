# 案件研判｜效果评测

## 对应简历条目

> **效果评测：**基于脱敏案件与专家标注构建事件级评测集，按案件划分开发集、测试集，统一系统输出与标注事件的匹配规则；在相同候选风险疑点上限与调用预算下开展**基线对比与策略消融**，用 LangSmith 记录结果；**候选风险疑点召回率 86.5%→92.4%**。

> 本条理解状态：已确认主线。依据用户确认的理解，结合研判策略、任务编排及当前公开评测实现整理。前置学习知识第 1—4 节保留用户已确认的原文；原始实验尚未明确的细节集中列在文末。

## 前置学习知识

### 1. 功能正确性：系统有没有按照要求执行

功能正确性关注程序功能和执行流程是否符合预期。例如，在案件研判系统中：

- 工具调用失败时，能否正确记录错误并处理后续任务？
- 有依赖的任务，是否等到所需结果返回后才执行？
- 中断后恢复，是否会重复提交已经保存的结果？

这些问题可以通过功能测试、单元测试、集成测试和回归测试检查。单元测试通常检查一个函数或组件，集成测试检查组件之间怎样配合，回归测试检查改动后原有行为是否仍然符合要求。它们的划分角度不同，可以相互交叉。

通过测试说明系统在所覆盖的场景下符合要求，并不意味着所有未知情况都已经得到验证。

### 2. 系统性能：完成任务需要多长时间，能处理多少工作

这里统一使用**“系统性能”**。它通常包括耗时、吞吐量和资源使用情况。“效率”可以描述单位时间或单位资源完成多少工作，但不适合作为这些指标的统一替代词。

| 观察角度 | 在本项目中看什么 |
| --- | --- |
| 响应时间或端到端耗时 | 从接收请求到完整研判结束需要多久，包括平均耗时、p95 等。 |
| 吞吐量 | 单位时间能完成多少案件或核查任务，统计时说明采用哪种单位。 |
| 资源占用与消耗 | CPU 使用情况、内存峰值、数据库连接占用等，是否接近运行环境的承受范围。 |

模型调用次数、工具调用次数和 Token 用量也应一起记录，它们反映调用用量，并可能影响费用。**Token 用量不等于本机 CPU 或内存占用；费用还取决于相应服务的计费方式。** 因此，性能、调用用量和成本有关联，但不能只用其中一个代替其他指标。

例如，提高并发可能缩短一批任务的完成时间，却增加同一时间的连接和内存占用；也可能因为数据库或模型服务拥堵，反而增加单次耗时。性能优化需要结合实际负载验证。

衡量性能时，要一起确认任务完成情况。请求很快失败，或省略必要核查后提前返回，都不能直接算作有效提速。

### 3. 结果质量：疑点有没有覆盖风险，最终判断有没有依据

系统正常运行，不代表业务结果一定正确。案件研判还要检查：候选风险疑点有没有遗漏应当识别的问题，最终风险事件有没有误判，以及报告中的判断是否有证据支持。

这里沿用[研判策略](研判策略.md)的定义：查询和统计结果整理成结构化事实；业务规则或大模型根据事实提出候选风险疑点；补证核验后，有证据支持的风险判断才作为最终风险事件输出。正文中的“疑点”均指候选风险疑点。

#### 为什么仍然叫“事件级评测集”

**事件级说明评测单位，不是给尚未核验的输出另起一个名称。** 专家按具体风险行为进行标注，说明主体、时间范围、行为类型和相关依据；一个案件可以包含多条标注事件。

候选阶段看系统提出的疑点覆盖了多少标注事件，最终阶段看核验后保留的风险事件是否与标注对应。两种输出都需要按主体、时间范围、风险行为等约定规则匹配，不能用一个宽泛问题匹配所有相关事件。现有评测函数执行一对一匹配，避免同一标注被重复计分。

| 指标 | 看什么 |
| --- | --- |
| 候选风险疑点召回率 | 专家标出的风险事件中，有多少已被候选风险疑点覆盖；此时不要求完成风险核验。 |
| 最终风险事件精确率（Precision） | 系统最终保留的风险事件中，有多少与专家标注对应得上。 |
| 最终风险事件召回率（Recall） | 专家标出的风险事件中，有多少被系统最终正确识别。 |

简历中的 86.5%→92.4% 使用“候选风险疑点召回率”这一名称，与最终阶段的精确率、召回率分别统计。它的分母是专家标注的风险事件数，不是系统自己提出的疑点数。

匹配标准、标注质量和评测集范围都会影响指标含义。报告的证据是否充分，还需要检查证据与判断的对应关系，不能只看精确率和召回率。

### 4. 测试和评测是什么关系

可以按评价目标理解这三类工作：

| 关注方向 | 核心问题 | 常见方法 |
| --- | --- | --- |
| 功能正确性 | 系统有没有按照要求执行？ | 功能测试、单元测试、集成测试、回归测试。 |
| 系统性能 | 完成任务需要多久，能处理多少工作，资源使用怎样？ | 性能测试、负载测试、基准对照。 |
| 结果质量 | 最终输出是否正确、完整、有依据？ | 离线评测、与专家标注对比、人工审核。 |

**这是按评价目标分类，不是把“测试”和“评测”划成互不相交的两类工作。** 测试常用明确条件检查是否符合要求；评测常在固定样本和标准下衡量表现。性能可以通过测试衡量，质量指标也可以设置通过标准，作为回归检查的一部分。

三类工作可以结合进行。例如，同一次对照既记录耗时和调用用量，也检查是否漏掉必要步骤、输出质量是否达标；性能测试还可能发现高负载下的执行错误。

#### 性能对照与策略对照，要固定的条件不同

比较串行与并发的耗时时，要确认两组完成可比的核查工作：必要步骤都已完成，核查内容基本一致，报告质量符合要求。这样才能说明提速不是靠少做工作换来的。这里检查质量，是为了保证耗时对比可信，并不代表并发本身提高了精确率或召回率。

比较研判策略的识别质量时，则固定评测案件、标注、匹配规则、候选风险疑点上限和调用预算，再改变待检验的策略。例如，去掉一条疑点发现通道后，查询内容和输出可能随之变化；这是需要观察的结果，不要求两组执行完全相同的核查任务。

“基线对比”是将改进流程与作为参照的流程比较；“策略消融”是在其他条件尽量一致时，去掉某项策略，观察效果如何变化。具体实验组合和结果在本条正式理解阶段再展开。

## 第一阶段：本条理解

这条工作的核心是：**用统一的数据、匹配规则和对照条件，判断研判策略能否减少风险遗漏，并分析哪些策略对结果有帮助。**

系统先整理事实，通过业务规则和大模型分析两条通道发现疑点，再规划、执行核查任务，对证据集中核验，必要时定向补证。评测沿着这条流程，分别检查候选疑点覆盖了多少标注事件，以及最终风险判断是否与标注对应。

### 1. 用案件数据和专家标注，明确评价对象

脱敏案件是系统的分析输入，专家标注是评分依据，记录应当识别的风险事件，包括主体、时间范围、风险行为和相关依据。专家标注只供评测程序评分使用，不进入研判流程。

“事件级”表示以一项具体风险行为为评测单位。一个案件可以包含多条标注事件，需要逐条检查系统是否覆盖。候选疑点仍是待核查问题；与标注事件匹配，只说明它覆盖了应当识别的风险。

数据按案件整体划分：开发集用于调整规则、提示词和策略，测试集用于检验确定后的方案。同一案件中的人员、交易和事件关联较强，将整个案件放在同一组，可以减少信息泄漏。测试集不用于反复调试。

### 2. 统一匹配规则，明确怎样才算找到了

先约定业务上怎样算同一事件，例如需要核对哪些主体、时间范围、风险行为和关键事实，再把这些条件写成统一的匹配规则。各个对照方案使用同一套规则。

当前公开评分代码按预设字段匹配：系统输出和专家标注都要提供这些字段，字段值统一格式后比较是否相等。时间重叠等附加条件，可以通过判断函数检查。代码不会自动判断两段描述的语义是否相同。

例如，只提出“此人可能存在资金问题”，又缺少识别具体事件所需的信息，就不能直接算作覆盖。

计分在同一案件内采用一对一匹配：一条输出最多匹配一条标注，一条标注也最多被匹配一次。缺少规则要求的字段时，不计为匹配成功，重复输出也不能重复得分。

### 3. 固定对照条件，区分整体改善与策略贡献

比较识别质量时，固定评测案件、专家标注、匹配规则和候选列表的统计位置。不属于本轮策略改动的模型、提示词等设置也保持一致。

多输出疑点、多调用工具，都可能增加覆盖风险的机会。因此，对照时既固定候选风险疑点数量上限，也固定整次研判的调用预算。预算分别限制模型调用次数、工具调用次数和 Token 用量，由各项核查与后续补证共同使用。

同时记录实际疑点数量和调用消耗，观察效果改善伴随多少开销。相同上限不代表实际消耗相同，查询内容和疑点数量可以随策略变化。

| 比较方式 | 具体做法 | 判断什么 |
| --- | --- | --- |
| 基线对比 | 将改进方案与作为参照的流程比较。 | 整体方案有没有改善。 |
| 策略消融 | 在完整方案中去掉一项待检验的策略，其他条件尽量一致。 | 这项策略在当前方案中有什么作用。 |

解释消融结果时，还要看候选列表保存在哪个阶段：

- **补证前的列表：**后续补证不会改变这份列表的召回率，补证效果要看后续阶段的相应指标。
- **补证后、集中核验前的列表：**召回率变化可能包含补证的作用，不能全部解释为最初两条通道发现疑点的能力变化。

当前公开主图在核查任务执行后、集中核验前汇总候选疑点。若要单独评价最初发现疑点的能力，需要另存补证前的列表。原始指标采用哪个统计位置，仍需实验记录确认。

### 4. 用 LangSmith 记录结果，支持比较与复查

研判流程接收案件输入，返回候选风险疑点和最终风险事件。评测程序按项目确定的规则，将输出与专家标注匹配并计算指标。LangSmith 记录输出、评分和实验配置，将它们关联到对应的运行。

这里有两种比较：评分时比较“系统输出与专家标注”，分析实验时比较“不同方案的评测结果”。发现指标变化后，再回看具体案件，检查哪些风险多找到了、哪些仍然遗漏，以及哪些最终判断没有与标注匹配；必要时结合调用记录分析原因。

### 5. 候选召回率的结果说明什么

候选风险疑点召回率，衡量专家标注的风险事件中，有多少被系统提出的疑点覆盖。基本公式是：

> 候选风险疑点召回率 = 被候选疑点匹配覆盖的标注事件数 ÷ 专家标注的风险事件总数。

当前公开评分代码先在各案件内匹配，再汇总匹配数与标注数计算整体召回率，不直接平均各案的召回率。候选与最终输出分别评分。原始实验采用的汇总方式，仍需核对记录。

**86.5%→92.4%，表示提高了 5.9 个百分点。**这说明在所用评测数据和约定条件下，候选疑点覆盖了更多标注事件，遗漏有所减少。

这些疑点仍需核验，召回率也不能说明无效疑点是否减少。最终风险事件的精确率看最终输出中有多少与标注匹配，最终召回率看标注事件中有多少被最终输出覆盖，两个阶段分别统计。各项策略的作用，还要结合消融结果分析。

## 第二阶段：面试问答

Q01 按 STAR 组织整条经历；Q02—Q07 分别围绕数据、匹配、指标、对照、消融和工具职责展开。“考察重点”“回答顺序”和方括号用于提示记忆，口述时不用念出来。

```text
Q01. 你是怎样做案件研判效果评测的？

考察重点：评测需求、个人职责、关键做法和结果。
回答顺序：S 为什么要评测 → T 我负责什么 → A 定数据与规则、做对照、查差异 → R 结果说明什么

答：
[S] 系统能生成报告，还需要检查有没有漏掉风险、有没有误判。调整研判策略后，要用统一标准比较效果。

[T] 我负责建立这部分离线评测流程，让不同方案能按同一标准比较，并回查具体结果。

[A] 我先用脱敏案件和专家标注构建事件级评测集，按案件划分开发集和测试集，并统一事件匹配规则。再在相同候选风险疑点上限和调用预算下，开展基线对比与策略消融。评测时用 LangSmith 记录输出、评分和实验配置，再回到具体案件，分析哪些风险多找到了、哪些仍然遗漏。

[R] 对照结果是，候选风险疑点召回率从 86.5% 提升到 92.4%，提高了 5.9 个百分点，说明在这组评测条件下，疑点覆盖了更多标注事件，遗漏有所减少。


Q02. 事件级评测集是怎样准备和划分的？

考察重点：评价单位，以及怎样减少开发与测试之间的信息泄漏。
回答顺序：案件与标注 → 事件级单位 → 按案件划分及原因

答：评测集由脱敏案件和对应的专家标注组成。案件数据用于研判，专家标注记录应当识别的风险事件，包括主体、时间范围、风险行为和相关依据，只供评分使用。

“事件级”表示以一项具体风险行为为评测单位。一个案件可以包含多条标注事件，需要逐条判断系统是否覆盖。

数据按案件整体划分：开发集用于调整规则、提示词和策略，测试集用于检验确定后的方案。同一案件中的记录关联较强，放在同一组可以减少信息泄漏。测试集不参与反复调试。


Q03. 系统输出与专家标注表述不同，怎样判断是否匹配？

考察重点：怎样把业务标准写成匹配规则，并避免重复计分。
回答顺序：约定识别条件 → 按字段比较 → 同一案件内一对一计分

答：先约定识别同一事件需要哪些信息，例如主体、时间范围和风险行为，再确定匹配字段和判断条件。各个方案使用同一套规则。

当前公开评分代码按预设字段比较：双方都要提供这些字段，字段值统一格式后判断是否相等；如需检查时间重叠等附加条件，可通过判断函数处理。只说“此人可能存在资金问题”，又缺少识别具体事件的信息，不能直接算作覆盖。

计分在同一案件内采用一对一匹配：一条输出最多匹配一条标注，一条标注也最多被匹配一次，避免重复得分。


Q04. 候选风险疑点召回率怎样计算？它与最终风险事件的指标有什么区别？

考察重点：指标的分母、统计阶段和结论范围。
回答顺序：怎样计算 → 数值变化说明什么 → 与最终指标的区别

答：候选风险疑点召回率，等于被候选疑点匹配覆盖的标注事件数，除以专家标注的风险事件总数，衡量应当识别的风险有多少进入了待核查范围。

从 86.5% 提升到 92.4%，表示提高了 5.9 个百分点，风险遗漏有所减少。但这些疑点仍需核验，召回率也不能说明无效疑点是否减少。

最终精确率看最终输出的风险事件中，有多少与专家标注匹配；最终召回率看专家标注的风险事件中，有多少被最终输出覆盖。因此，候选阶段和最终阶段要分别统计。


Q05. 怎样保证不同研判策略的对照具有可比性？

考察重点：怎样控制其他影响因素，以及相同上限与实际消耗的区别。
回答顺序：固定数据、规则和统计位置 → 限制额度并记录消耗 → 只改变待检验的策略

答：固定评测案件、专家标注和匹配规则，并在流程的同一位置统计候选列表，避免把补证前后的结果混在一起比较。

同时保持候选风险疑点数量上限和整次研判的调用预算一致，预算分别限制模型调用次数、工具调用次数和 Token 用量。记录实际疑点数量与调用消耗，比较识别效果和实际开销。相同上限不要求实际查询内容和消耗完全相同。

在这些条件下调整需要检验的策略，不属于本轮策略改动的模型、提示词等设置保持一致。


Q06. 基线对比和策略消融分别用来判断什么？

考察重点：整体改善与单项策略在当前方案中的作用。
回答顺序：基线比较什么 → 消融怎样做 → 指标变化说明什么

答：基线对比是把改进方案与作为参照的流程比较，判断整体方案有没有改善。

策略消融是在完整方案中只去掉一项待检验的策略，其他条件尽量保持一致，再观察对应阶段的指标怎样变化。

如果去掉后指标下降，可以作为这项策略在当前方案中有帮助的依据。这个结论限于本次组合和评测条件，不能把整套方案的提升全部归给它。


Q07. LangSmith 在这套评测中具体负责什么？

考察重点：平台与业务评分的分工，以及记录怎样帮助分析结果。
回答顺序：平台负责什么 → 怎样评分和记录 → 怎样比较与复查

答：LangSmith 主要记录各个方案的运行输出、评分和实验配置，并支持比较结果。业务上的事件匹配规则和评分逻辑由项目确定。

运行时，研判流程返回候选风险疑点和最终风险事件，评测程序将它们与专家标注匹配并计算指标。LangSmith 把输出、分数和配置关联到对应的运行记录。

比较时先看指标变化，再回到具体案件，看哪些风险多找到了、哪些仍然遗漏，以及哪些最终判断没有与标注匹配；必要时结合调用记录分析原因。
```

## 待补实验事实

以下细节仍需结合原始实验记录补充；现有理解与问答先按已知事实整理：

- **基线与消融组合：**作为参照的流程包含哪些步骤，各个消融版本具体关闭了什么策略、对应结果，以及各组实际使用的候选上限和调用预算。
- **匹配与统计口径：**实际采用的匹配字段、时间范围判断条件，以及 86.5%→92.4% 使用的候选列表统计位置。补证前的初始疑点与补证后、集中核验前的疑点需要区分。
- **样本与结果汇总：**开发集、测试集各有多少案件和标注事件，86.5% 与 92.4% 来自哪组数据及对应匹配数；是否重复运行，以及整体分数是汇总事件数量计算，还是按案件或运行取平均。

已有简历指标按用户确认的事实保留。当前公开源码用于核对评分、预算和记录机制，不据此推断原始实验的具体配置或单项策略贡献。示例协议中的 baseline、full 和关闭定向补证的版本属于公开合成示例，不是原始实验组合的证据。
