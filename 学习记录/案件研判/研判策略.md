# 案件研判｜研判策略

## 简历条目

> **研判策略：**按业务口径**预设参数化 SQL**，筛选聚合百万级案件记录，形成结构化事实；结合风险识别规则与模型线索生成候选，以核验结果驱动**定向补证**；对照基线流程，最终风险事件：**精确率 81.0%→84.9%**，**召回率 85.0%→87.7%**。

> 本条理解状态：已确认（按用户要求保存本轮最终版本）。

## 第一阶段：本条理解

这条工作的核心是：先从案件记录中整理事实，再形成候选风险事件，通过补证和核验判断候选是否成立。它展示的是一套从数据处理到证据核对的研判方法。

1. **预设参数化 SQL：把业务口径落实为可复用的查询。**

   业务口径规定查哪些数据、怎样关联和统计；开发者据此预先编写 SQL，执行时传入人员、账户、时间范围等参数，由数据库完成筛选和聚合。

   “结构化事实”就是用明确字段表达查到的记录和统计结果，供后续分析与核对。“百万级”说明数据处理规模，不代表把百万条记录直接交给模型。预设查询便于保持口径一致，但新的查询需求可能需要补充或调整模板。

2. **规则与模型：根据事实形成候选，不能直接认定风险。**

   风险识别规则依据明确条件发现可疑情况，模型结合事实提出需要进一步检查的关联或线索，两者共同用于生成候选事件。

   这里要分清：查询事实回答“查到了什么”，候选事件回答“这些事实可能说明什么”。候选仍然需要证据支持，不能把规则触发或模型判断直接当成最终结论。业务查询口径与风险识别规则按用途区分；部分风险规则也可以用 SQL 实现，并非技术上完全分开。

3. **补证与核验：先查证候选，再根据缺口定向补查。**

   结合项目的完整流程，候选形成后开展补证，再集中核验；如果核验发现影响判断的证据缺口，就针对缺口进一步查询，补回的信息再用于核验。

   例如，仅用来说明机制：已经查到资金往来，但判断还缺少双方关系信息，就针对相关主体补查关系数据。“定向”的关键是，补查内容和范围由当前缺少的依据决定。补证既可能支持候选，也可能使其被修正或排除；证据仍不足，不等于候选已被证实。

4. **指标说明最终研判质量，不能单独证明某个环节的贡献。**

   这里评价的是补证、核验后的最终风险事件，不是候选阶段的召回率。

   精确率从 81.0% 提升到 84.9%，表示系统输出中符合标注标准的事件比例提高；召回率从 85.0% 提升到 87.7%，表示标注事件中被系统正确识别的比例提高。

   在统一的评测口径和可比条件下，这说明整套流程相较基线改善了最终识别质量。单项策略贡献多少，需要对应的消融结果，不能把整体提升全部归因于定向补证。

理解主线：按业务口径取数 → 从事实形成候选 → 补证后核验 → 根据缺口定向补查 → 用事件级评测验证整体效果。

## 第二阶段：面试问答

```text
Q01. 你是怎样设计这套研判策略的？

答：这个项目面向纪检监察案件研判。我负责的部分以上游业务分析模型的结果缓存为输入，从中发现值得排查的疑点，再通过补证和核验形成有依据的判断。

我先根据案件数据结构与研判需求，梳理查询、筛选和统计方式，与甲方领域人员确认后，落实为预设的参数化 SQL，整理出后续分析需要的结构化事实。

再结合风险识别规则和大语言模型提出的线索生成候选。候选经过补证后集中核验；如果关键依据仍然不足，就围绕缺口继续补查，再次核验。

对照基线流程，最终风险事件的精确率从 81.0% 提升到 84.9%，召回率从 85.0% 提升到 87.7%。这是整套流程的对照结果。


Q01-1. 你处理的数据来自哪里？上游业务模型和大语言模型有什么区别？

答：我直接处理的是甲方业务分析平台生成的模型结果缓存。这些结果可能是筛选后的记录、统计指标、关系数据或已有的可疑对象标记。

这里的“业务模型”，指平台已有的业务分析功能，例如消费类型统计、资金流向分析。它描述的是业务分析用途，不意味着每个模型都是机器学习模型。

“大语言模型”则是后续阅读事实摘要、理解关联并提出待核查线索的推理组件。介绍时，可以分别称为“上游业务分析模型”和“大语言模型”，避免歧义。

规模方面，目前确认的表述是“百万级案件记录”。模型缓存总行数、单案规模和各类别规模，需要按当时统计另行说明，不能直接视为同一个数字。百万级也不意味着把全部记录直接交给大语言模型。


Q01-2. 四类业务模型分别是什么？人员画像用什么字段解释最直观？

答：现有示例配置中的四类是人员画像、金融画像、电信画像和多维分析。介绍时，每类选择一个代表用途即可。

人员画像可以用“人员与账户、号码的对应关系”解释。配置中有姓名、银行卡、电话等字段，也有账户余额类结果。它们帮助系统识别分析对象，并关联相关账户和号码。

金融画像可以举消费类型分布或资金流向分析，代表信息包括交易金额、时间、方向和交易对手。

电信画像可以用通联关系解释，例如谁与谁联系、何时联系、联系多少次。这些是通俗示例，实际字段需要以客户提供的结果为准；当前示例配置中的这一类没有话单数据。

多维分析可以举银行转账关系、同日相同金额转向不同对手等分析，体现对主体、金额、时间和关系等维度的组合使用。

这些是平台的业务分类，内容可以交叉，不能简单地与人员、资金、通联、资产四种数据领域一一对应。解释人员画像时，优先使用已经确认存在、且能说明研判用途的字段，无须额外假设存在行为标签或人员关系标签。


Q01-3. 面试介绍时，需要先把数据类别、字段和规模全部讲清楚，才能讲设计吗？

答：需要先交代支撑设计的必要背景，但不必在开场讲完全部数据细节。

开场让面试官知道三件事即可：系统处理什么输入、希望得到什么结果、我负责哪部分工作。随后进入研判策略的主线，被追问时再展开模型类别、代表字段和查询细节。

学习准备时，可以沿着“业务场景与数据基础 → 需求和约束 → 方案设计 → 技术实现与选型 → 效果验证”理解完整逻辑。

面试表达则根据问题选取相关部分。介绍整条工作时先讲背景；被问到参数化 SQL 或候选生成时，可以直接回答对应机制，不需要每次重新介绍整个系统。


Q01-4. 方案设计、架构设计、技术实现和技术选型，分别在回答什么问题？

答：方案设计回答“怎样解决业务问题”，架构设计进一步明确模块职责和协作关系，技术实现把这些安排落实为可以运行的机制，技术选型解释为什么这样实现及其代价。

在当前条目中，把过程安排为事实准备、候选生成、补证和核验，属于研判策略与流程设计；明确各环节的输入、输出、数据流和依赖，涉及架构设计。

具体落地包括 SQL 查询模板、统计计算、规则条件、候选数据结构、工具接口和状态流转。使用框架只是其中一部分，例如用 LangGraph 组织步骤和条件分支。

选择理由要结合约束解释。例如，预设 SQL 便于检查和复用查询逻辑，但新增需求需要维护模板；模型分析可以补充线索，同时增加调用成本和推断不可靠的问题。

讲“研判策略”时，重点放在数据如何变成候选、候选如何得到核验。任务调度、并发和恢复机制，可以在对应条目或追问中展开。


Q02. 简历里的“业务口径”是什么意思？你怎样据此设计 SQL？

答：业务口径就是查询、筛选和统计数据时采用的具体标准，明确查什么、怎样关联，以及怎么算。

在项目中，这些标准的设计依据是案件数据结构与研判需求：有哪些字段和关联关系，决定能够查询什么；需要回答哪些研判问题，决定应该怎样筛选和统计。

我据此提出初步方案，再与甲方领域人员确认具体标准，最后落实为预设的参数化 SQL。

通俗地说，就是：“根据现有数据和研判需要，明确要查什么、怎么算，与业务方确认后写成查询。”

“业务口径”强调标准本身。多方讨论是本项目确认标准的方式，对齐认知、消除歧义是它的作用；最终还要形成程序可以执行的明确约定。


Q02-1. 为什么采用预设参数化 SQL？执行时怎样使用？

答：主要是为了让查询逻辑可检查、可复用，并让后续分析建立在明确的查询结果上。

我预先编写查询结构和统计逻辑，执行时传入人员、账户和时间范围等参数，由数据库完成筛选和聚合。金额、次数等结果由数据库或确定性代码计算。

这样便于检查查询范围和统计方式，也避免模型临时生成不可控的查询。它的局限是查询能力受已有模板约束，新的分析需求可能需要补充或调整模板。


Q03. 风险识别规则是什么？这些规则是怎样确定并实现的？

答：风险识别规则，就是把业务上值得排查的情况写成明确条件，再由 SQL 或程序逻辑检查哪些对象符合条件。

例如，可以围绕金额是否达到配置阈值、某个时间窗口内交易是否频繁，以及资金路径是否满足特定条件设计规则。这些只是规则类型的示例，具体阈值和条件需要结合业务确定。

设计时，我先梳理现有模型结果包含哪些字段、能够建立哪些关联，再借助 AI 辅助整理可能的风险模式和识别条件，形成初步方案。

随后与甲方领域人员讨论，结合他们的专业经验，确定哪些规则值得采用、优先级如何，以及判断条件怎样设置，再由我完成技术实现。

我的职责是结合数据能力提出方案，把业务判断转化为明确条件并实现；甲方提供领域经验和业务判断；AI 用于辅助探索和梳理。最终采用的规则及条件，通过沟通共同确定。

另外，存在 A→B→C 的资金路径本身只是一项关系事实。是否值得列为风险候选，还要结合时间、方向、金额等业务条件判断。


Q03-1. 模型线索是什么意思？为什么需要它补充风险识别规则？

答：模型线索，就是大语言模型根据初步整理的案件事实，分析后提出的可疑情况或待核查关联。

规则按照预先定义的条件检查数据，依据明确、便于复核，但覆盖范围受已编码条件限制。大语言模型可以结合多条事实、业务含义和时间关系，提出补充的核验问题，同时也可能产生缺乏证据支持的推断。

因此，两种方式共同用于候选发现：规则覆盖明确的筛查条件，模型补充可能未被现有规则表达的组合疑点。两者的输出都只是候选，后续仍需补证和核验。

这里还要区分两个 AI 使用环节：开发时，AI 辅助我梳理规则；系统运行时，大语言模型根据当前案件事实提出线索。前者辅助方案设计，后者参与候选生成。


Q03-2. “事实包”到底是什么？面试中可以换成什么表达？

答：事实包是把查到的记录和计算结果，按照统一结构组织在一起，并保留来源信息的数据集合。

例如，一项内容可以说明某主体在某个时间范围内发生多少笔交易、合计金额多少、主要对手是谁，并附上对应的记录引用或可恢复的查询范围。

面试中可以称为“初步整理的案件事实”；需要强调技术形式时，可以说“带来源引用的结构化事实摘要”。

例如：“先用 SQL 和程序整理出带来源引用的数据摘要，再交给规则和大语言模型分析。”

其中保存的是数据与计算结果。模型提出的关联假设应单独作为候选保存，避免把推断写成已知事实。


Q03-3. 两条候选通道怎样配合？能保证不漏掉重要线索吗？

答：方案上，两条通道从共同的事实基础分别提出候选，再统一校验、去重并选择后续调查对象，目的是减少初始候选阶段的遗漏。

关键是让模型看到未命中规则的代表性事实。如果只把规则筛出的候选交给模型，它主要是在复查已有候选，就难以补充规则范围以外的线索。

例如，仅作机制说明：摘要里出现 A 向 B、B 向 C 的先后往来，但没有触发现有金额或次数阈值。模型可以提出“是否存在连续中转”的核验问题，再由精细查询检查时间、方向和金额是否对应。如果相同路径条件已经写成规则，规则也可以发现它。

两路命中同一事件时，需要合并来源和依据；两路分别发现不同疑点时，在统一候选上限下选择调查对象。逻辑上独立，不要求同时执行。

这种互补不能保证不漏。如果上游未提供相关数据，或者摘要遗漏关键关系，两条通道都可能受影响。是否有效，需要在相同候选上限和调用预算下，比较新增有效候选、候选召回率和最终事件质量；具体贡献还需要消融对照支持。


Q04. “以核验结果驱动定向补证”具体是什么意思？

答：就是把核验发现的证据缺口，转成有明确对象和范围的补查任务。

例如，仅作机制说明：已经查到资金往来，但还缺少判断所需的双方关系信息，就围绕相关主体补查关系数据。查谁、查什么、查哪个时间范围，都由当前缺口决定。

补回的信息再用于核验。它可能支持候选，也可能使候选被修正或排除；证据仍不足时，应保留待核验状态。


Q05. 这两个指标怎样评测？能说明哪些效果？

答：评价对象是补证和核验后的最终风险事件，以专家标注为参照。精确率看输出事件中有多少正确匹配标注，召回率看标注事件中有多少被正确识别。

我基于脱敏案件和专家标注构建事件级评测集，按案件划分开发集和测试集。在测试集上使用统一的事件匹配规则，并在相同候选上限和调用预算下比较基线与改进流程。

最终风险事件的精确率从 81.0% 提升到 84.9%，召回率从 85.0% 提升到 87.7%，说明整套流程在这组评测条件下改善了最终识别质量。

这里的召回率属于最终事件阶段，不能直接替代候选召回率，也不能单凭整体指标判断规则、模型或定向补证各自贡献了多少。
```
