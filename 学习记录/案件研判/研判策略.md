# 案件研判｜研判策略

## 统一术语

| 名称 | 含义 |
| --- | --- |
| **待核查疑点** | 根据已有事实提出、需要进一步查清的涉嫌违规违纪问题。要说明涉及哪些人、哪段时间，以及什么行为值得核查。 |
| **核查任务** | 为查清疑点而安排的具体工作，例如查询交易明细、核对双方关系和交易背景。 |
| **最终风险事件** | 经过补证和核验，系统认为已有依据支持，并纳入最终报告的具体风险情形。需要说明涉及哪些人、哪段时间、发生了什么，以及判断依据是什么。 |

例如，查到“A 与 B 在某段时间内存在多笔转账，交易频次达到筛查条件”，这是**已经查到的事实**。

根据这些事实提出“这些转账是否缺乏正常业务依据”，这是**待核查疑点**。

接下来安排“查询交易明细，核对双方关系和资金用途”，这是**核查任务**。

任务执行完成后，还要对证据进行集中核验。只有系统认为已有依据支持的风险情形，才会作为**最终风险事件**输出。疑点被排除，或者证据仍然不足，都需要分别记录。

疑点可以写成一个问题，也可以写成“可能存在某种风险，需要进一步核查”。两种写法表达的都是**尚待验证的判断**。

这里的“最终”指本次系统流程的输出阶段。这些风险判断仍可能有误报和漏报，需要由人工复核，并与专家标注进行评测对照。

## 第一阶段：本条理解

这条工作的核心是：**先从大量案件数据中整理出相关事实，再通过规则和大语言模型发现值得核查的问题，最后安排查询、补充证据，判断这些问题是否有依据支持。**

要解决的主要问题有两个：一是数据太多，不能全部交给大语言模型；二是发现可疑情况后，还需要继续核查，才能判断它是正常往来，还是存在违规违纪风险。

### 先弄清数据从哪里来、里面有什么

我接入的是甲方已有平台整理并保存的案件数据，涉及人员、资金、通联和资产等信息。平台已经按不同业务内容组织这些数据，但其中仍保留大量明细，例如每笔交易的时间、金额和对手。

这些记录涉及人员较多，时间跨度较大，整体达到百万级。这里说的是项目处理的记录规模，并不表示每个案件或每类数据都有百万条。

我需要先结合数据说明和实际样本，弄清字段是什么意思、哪些记录可以关联，再围绕当前要分析的问题查询和统计。

### 第一步，用预先写好的查询和程序整理事实

例如，要分析某个人在一段时间内的资金往来，可以先查出相关账户和交易记录，再统计交易次数、累计金额，并保留对应记录的来源。

把这些结果按照明确字段记录下来，就是**结构化事实**。它说明已经查到了什么、计算出了什么，后面可以据此分析，也可以回到原记录核对。

查询时采用的具体标准，就是简历中的“业务口径”。例如：

- 查哪个人、哪些账户、哪个时间段；
- 人员和账户按照什么信息关联；
- 哪些交易计入统计，金额和次数怎样计算。

我根据案件数据结构和研判需求提出这些标准，再与甲方领域人员确认，落实到预设的参数化 SQL 和程序逻辑中。

“参数化 SQL”可以理解为：**查询结构预先写好，执行时再传入人员、账户和时间范围等具体参数。**

我把 SQL 和相关处理逻辑封装成函数，再作为查询分析工具提供给 Agent。Agent 提出工具名称和参数，后端调用对应函数，执行查询并返回结果。

因此，SQL 负责工具内部的查询；工具则让 Agent 能够调用这项查询功能。疑点发现和后续补证，都可以使用这些工具。

### 第二步，用规则和大语言模型分别寻找值得核查的问题

规则负责检查事先确定的条件。例如，单笔金额、一定时间内的累计金额，或者交易次数是否超过设定阈值。

这些条件需要结合实际业务确定，并与甲方领域人员确认。命中规则后，系统记录值得关注的情况及对应事实，形成待核查疑点，后续还要继续核验。

大语言模型则读取相关事实，结合资金往来、时间和人员关系，提出需要进一步核查的问题。

例如，查询结果显示 A 向 C、C 向 B 都发生过转账，时间和金额上存在值得关注的联系。模型可以提出：这两笔交易是否有关联？C 在其中承担什么角色？相关交易是否有正常业务依据？这些问题都需要后续查询验证。

两种方法的作用不同：**规则检查明确条件，大语言模型结合多条事实提出可能被现有规则遗漏的问题。**

要让大语言模型补充发现问题，它需要看到当前分析范围内的相关事实，包括一些没有触发规则的记录。如果只给它规则已经命中的结果，它能继续发现的问题就会受到限制。

这些事实也不能全部一次性输入模型。需要围绕当前分析对象挑选内容，组织成摘要，并保留来源。内容较多时，可以按人员或业务内容分批处理；具体怎样筛选、分批，还要以实际实现为准。

这里的“事实包”，就是把相关查询结果、统计结果和来源放在一起，供后续分析使用。**整理事实不需要等到规则命中后才进行。**

### 第三步，把疑点和相关事实一起交给规划环节，安排核查任务

规则和大语言模型发现的疑点需要汇总。如果两路发现的是同一个问题，就需要合并重复内容，同时保留各自的依据。

一条疑点要讲清楚：怀疑什么、涉及哪些人、哪个时间段、根据哪些事实提出，以及还有什么没有查清。

规划时，再把这些疑点、相关事实、可用工具和执行限制交给大语言模型，让它提出具体核查任务，说明查谁、查什么、查哪段时间，以及怎样算完成。

**疑点告诉模型要查清什么问题，事实告诉模型已经知道什么、还缺什么。** 因此，规划时仍然需要相关事实，不能只提供一句疑点描述。

一个疑点可以对应多个任务。例如，要判断一组交易是否有正常业务依据，可能既需要核对交易明细，也需要查询人员关系和能够获取的业务背景。

这些内容可以按照固定字段记录。疑点记录保存问题及已有依据，任务记录保存要执行的工作。描述本身仍然可以使用自然语言，固定字段方便后端检查、保存和关联。

疑点发现和任务规划也可以由同一个大语言模型完成，但两项工作的目标不同：前者提出值得查的问题，后者安排具体怎样查。实际拆成几次调用，需要以代码为准。

### 第四步，执行核查任务，对证据进行集中核验，再决定是否继续补证

后端检查任务和工具参数后，调用查询分析工具获取信息。相关任务完成后，把查到的证据放在一起，判断疑点是否得到支持、需要修正、可以排除，还是证据仍然不足。

例如，已经发现双方资金往来的金额或频次值得关注，但还不能判断交易是否正常，就继续查询双方关系、交易明细，以及能够获取的资金用途和业务背景。

核验时，如果发现证据不足，就需要进一步说明：**缺少什么信息，这些信息为什么会影响判断，以及下一步可以怎样获取。** 然后据此安排补证任务。

这就是“以核验结果驱动定向补证”：核验发现哪里还没有查清，下一步就围绕这个问题补充证据。

补证同时关注支持和反驳疑点的信息。查回的结果可能支持原来的疑点，也可能说明属于正常往来，或者仍然无法判断。没有查到业务依据，也不能直接当作违规的证据。

是否继续补证，需要分清两类条件：

| 需要考虑什么 | 具体含义 |
| --- | --- |
| **数据和工具能查到什么** | 现有数据是否包含所需信息，已有工具是否支持这项查询。缺少数据或工具能力时，需要记录限制，或者由开发者补充相应能力。 |
| **还允许继续查多少** | 按资源预算、补证轮次上限和停止条件，控制是否继续执行。这里的资源预算包括大语言模型调用次数、工具调用次数和 Token 等额度；一轮补证可以包含多项任务。 |

已有依据足以作出判断时，就不需要重复补证。证据仍然不足，但已经达到执行上限时，应停止继续尝试，并说明哪些问题尚未查清。如果调用被预算限制拒绝或程序执行失败，还要记录相应的失败状态。

**核查任务完成，只说明安排的查询和检查已经执行，不等于疑点成立。** 最终判断仍然要根据查到的证据作出。

任务之间怎样安排先后顺序、怎样通过异步调用支持并发，见[任务编排](任务编排.md)。

### 第五步，分别评价疑点发现和最终输出的效果

评测以专家事先标出的风险事件为对照，按照同一套匹配规则，判断系统结果是否与标注对应。

| 指标 | 看什么 | 结果 |
| --- | --- | --- |
| **疑点阶段召回率** | 专家标出的风险事件中，有多少在疑点发现阶段就被系统提出。此时还不要求完成核验。 | 86.5%→92.4% |
| **最终风险事件精确率** | 系统最终报出的风险事件中，有多少与专家标出的事件对应得上。 | 81.0%→84.9% |
| **最终风险事件召回率** | 专家标出的风险事件中，有多少被系统最终正确找出。 | 85.0%→87.7% |

评测集使用脱敏案件和专家标注，按案件划分开发集、测试集。比较基线和改进流程时，要保持疑点数量上限、调用预算等条件一致。

这些结果说明，在这组评测条件下，整套流程漏掉的风险事件减少了，最终输出中正确识别的比例也提高了。

要判断规则、大语言模型或定向补证各自带来了多少改善，还需要在其他条件一致时，比较加入或去掉某项策略后的结果，也就是进行消融对照。

### 关于个人工作和 AI 的作用

在我负责的部分，我需要理解需求和数据，设计流程，编写 SQL、工具和程序，再通过测试与评测检查结果。

开发时，我会借助 AI 梳理可选方法和规则思路，再结合实际数据判断这些建议是否适用，通过验证决定采用、修改还是舍弃。涉及业务标准的内容，与甲方领域人员确认。

开发时用 AI 帮助设计，与系统运行时用大语言模型分析案件，是两种不同的使用场景。

Q02-1. SQL 和查询分析工具是什么关系？补证时怎样复用？

考察重点：是否清楚 SQL、工具、Agent 和后端各自做什么。
回答顺序：怎样封装 → 谁提出调用、谁执行 → 补证时怎样使用

答：我把预设 SQL 和相关处理逻辑写进函数，再把函数作为工具提供给 Agent。SQL 负责内部查询，工具让 Agent 能够调用这项功能。

执行时，Agent 提出工具名称和参数，后端检查后调用对应函数，并返回结果。查询结构预先写好，大语言模型不需要临时生成 SQL。

疑点发现和补证可以使用同一类工具。补证时，根据还没有查清的问题，指定要查的人员、账户和时间范围；如果已有工具无法完成，再补充或调整相应功能。


Q03. 风险识别规则是怎样确定和实现的？

考察重点：规则有没有业务依据，以及怎样理解规则命中。
回答顺序：规则是什么 → 怎样确定 → 怎样实现 → 命中后怎么办

答：风险识别规则，就是把值得排查的情况写成明确条件，再用 SQL 或程序检查。

我先结合现有数据和研判需求提出规则思路，再与甲方领域人员确认判断条件，最后编写程序并验证结果。例如，可以检查单笔金额、一定时间内的累计金额或交易次数是否超过阈值，具体阈值要根据业务确定。

命中后，系统记录待核查疑点和对应事实，再交给后续补证核验。规则命中本身不代表已经存在违规行为。

考察重点：模型根据什么提出问题，结果怎样交给后续使用。
回答顺序：读取什么 → 怎样分析 → 输出什么

答：大语言模型读取相关事实摘要，结合交易时间、金额和人员关系，提出需要进一步核查的问题。

例如，查询结果中既有 A 向 C 的转账，也有 C 向 B 的转账，时间和金额上存在值得关注的联系。模型可以提出，这些交易是否有关联、C 在其中承担什么角色，以及是否有正常业务依据。这些都是后续要查清的问题。

输出时，用自然语言说明疑点，同时记录涉及人员、时间范围、引用了哪些事实，以及还有什么没有查清，供后续规划任务使用。


Q03-2. 事实包和待核查疑点有什么区别？

考察重点：能否区分已经查到的信息和仍需验证的问题。
回答顺序：直接区分 → 对照举例 → 说明两者关系

答：事实包是整理好的查询记录、统计结果和来源，说明已经查到了什么；疑点说明根据这些事实，还有什么风险问题需要核查。

例如，“某段时间内存在多笔转账”是事实，“这些转账是否缺乏正常业务依据”是疑点。

事实整理不需要等规则命中后才进行。规则和大语言模型都可以根据整理好的事实发现问题。


Q03-3. 规则和大语言模型怎样互补？大语言模型会读取全部事实吗？

考察重点：为什么使用两种方法，以及怎样处理模型输入限制。
回答顺序：各自的作用 → 互补需要什么信息 → 怎样控制输入量 → 怎样验证效果

答：规则负责检查明确条件，大语言模型则结合多条事实，提出可能被现有规则遗漏的问题。

为了补充发现疑点，模型也需要看到没有触发规则、但与当前分析有关的事实。如果只给它规则命中的结果，它能发现的问题就会受到限制。

同时，模型不能一次读取全部记录，需要围绕当前分析对象组织事实摘要，内容多时再分批处理，并保留来源以便回查。

实际多发现了多少问题，需要在相同疑点数量上限和调用预算下评测，再通过消融对照判断两种方法各自的作用。


Q03-4. 这些方案是你自己做的吗？你怎样使用 AI？

考察重点：个人贡献是否清楚，是否能够判断和验证 AI 的建议。
回答顺序：我的职责 → AI 帮助什么 → 我怎样检查 → 谁负责业务确认和最终选择

答：在我负责的部分，方案设计、代码实现和测试验证由我完成。AI 主要帮助我梳理可选方法和规则思路。

对它的建议，我会先检查需要的数据是否具备、判断依据是否合理、是否适合当前需求，再通过验证决定采用、修改还是舍弃。

涉及业务标准的内容，与甲方领域人员确认；最终采用什么方案、代码是否符合要求、验证结果怎样，由我负责。


Q03-5. 发现疑点后怎样规划任务？规划时还要输入事实吗？

考察重点：是否清楚疑点发现与任务规划怎样衔接。
回答顺序：为什么还需要事实 → 提供哪些信息 → 规划得到什么

答：规划时仍然需要相关事实，因为模型既要知道查什么问题，也要知道已经查到了什么、还有什么没有查清。

整理两路发现的疑点后，把选定疑点、对应事实、可用工具和执行限制交给大语言模型。它再提出具体核查任务，说明针对哪个疑点、查谁、查什么、查哪段时间，以及怎样算完成。

一个疑点可以对应多个任务。规划阶段安排要做的工作，任务执行后才会得到新的查询结果。


Q04. 定向补证具体怎么做？怎样决定是否继续？

考察重点：能否根据核验结果安排下一步，并说明什么时候停止。
回答顺序：发现什么不足 → 怎样安排补证 → 怎样再次判断 → 何时停止

答：定向补证就是在核验发现证据不足时，先说明还缺什么、为什么影响判断，再针对这些问题安排查询。

例如，双方资金往来的金额或频次值得关注，但还不能判断是否正常，就继续查询双方关系、交易明细，以及能够获取的资金用途和业务背景。

查回后再次核验，同时查看支持和反驳疑点的信息。结果可能支持、修正或排除疑点，也可能仍然无法判断。

是否继续，要看证据是否还不足、现有数据和工具能否获取所需信息，以及资源预算和补证轮次是否允许。停止补证后，仍未查清的问题需要明确记录，不能直接当作已经得到支持的风险结论。


Q04-1. 核查任务完成，就说明疑点成立了吗？

考察重点：能否分清任务完成和风险判断。
回答顺序：直接回答 → 举例说明 → 解释最终怎样判断

答：不能。任务完成只说明安排的查询和检查已经执行，是否存在风险还要根据结果判断。

例如，“这些转账是否缺乏正常业务依据”是疑点，“查询交易明细并核对双方关系”是核查任务。即使查询成功，也可能发现这些交易属于正常往来，或者现有信息仍然不足。

因此，一个疑点可能需要多项任务。相关证据经过集中核验后，系统认为已有依据支持的风险情形，才会作为最终风险事件输出。
