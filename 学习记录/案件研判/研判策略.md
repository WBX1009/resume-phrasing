# 案件研判｜研判策略

## 统一术语

| 名称 | 含义 |
| --- | --- |
| **结构化事实** | 按明确字段组织、保留来源的数据记录。它来自对原始案件数据的查询、筛选、关联或聚合统计，可以保存明细、关联结果或统计指标，说明已经查到了什么、计算出了什么。 |
| **候选风险疑点** | 根据已有事实，通过业务规则或大模型分析提出、尚需补证核验的风险问题。说明涉及哪些人、哪段时间、什么行为或情形值得核查，以及依据是什么。下文可简称“疑点”。 |
| **核查任务** | 为查清疑点安排的具体工作，例如查询交易明细、核对双方关系、交易背景和资金用途。 |
| **最终风险事件** | 补证核验后，系统认为有证据支持、并纳入最终报告的具体风险行为或情形。需要说明主体、时间范围、具体行为或情形，以及判断依据。 |

例如，查到“A 与 B 在某段时间内存在多笔转账”，这是**结构化事实**；提出“这些转账是否缺乏正常业务依据”，这是**候选风险疑点**；安排“查询交易明细、核对双方关系和资金用途”，这是**核查任务**。

补证取得的新事实用于支持、修正或排除疑点。只有证据支持的风险判断，才作为**最终风险事件**输出；被排除或仍证据不足的疑点，分别记录，不能自动升级为风险事件。

查询、统计工具返回记录和计算结果，整理后形成结构化事实。业务规则筛查和大模型分析根据这些事实提出候选风险疑点；集中核验时，大模型综合相关事实，给出支持、修正、排除疑点或证据不足的判断，并指出仍缺少的证据。这些判断属于分析结果。事实、疑点和核验结果都可以采用结构化格式，但各自表达的内容不同。

本文统一采用“候选风险疑点”和“最终风险事件”区分核验前后两个阶段。核验要查清所怀疑的具体行为或情形是否实际存在，以及已有证据是否足以支持相应风险判断。即使已确认双方发生过转账，也还需要核对交易背景、资金用途、人员关系等信息，并检查有无反驳疑点的证据。这里的“最终”指本次系统流程的输出，仍可由人工复核。

## 前置学习知识

### 表、记录、字段、对应关系与关联

下面以人员、银行账户和交易数据为例，说明这些概念。

| 概念 | 含义与例子 |
| --- | --- |
| **表（Table）** | 用行和列组织并存储某一类数据，例如人员表、银行账户表、交易记录表。 |
| **记录（Record/Row）** | 表中的一行数据，例如某个人的信息、某个银行账户的信息，或者某笔交易。 |
| **字段（Field/Column）** | 表中的一列，表示记录的某个属性，例如人员 ID、银行账号、交易金额、交易时间。 |
| **对应关系** | 根据字段的业务含义和匹配条件，确定记录之间的业务联系。例如，人员表中的 `person_id` 表示人员 ID，账户表中的 `owner_id` 表示账户所属人员的 ID；两者使用同一套人员标识，值相同时，就能确定该账户属于哪个人。 |
| **关联（Join）** | 按指定字段和匹配条件，将相关记录组合起来，供后续查询、筛选、统计或联合分析使用。例如，通过人员 ID 关联人员表与账户表，再通过银行账号关联交易记录表。 |

补充说明：

- 关联字段不要求名称相同，关键是字段的业务含义和匹配条件。例如，`person_id` 和 `owner_id` 可以通过相同的人员 ID 匹配。
- 匹配条件不限于字段值相等。例如，可以把交易记录与业务期间记录关联，判断交易时间是否位于对应期间的开始时间和结束时间之间。
- SQL 的 `JOIN` 可以直接提供关联结果，供同一条查询继续筛选、分组和聚合统计，不需要先创建并保存一张新的联合表。
- **数据关联**解决哪些记录存在对应关系、怎样把它们组合起来；**数据聚合**对记录进行计数、求和等汇总计算；**业务分析**再结合这些数据判断具体情况。关联后的数据可以用于联合分析，关联操作本身并不完成业务判断。

### 明细、关联结果和统计指标都可以成为结构化事实

| 结果类型 | 表达什么 | 例子 |
| --- | --- | --- |
| **明细** | 从原始案件数据中选出的具体记录及所需字段。 | 某笔交易的交易号、时间、金额和收付款账户。 |
| **关联结果** | 根据匹配条件组合相关记录后得到的信息。 | 将一笔交易与付款账户、账户所属人员的信息放在一起。 |
| **统计指标** | 对一组记录进行汇总计算得到的数值。 | 某人在指定时间段内的交易次数、累计金额。 |

这三类结果都可以按明确字段记录并保留来源，形成结构化事实。统计指标还需要说明统计对象、时间范围和计算口径，便于回查和核对。

它们不是每次都要依次经过的三个处理层级：明细和关联结果都可以直接用于后续分析；聚合统计既可以基于单表记录，也可以基于关联结果。

### 业务规则与判断条件的区别

- **业务规则（Rule）**：根据业务需求制定的完整判断逻辑，说明检查什么情况、满足哪些条件时产生什么结果。例如，统计某账户在指定时间内的交易次数，如果超过设定阈值，就生成一条候选风险疑点。
- **判断条件（Condition）**：规则中具体要检查的要求，例如“单笔交易金额超过设定阈值”或“指定时间内交易次数超过设定阈值”。

**两者的关系**：一条业务规则可以包含一个或多个判断条件，多个条件可以通过“与”“或”等逻辑组合。规则说明完整的判断逻辑及触发结果，条件说明其中具体需要满足的要求。

## 第一阶段：本条理解

这条工作的核心是：**先从案件数据中整理出相关事实，再通过业务规则通道和大模型分析通道发现候选风险疑点。随后规划并执行核查任务，对证据进行集中核验，判断疑点是否得到支持；证据不足时，再围绕缺口定向补证。**

下文“大模型”指大语言模型。两条通道分别提出疑点，汇总后共同进入任务规划、补证和核验。

要解决的主要问题有两个：

- **怎样准备大模型需要的信息。** 单案数据太多，不能全部交给大模型，需要围绕研判问题筛选、关联和统计数据，整理成带有来源的结构化事实，再组织成模型本轮需要的输入。
- **怎样根据事实作出有依据的风险判断。** 拿到局部事实后，还需要发现疑点、规划核查任务，通过补证查清所怀疑的行为或情形是否实际存在，并核对交易背景、资金用途、人员关系等信息。再由大模型综合支持和反驳疑点的证据，检查这些证据能否相互印证、证据链是否足以支持或排除疑点；仍有缺口时，明确记录证据不足。

### 先弄清数据从哪里来、里面有什么

我接入的是甲方已有平台整理并保存的案件数据，涉及人员、资金、通联和资产等信息。平台按不同业务场景及其对应的数据类别组织并保存这些数据，其中保留了大量明细，例如每笔交易的时间、金额和交易对手。

单个案件内，涉及多个人员，时间跨度也较大，人员、资金、通联和资产等各类数据的记录总数达到百万级。

我先结合甲方给出的业务含义说明和实际样本，弄清字段含义和记录之间的对应关系，再围绕当前研判问题执行预设的数据库查询（从数据库取得所需记录或计算结果），按需要完成以下处理：

- **筛选记录**（按人员、账户和时间范围等条件，选出需要分析的记录）。
- **关联记录**（依据人员标识、账号等字段的业务含义和匹配条件，把相关记录组合起来，供后续联合分析使用）。
- **聚合统计**（将多条记录汇总计算，例如按人员、交易对手或时间段分组，计算交易次数、累计金额等指标）。
- **整理结果**（将所需明细、关联结果或统计指标按明确字段记录，并保留来源，形成结构化事实）。

查询可以包含筛选、关联和聚合统计。筛选可以放在子查询中先做，也可以在关联后做；筛选位置会影响保留哪些记录，需要按查询目的安排。聚合是统计中常用的一种计算方式，这里合称“聚合统计”，不另拆成两个固定步骤。

### 第一步，用预先写好的查询和程序整理事实

例如，要分析某个人在一段时间内的资金往来，可以先查出相关账户和交易记录，再统计交易次数、累计金额，并保留对应记录的来源。

相关明细、关联结果或统计指标，按明确字段记录并保留来源后，就是**结构化事实**。它说明已经查到了什么、计算出了什么，后面可以据此分析，也可以回到原记录核对。

查询时采用的具体标准，就是简历中的“业务口径”。例如：

- 查哪个人、哪些账户、哪个时间段；
- 人员记录、账户记录和交易记录依据哪些字段、按什么条件关联（例如，按人员 ID 匹配人员表与账户表，再按银行账号关联交易记录）；
- 哪些交易计入统计，金额和次数怎样计算。

人员、资金等是业务数据类别，金额、交易对手等是记录中的字段。“关联”按已经确认的匹配条件组合相关记录；后续的联合分析再结合金额、时间、人员关系等信息，判断具体情况。

我根据案件数据结构和研判需求提出这些标准，再与甲方领域人员确认，落实到预设的参数化 SQL 和程序逻辑中。

“参数化 SQL”可以理解为：**查询结构预先写好，执行时再传入人员、账户和时间范围等具体参数。**

我先把预设 SQL 和相关处理逻辑封装成处理函数，由处理函数接收查询参数、执行 SQL，并整理返回结果。

**处理函数**是实际完成某项工具功能的函数。这里的查询分析工具用它查询和整理数据；其他工具的处理函数也可以负责计算或调用外部服务。

具体实现时，我将这些处理函数注册为工具：为每个工具定义名称、用途和参数格式，并在后端建立工具名称与处理函数的对应关系。调用大模型时，后端提供可用工具的说明，由模型根据任务选择工具并生成调用参数。

随后，后端检查工具是否允许调用、参数是否符合要求，再执行对应的处理函数，将结果返回给 Agent 继续处理。

在这些查询分析工具中，**SQL 负责查询数据，处理函数负责执行查询并整理结果，后端将处理函数注册为工具，供 Agent 调用。** 疑点发现和后续补证，都可以通过这些工具获取相关事实。

**工具调用机制连接模型发起的工具调用请求与后端处理函数的执行，完成请求检查、调用分发和结果返回。**

### 第二步，通过业务规则通道和大模型分析通道发现疑点

**业务规则通道**按照预先设定的业务规则（包含具体的判断逻辑和条件）筛查，发现值得进一步核查的疑点。例如，可以检查单笔交易金额、一定时间内的累计金额或交易次数是否超过设定阈值；也可以根据预先规定的账户关系、转账顺序和时间范围，检查是否存在特定资金流转链。

这些业务规则需要结合实际业务制定，并与甲方领域人员确认，包括判断条件怎样组合、阈值怎样设定。规则命中后，系统生成候选风险疑点，并关联触发规则的结构化事实。疑点和相关事实一起作为后续任务规划的输入。

**大模型分析通道**读取相关事实，把资金往来、交易时间、金额和人员关系等信息放在一起分析，提出需要进一步核查的疑点。

例如，查询结果显示 A 向 C、C 向 B 都发生过转账，时间和金额上存在值得关注的联系。模型可以提出：这两笔交易是否有关联？C 在其中承担什么角色？相关交易是否有正常业务依据？这些问题都需要后续查询验证。

两条通道的作用不同：**业务规则通道按照预先设定的判断逻辑和条件筛查；大模型分析通道结合多条事实进行分析，寻找现有规则可能漏掉的疑点。**

分批分析采用以下方案：围绕当前分析对象，先按单个人员或关联人员组归集相关事实，再在组内按业务数据类别整理，并结合时间范围和单批输入长度上限拆分。每批保留事实摘要、来源及相关人员和账户的标识，便于联系其他批次的结果。各批产生的疑点统一汇总，合并重复疑点并保留对应事实。

这里的“事实包”，就是把当前分析需要的结构化事实放在一起，包括所需明细、关联结果或统计指标及其来源。

### 第三步，把疑点和相关事实一起交给规划环节，安排核查任务

两条通道发现的疑点需要汇总。如果发现的是同一个问题，就需要合并重复内容，同时保留各自的依据。

一条疑点要讲清楚：怀疑什么、涉及哪些人、哪个时间段、根据哪些事实提出，以及还有什么没有查清。

规划时，把疑点、相关事实、可用工具说明和**任务输出规范（Schema）**交给大模型，让它按规定的字段生成核查任务，说明核查目标、涉及人员、时间范围、所需工具、任务依赖和完成条件。

任务输出规范规定输出包含哪些字段、字段采用什么类型，以及哪些字段必须填写。允许查询的人员、时间范围和可用工具等任务范围要求，也要提前告诉模型。模型提出计划后，后端检查输出结构、任务范围和依赖关系；执行时，再检查资源预算、并发上限和循环停止条件。

本文的**资源预算**指整次研判可使用的模型调用次数、工具调用次数和 Token 额度。并发上限和循环停止条件分别控制同时执行多少、何时停止，继续单独说明。

**疑点告诉模型要查清什么问题，事实告诉模型已经知道什么、还缺什么。** 因此，规划时仍然需要相关事实，不能只提供一句疑点描述。

一个疑点往往需要多项核查，部分任务还需要前面任务的结果。例如，要核查一组资金往来，可能需要先查出关联账户，再根据这些账户查询交易明细，同时安排人员关系核查。因此，需要先把要查的内容拆成具体任务，明确各项任务的目标、范围和依赖关系，再交给后端执行。

疑点和核查任务都按固定字段记录。疑点记录保存可疑问题、涉及人员、时间范围、已有事实及其来源，以及还缺少哪些证据；任务记录保存对应疑点、核查目标、查询范围、所需工具、依赖关系和完成条件。

疑点描述可以使用自然语言，固定字段便于后端检查、保存，并将任务结果与对应疑点联系起来。

疑点发现和任务规划也可以由同一个大模型完成，但两项工作的目标不同：前者提出值得查的问题，后者安排具体怎样查。

### 第四步，执行核查任务，对证据进行集中核验，再决定是否继续补证

后端检查任务和工具参数后，调用查询分析工具获取事实。相关任务完成后，后端汇总事实及其来源，交给大模型进行集中核验：根据证据判断所怀疑的行为或情形是否实际存在，再结合交易背景、资金用途、人员关系等信息，判断疑点是否得到支持、需要修正、可以排除，还是证据仍然不足。

例如，已经发现双方资金往来的金额或频次值得关注，但还不能判断交易是否正常，就继续查询双方关系、交易明细，以及能够获取的资金用途和业务背景。

集中核验发现证据不足时，先明确：**要对这个疑点作出判断，目前还缺哪些信息或证据，下一步怎样获取。** 再据此安排定向补证任务。

这就是“以核验结果驱动定向补证”：核验发现哪里还没有查清，下一步就围绕这个问题补充证据。

补证同时关注支持和反驳疑点的信息。查回的结果可能支持原来的疑点，也可能说明属于正常往来，或者仍然无法判断。没有查到业务依据，也不能直接当作违规的证据。

是否继续补证，需要分清两类条件：

| 需要考虑什么 | 具体含义 |
| --- | --- |
| **数据和工具能查到什么** | 现有数据是否包含所需信息，已有工具是否支持这项查询。缺少数据或工具能力时，需要记录限制，或者由开发者补充相应能力。 |
| **还允许继续查多少** | 后端按全案资源预算，分别限制模型调用总次数、工具调用总次数和 Token 用量，并检查循环停止条件。各阶段及后续补证共同使用全案预算，不能每轮重新计算一份额度。 |

已有依据足以作出判断时，就不需要重复补证。停止执行时，要分别说明**为什么停止、哪些核查已经完成，以及证据能否支持判断**。

- **资源预算不足以继续调用时，按预算停止。** 达到上限，或者剩余额度不足以满足下一次调用需要，都会阻止新增调用。这属于受限结束，不等于程序出错；如果仍有必要核查未完成，就记录已完成内容、未完成内容和证据缺口。
- **程序异常或依赖服务故障时，按异常处理。** 记录具体原因和受影响的任务，对调用方说明当前进度、结果是否可用及未完成部分，同时保留日志供开发者定位。

两者按停止原因区分，不能简单分成“面向使用者的失败”和“面向开发者的失败”。预算耗尽可能使部分核查未能完成，但它既不说明程序有缺陷，也不说明疑点成立或不成立。

**报告生成的设计建议：在全案资源预算内预留报告生成所需的模型调用次数和 Token 额度，补证不能占用这部分额度。** 停止补证后，报告整理已有结果并注明未完成事项和证据缺口；报告阶段仍有明确上限。报告已经生成、必要核查是否完成、证据是否充分，需要分别记录。

**核查任务完成，只说明安排的查询和检查已经执行，不等于疑点成立。** 最终判断仍然要根据查到的证据作出。

以上是这套研判策略与流程设计。任务之间怎样安排先后顺序、怎样通过异步调用支持并发，以及整体与局部的执行控制，见[任务编排](任务编排.md)。

### 第五步，分别评价疑点发现和最终输出的效果

评测以专家事先标出的风险事件为对照，按照同一套匹配规则，判断系统结果是否与标注对应。

| 指标 | 看什么 | 结果 |
| --- | --- | --- |
| **候选风险疑点召回率** | 专家标出的风险事件中，有多少已被候选风险疑点覆盖。此时不要求已经形成最终风险事件。 | 86.5%→92.4% |
| **最终风险事件精确率** | 系统最终报出的风险事件中，有多少与专家标出的事件对应得上。 | 81.0%→84.9% |
| **最终风险事件召回率** | 专家标出的风险事件中，有多少被系统最终正确找出。 | 85.0%→87.7% |

**基线流程**是本次比较预先选定的参照版本，例如已有方法或自己较早的实现。**改进流程**是本轮要评估的新版本，针对原有问题调整了分析方法、规则或流程。两者是同一次对照中的比较对象；新版本是否更好，由评测结果判断。

评测集使用脱敏案件和专家标注，按案件划分开发集、测试集。开发时用开发集比较版本、调整策略，方案确定后再用测试集检验效果。每次对照都固定参照版本，并保持评测案件、专家标注、匹配规则、候选列表统计位置、候选风险疑点上限和资源预算一致；不属于本轮改动的模型、提示词等配置也保持一致。

比较时既看识别质量，也记录实际资源消耗和任务完成情况，再回到具体案件分析误报与遗漏。相同资源预算指各项额度上限相同，实际调用次数和 Token 消耗可以不同。

这些结果说明，在这组评测条件下，整套流程漏掉的风险事件减少了，最终输出中正确识别的比例也提高了。

要判断业务规则通道、大模型分析通道或定向补证各自带来了多少改善，还需要在其他条件一致时，比较加入或去掉某项策略后的结果，也就是进行消融对照。

### 关于个人工作和 AI 的作用

在我负责的部分，我先明确业务需求，了解实际数据的结构和特点，以及技术与资源约束（如现有系统和工具的能力、部署要求、资源预算）。在此基础上设计整体研判方案，确定怎样发现疑点、怎样补证核验，以及各阶段怎样衔接。再编写 SQL、工具处理函数和流程代码完成实现，通过测试与评测检查结果。

整体研判方案包含分析与核验策略，也包含各阶段的处理流程。“策略”说明采用什么方法解决问题，“流程”说明各项工作怎样组织和衔接。

验证时分别关注**功能正确性、系统性能和结果质量**：程序是否按要求执行，完成任务需要多久、使用多少资源，以及识别结果是否正确、完整。测试与评测可以交叉，例如质量指标也可以用于回归检查。具体区别与 LangSmith 的作用，见[效果评测的前置学习知识](效果评测.md)。

开发时，我会借助 AI 分析问题、提出建议，再根据业务需求、实际数据和技术与资源约束，判断这些建议是否适用，并通过测试与评测决定采用、调整还是舍弃。涉及业务口径和判断标准的内容，与甲方领域人员确认。

开发时用 AI 帮助设计，与系统运行时用大模型分析案件，是两种不同的使用场景。

Q01-1. 数据来自哪里？为什么要先整理事实？

我先根据数据说明和样本，确认关联字段的业务含义和匹配条件。例如，通过表示同一人员 ID 的字段关联人员表与账户表，再按银行账号关联交易记录。字段名称不必相同，关键是能否按业务含义正确匹配；相关标准会请甲方领域人员确认。

Q02. “业务口径”是什么意思？怎样落实到 SQL？

考察重点：能否把业务要求变成明确的查询和统计标准。
回答顺序：口径是什么 → 举例说明 → 怎样确定并实现

答：业务口径就是查询数据时采用的筛选、关联和统计标准，也就是查哪些记录、怎样对应、怎样计算。

例如，统计某个人的交易次数，要先根据账户归属信息找到他的账户，再明确统计哪个时间段、哪些交易计入，以及按人员还是按交易对手分组计算。

我结合数据说明、实际样本和研判需求提出这些标准，与甲方领域人员确认后，再落实到参数化 SQL 和程序逻辑中。


Q02-1. SQL 和查询分析工具是什么关系？补证时怎样复用？

考察重点：是否清楚 SQL、处理函数、工具定义和调用机制各自做什么。
回答顺序：SQL 与处理函数 → 注册为工具 → 检查并执行调用请求 → 补证时复用

答：在查询分析工具中，SQL 负责查询数据，处理函数负责接收参数、执行查询并整理结果。“处理函数”指实际完成工具功能的函数，其他工具的处理函数也可以负责计算或调用外部服务。

我把预设 SQL 和结果处理逻辑封装成处理函数，再将处理函数注册为工具，为每个工具定义名称、用途和参数格式，并在后端建立工具名称与处理函数的对应关系。

调用大模型时，后端提供工具说明，由模型选择工具并生成参数。后端检查工具是否允许调用、参数是否符合要求，再执行对应的处理函数并返回结果。工具调用机制就这样连接模型发起的请求与后端处理函数的执行，完成请求检查、调用分发和结果返回。

疑点发现和补证可以复用这些工具，补证时围绕具体缺口指定人员、账户和时间范围；需要扩展查询能力时，由开发者补充或调整工具。


Q03. 业务规则是怎样确定和实现的？

考察重点：能否区分业务规则与判断条件，说明规则的业务依据和输出。
回答顺序：怎样制定并确认规则 → 用例子区分规则与条件 → 怎样实现 → 疑点与事实交给谁

答：我先结合现有数据和研判需求制定业务规则，明确检查什么、采用哪些判断条件、条件怎样组合，以及满足后输出什么，再与甲方领域人员确认。

例如，统计某账户在指定时间内的交易次数，超过设定阈值时生成疑点。这是一条完整规则，“交易次数超过阈值”是其中的判断条件。规则确定后，用 SQL 或程序实现，并验证结果。

业务规则通道按这些规则筛查。规则命中后，系统生成候选风险疑点，并关联触发规则的结构化事实，二者一起交给后续任务规划。规则命中本身不代表已经存在违规行为。


Q03-1. 大模型分析通道怎样发现疑点？输出什么？

考察重点：模型根据什么提出问题，结果怎样交给后续使用。
回答顺序：读取什么 → 怎样分析 → 输出什么

答：大模型分析通道读取相关事实摘要，把资金往来、交易时间、金额和人员关系等信息放在一起分析，提出需要进一步核查的疑点。

例如，查询结果中既有 A 向 C 的转账，也有 C 向 B 的转账，时间和金额上存在值得关注的联系。模型可以提出，这些交易是否有关联、C 在其中承担什么角色，以及是否有正常业务依据。

输出时，用自然语言说明可疑问题，同时记录涉及人员、时间范围、已有事实及其来源，以及还缺少哪些证据。疑点和相关事实一起供后续任务规划使用。


Q03-2. 结构化事实、候选风险疑点和最终风险事件有什么区别？

考察重点：能否分清查到的信息、待核查的问题和有证据支持的风险判断。
回答顺序：事实是什么 → 据此提出什么疑点 → 核验具体查什么 → 怎样形成最终输出

答：结构化事实来自对原始案件数据的查询，以及按需要进行的筛选、关联或聚合统计。它按明确字段记录明细、关联结果或统计指标，并保留来源，说明已经查到了什么、计算出了什么。

候选风险疑点说明根据这些事实，还有什么风险问题需要查清；最终风险事件则是补证核验后，系统认为有证据支持的风险行为或情形。

例如，“某段时间内存在多笔转账”是事实，“这些转账是否缺乏正常业务依据”是疑点。核验时要查清所怀疑的行为或情形是否实际存在，核对交易背景、资金用途、人员关系等信息，再结合支持和反驳疑点的证据，判断相应风险是否有依据。

查询和统计工具提供事实，大模型负责综合这些事实进行分析与核验。有证据支持的风险判断才进入最终输出；疑点被排除或证据仍不足的，分别记录。


Q03-3. 业务规则通道和大模型分析通道怎样互补？事实怎样分批输入模型？

考察重点：为什么使用两条通道，以及分批分析怎样组织。
回答顺序：各自的作用 → 按什么分批 → 怎样汇总结果 → 怎样验证效果

答：业务规则通道按照预先设定的判断逻辑和条件筛查；大模型分析通道结合多条事实进行分析，寻找现有规则可能漏掉的疑点。

分批方案是先按单个人员或关联人员组归集事实，再在组内按业务数据类别整理，并结合时间范围和单批输入长度上限拆分。每批保留事实摘要、来源及相关人员和账户的标识，便于联系其他批次的结果。

各批产生的疑点统一汇总，合并重复疑点并保留对应事实。实际多发现了多少问题，需要在相同候选风险疑点上限和资源预算下评测，再通过消融对照判断两条通道各自的作用。


Q03-4. 这些方案是你自己做的吗？你怎样使用 AI？

考察重点：个人贡献是否清楚，是否能够判断和验证 AI 的建议。
回答顺序：我的职责 → AI 怎样辅助 → 怎样判断适用性 → 业务确认与最终责任

答：在我负责的部分，整体研判方案、流程实现和测试验证由我完成。开发过程中，我会借助 AI 分析问题、提出建议。

我根据业务需求、实际数据和技术与资源约束，检查建议的依据是否合理、数据是否满足使用前提、现有系统和工具是否支持，再通过测试与评测决定采用、调整还是舍弃。

涉及业务口径和判断标准的内容，与甲方领域人员确认；最终采用什么方案、代码是否符合要求、验证结果怎样，由我负责。


Q03-5. 发现疑点后为什么还要规划任务？规划时输入什么、输出什么？

考察重点：是否清楚规划的必要性，以及疑点、事实和任务怎样衔接。
回答顺序：为什么需要规划 → 提供哪些信息 → 按什么规范输出 → 后端怎样检查

答：一个疑点往往需要多项核查，部分任务还要使用前面任务的结果。例如，先查出关联账户，才能据此查询交易明细，因此需要先拆分任务、明确依赖关系。

规划时，把疑点、相关事实、可用工具说明和任务输出规范（Schema）交给大模型。事实帮助它知道已经查到了什么、还缺什么；Schema 规定任务包含哪些字段、字段类型和必填要求。

模型据此生成核查任务，说明对应疑点、核查目标、涉及人员、时间范围、所需工具、依赖关系和完成条件。后端检查输出结构、任务范围和依赖关系，再按资源预算等限制执行。


Q04. 定向补证具体怎么做？怎样决定是否继续？

考察重点：怎样补齐判断依据，以及怎样区分预算停止、核查未完成和异常。
回答顺序：明确还缺什么 → 补证与大模型核验 → 判断是否继续 → 记录停止原因和结果

答：定向补证就是在集中核验发现证据不足时，先明确要对疑点作出判断还缺哪些证据、下一步怎样获取，再针对缺口安排查询。

例如，双方资金往来的金额或频次值得关注，但还不能判断是否正常，就继续查询双方关系、交易明细，以及能够获取的资金用途和业务背景。查回的事实交给大模型再次核验，同时查看支持和反驳疑点的信息。

后端根据证据缺口、数据和工具能力、全案资源预算及循环停止条件，决定是否继续。预算不足时停止新增调用，记录受限原因、已完成内容和未完成部分；这不等于程序出错。程序异常或依赖服务故障则记录具体原因和受影响任务，向调用方说明结果是否可用，并保留日志供定位。

为在停止补证后仍能整理报告，设计上建议在全案预算内预留有上限的报告生成额度。报告说明已有结果和证据缺口；报告生成不代表核查已经全部完成，也不代表疑点已经得到证据支持。


Q04-1. 核查任务完成，就说明疑点成立了吗？

考察重点：能否分清任务完成和风险判断。
回答顺序：直接回答 → 举例说明 → 解释最终怎样判断

答：不能。任务完成只说明安排的查询和检查已经执行，是否有依据支持疑点还要根据取得的事实判断。

例如，“这些转账是否缺乏正常业务依据”是疑点，“查询交易明细并核对双方关系”是核查任务。即使查询成功，也可能发现这些交易属于正常往来，或者现有信息仍然不足。

因此，一个疑点可能需要多项任务。大模型结合相关事实进行集中核验后，有证据支持的风险情形才作为最终风险事件输出。


Q05. 怎样比较基线与改进流程？评测结果说明了什么？

考察重点：是否理解比较对象、对照条件和指标的含义。
回答顺序：比较哪些版本 → 固定哪些条件 → 指标含义与结果 → 怎样判断改动的效果

答：基线流程是预先选定的参照版本，改进流程是调整分析方法、规则或流程后的待评估版本。用同一套标准比较两者，才能判断改动是否改善了效果。

我用脱敏案件和专家标注构建评测集，按案件划分开发集、测试集。对照时使用同一批评测案件、标注和匹配规则，在同一流程位置统计候选疑点，并保持候选风险疑点上限与资源预算一致。这里的资源预算分别限制模型调用次数、工具调用次数和 Token 用量，同时记录实际消耗。

候选风险疑点召回率，看专家标出的风险事件中，有多少已在系统提出的疑点中得到覆盖，从 86.5% 提升到 92.4%。

最终精确率，看系统最终报出的事件中，有多少与专家标注对应得上，从 81.0% 提升到 84.9%；最终召回率，看专家标出的事件中，有多少被系统最终正确找出，从 85.0% 提升到 87.7%。

这些结果说明，整套流程在这组评测条件下改善了识别效果。还要结合实际消耗、任务完成情况和误报、遗漏案例，判断改动的收益与代价；单个环节的贡献通过消融对照分析。

## 已采用的简历措辞

简历正文与本文统一为：

> **通过业务规则与大模型分析两条通道发现候选风险疑点。**

两条通道说明怎样发现问题，“候选风险疑点”说明发现的是什么。补证核验后，有证据支持的风险判断才纳入最终风险事件。评测段相应使用“候选风险疑点上限”和“候选风险疑点召回率”。

事实、疑点和核验结论按含义区分，不按是否采用结构化格式区分。源码标识与业务名称的对照统一放在[效果评测](效果评测.md)中，不增加另一套业务概念。

### 预算停止的实现对照

当前[任务调度器](../../项目源码/案件研判/src/case_task_scheduler.py)在预算不足时抛出 `BudgetLimitExceeded`；核查任务内发生的预算超限仍会被记录为通用的 `failed`，并保留这个原因。因此，不能只凭 `failed` 判断发生了程序错误。规划、核验和汇总的模型调用共用同一预算检查入口。[主图](../../项目源码/案件研判/src/case_workflow_graph.py)会根据执行状态记录整次运行结果，报告保存与运行成功也不是同一件事。上述报告专用额度预留属于设计建议，现有代码尚未单独实现这项预留。
