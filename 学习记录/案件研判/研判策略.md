# 案件研判｜研判策略

## 简历条目

> **研判策略：**按业务口径**预设参数化 SQL**，筛选聚合百万级案件记录，形成结构化事实；结合风险识别规则与模型线索生成候选，以核验结果驱动**定向补证**；对照基线流程，最终风险事件：**精确率 81.0%→84.9%**，**召回率 85.0%→87.7%**。

> 本条理解状态：已确认（按用户要求同步本轮确认的数据介绍、工具、候选通道与 AI 辅助口径）。

## 第一阶段：本条理解

这条工作的核心是：从甲方已有平台提供的案件数据中整理事实，通过规则与大语言模型发现值得排查的候选，再通过补证和核验，判断现有证据能否支持这些候选。

### 数据背景与统一称呼

我接入的是**甲方已有平台按业务主题组织并保存的案件数据**，涉及人员、资金、资产和通联等信息。各类数据的业务说明与字段信息，帮助我理解记录的含义、对象之间的关联，以及可以分析哪些问题。

这些数据仍保留大量细粒度记录，涉及人员较多、时间跨度较大，整体达到百万级。不能将全部记录直接放入大语言模型上下文，需要先围绕研判需求进行筛选、关联和统计，再将结果整理为结构化事实。

“按业务主题组织”说明数据的组织方式，不等于采用了机器学习聚类，也不说明上游只做过分类或筛选。现阶段确认的是仍保留大量细粒度记录，不把全部输入一概称为未经处理的原始明细。“人员、资金、资产和通联”概括数据领域，不代表平台恰好分成四个互斥类别；正式分类及其层级仍需核对原始配置。

“百万级”说明项目处理的案件记录规模，不代表每个案件、每类数据都达到百万条，也不代表全部记录都会进入大语言模型上下文。

### 关键做法与因果

1. **先理解数据，再用查询分析工具整理事实。**

   我先结合数据说明和实际样本，确认字段含义和关联关系，再针对不同业务数据的特点，通过预设的参数化 SQL 和相应程序逻辑完成筛选、关联和统计，形成结构化事实。

   例如，仅用于说明机制：按人员、账户和时间范围查找记录，统计交易次数、累计金额，或者整理资金往来关系。查到的记录和统计结果按明确字段组织，并保留来源，供后续分析与核对。

   这些 SQL 和程序逻辑被封装为**可调用的查询分析工具**。工具是可调用的程序入口，内部执行预设 SQL 和相应程序逻辑；不是将一段 SQL 文本直接当作工具。

   查询、关联和统计时采用的具体标准，就是简历中所说的“业务口径”。我结合案件数据结构与研判需求提出方案，涉及业务合理性的关联方式、统计口径和风险识别条件，在实际采用前与甲方领域专业人员确认。沟通确认是形成标准的过程，“口径”本身指确定后的标准。

2. **规则筛查与大语言模型分析共同生成风险事件候选。**

   风险识别规则把值得关注的情况写成明确条件，再由 SQL 或程序检查哪些记录、对象或关系符合条件。例如，单笔交易金额、一定时间内的累计交易金额或交易次数超过设定阈值。这些是机制示例，不代表已经确认的具体阈值。

   大语言模型综合资金往来、时间和人员关系等事实，提出待核查的候选线索。例如，仅用于说明机制：结合 A 经多个中间账户向 B 转款的路径与相关人员关系，提出中间人是否在代为转款、B 是否为实际受益人等疑点。

   资金路径由查询或程序计算得到，大语言模型结合路径与其他事实提出待核查的解释。多跳路径本身也可以由确定性程序识别，不能将它描述为大语言模型独有的能力；存在这条路径也不等于已经证实风险。

   规则依据明确条件筛查，大语言模型补充可能未被现有规则覆盖的候选线索，两者结合的目的是减少候选遗漏。互补效果取决于输入信息：如果大语言模型只看到规则命中的候选，它发现其他线索的范围就会受到限制。

   **事实说明“查到了什么”，候选说明“哪些情况值得继续查”。**规则命中或大语言模型提出疑点，都需要后续查证。查询统计与风险识别按用途区分，部分风险规则也可以用 SQL 实现。

   开发时，我会借助 AI 辅助梳理可选的分析方法、处理策略和风险识别规则的设计思路，再结合需求与约束判断其前提、逻辑和适用性，通过实际验证决定采用、修改还是舍弃。涉及业务标准的部分与甲方领域专业人员确认。开发时用 AI 辅助设计，与系统运行时用大语言模型分析当前案件，是两个不同的使用环节。

3. **复用查询分析工具，围绕证据缺口定向补查。**

   候选形成后，先围绕疑点补查相关信息，再集中检查证据能否支持候选。如果仍缺少影响判断的关键依据，就根据具体缺口进一步限定人员、账户和时间范围等参数，调用查询分析工具补查后再次核验。

   例如，仅用于说明机制：已经查到双方资金往来，但判断还需要双方关系信息，就针对相关主体补查关系数据。“定向”就是围绕当前缺少的依据，决定查谁、查什么、查哪个时间范围。

   候选生成和补证阶段统一使用“查询分析工具”这一称呼，不另设两套粗、细粒度工具的表述。补证时参数更具体，表示查询对象和范围更聚焦；前期查询和统计得到的仍然是明确结果，并非模糊估计。实际能否完成某项补查，取决于现有数据与工具能力；新的需求可能需要补充或调整查询模板。

   补回的信息可能支持候选，也可能使候选被修正或排除。证据仍然不足时，就不能把候选当作已经证实的结论。

4. **用最终事件的评测结果判断整体效果。**

   这里评价的是补证、核验后最终输出的风险事件。精确率从 81.0% 提升到 84.9%，表示输出事件中符合标注标准的比例提高；召回率从 85.0% 提升到 87.7%，表示标注事件中被系统正确识别的比例提高。

   在统一评测标准和可比条件下，这说明整套流程相较基线改善了最终识别质量。这两个数不能代替候选阶段的召回率，也不能单独证明某个环节的贡献。要判断某项策略的贡献，需要在其他条件一致时，比较加入或去掉这项策略后的结果。

理解主线：理解数据与研判需求 → 查询分析工具整理事实 → 规则与大语言模型生成候选 → 补证后核验 → 围绕缺口复用工具补查 → 评测最终事件质量。涉及业务合理性的标准在实际采用前由甲方领域专业人员确认。

### 工程用词与责任范围

“方案设计”是一项工作，“技术方案”通常指这项工作形成的内容；“技术路线”强调其中的主要实现路径，不等于代码实现。方案设计可以具体到架构、选型与实现设计，不限于大致的思想和策略。

| 表达 | 主要说明什么 |
| --- | --- |
| 需求与约束分析 | 要解决什么问题，目标、范围、输入输出和限制是什么。 |
| 方案设计 | 准备采用什么流程、方法和策略解决问题。 |
| 架构设计 | 各模块负责什么，怎样协作，数据怎样流转。 |
| 技术路线与选型 | 采用怎样的实现路径和技术组合；具体选择哪些框架、数据库等组件。 |
| 代码实现 | 编写 SQL、程序、接口和工具，将设计落实为可执行功能。 |
| 测试与效果验证 | 检查实现是否符合要求，以及效果是否达到预期。 |

这些工作会相互影响和调整，不必理解为严格串行的阶段。在自己承担的工作范围内，我负责需求与约束分析、方案设计、技术选型、代码实现和测试验证，并对最终的方案选择、实现质量和验证结果负责；涉及业务标准的内容由甲方领域专业人员确认。

答：业务口径就是查询、筛选和统计数据时采用的具体标准，通俗地说，就是明确要查什么、怎样关联、怎么算。

在项目中，我结合数据说明和实际样本，确认字段含义和关联关系，再根据研判需求设计取数范围、关联方式和统计口径。

这些涉及业务合理性的标准会在实际采用前与甲方领域专业人员确认，并落实到预设的参数化 SQL 和相应程序逻辑中。“口径”强调标准本身，沟通确认是形成标准的过程。


Q02-1. 为什么采用预设参数化 SQL？怎样将它用于查询和补证？

答：主要是为了让查询逻辑可检查、可复用，并让后续分析建立在明确的查询结果上。

我预先写好 SQL 的查询结构和统计逻辑，与相应程序逻辑一起封装为查询分析工具。执行时传入人员、账户和时间范围等参数，由数据库和程序完成筛选、关联与统计，大语言模型不需要临时生成 SQL。

候选生成和补证阶段统一使用这类工具。补证时根据具体证据缺口进一步限定参数，使查询范围更聚焦；前期统计结果仍然是明确结果，不是模糊估计。

它的局限是查询能力受已有模板和数据约束，新的分析需求可能需要补充或调整模板。


Q03. 风险识别规则是什么？这些规则是怎样确定并实现的？

答：风险识别规则就是把业务上值得排查的情况写成明确条件，再用 SQL 或程序逻辑筛选候选事件。例如，单笔交易金额、一定时间内的累计交易金额或交易次数超过设定阈值。这些是机制示例，具体阈值需要结合实际业务确认。

我根据可用数据和研判需求提出规则设计思路，借助 AI 辅助梳理可选方法，再结合需求与约束审查和验证这些建议。

涉及业务合理性与具体标准的部分，会与甲方领域专业人员确认，再由我落实为规则判断逻辑并验证结果。

存在 A→B→C 的资金路径只说明查到了一项关系；是否值得列为风险候选，还需要结合时间、方向、金额和人员关系等条件判断。


Q03-1. “模型线索”是什么意思？为什么需要它补充风险识别规则？

答：简历中的“模型线索”指大语言模型综合多条案件事实后，提出的待核查候选线索。

例如，仅用于说明机制：结合 A 经多个中间账户向 B 转款的路径与相关人员关系，提出中间人是否在代为转款、B 是否为实际受益人等疑点。资金路径由查询或程序计算得到，大语言模型在此基础上结合其他事实提出待核查的解释。

规则按预先确定的条件检查，依据明确、便于复核，但覆盖范围受已有条件限制。大语言模型可以补充可能未被现有规则覆盖的候选线索，同时也可能产生缺乏证据支持的推断。因此，两路输出都需要后续补证和核验。

这里还有两个不同的 AI 使用环节：开发时，AI 辅助我设计和实现；系统运行时，大语言模型分析当前案件并提出候选线索。


Q03-2. “事实包”是什么？面试中可以换成什么表达？

答：这里的“事实包”指把查询到的记录、统计结果和来源信息组织起来，供后续分析使用的数据。

例如，仅作结构说明：某个主体在一段时间内的交易次数、合计金额，以及这些结果对应的数据来源。

面试中可以直接说“初步整理的案件事实”；需要强调数据形式时，可以说“结构化事实”，不必把“事实包”当作一个必须掌握的技术名词。

还要区分查到或计算出的内容与大语言模型的推测，避免把待核查的关联写成已知事实。


Q03-3. 两条候选通道怎样互补？能保证不漏掉重要线索吗？

答：两条通道都基于整理后的案件事实提供候选，规则负责按明确条件筛查，大语言模型综合多条事实提出待核查的候选线索，目的是减少候选阶段的遗漏。

互补能发挥多少作用，还取决于输入范围。如果大语言模型只看到规则命中的候选，它发现其他线索的范围就会受到限制。要扩大覆盖，还需要提供与研判相关、但未触发规则的事实。

两路结合也不能保证不漏。上游缺少数据，或者整理事实时遗漏了关键关系，两路都可能受到影响。

实际效果需要在相同候选上限和调用预算下评测；要判断大语言模型或规则分别贡献了多少，还需要结合消融对照。


Q03-4. 这些方法和规则是你自己设计的吗？你怎样使用 AI 并对结果负责？

答：我负责结合实际数据和研判需求设计方案，过程中会借助 AI 辅助梳理可选的分析方法、处理策略和风险识别规则的设计思路。

对这些建议，我会结合需求与约束，判断其前提是否成立、推理是否合理，以及是否适用于当前问题，再通过实际验证决定采用、修改还是舍弃。涉及业务标准的部分，会与甲方领域专业人员确认。

在我承担的工作范围内，我负责需求与约束分析、方案设计、技术选型、代码实现和测试验证，并对最终的方案选择、实现质量和验证结果负责。


Q04. “以核验结果驱动定向补证”具体是什么意思？

答：就是把核验发现的证据缺口，转成有明确对象和范围的补查任务，再复用查询分析工具获取所需信息。

例如，仅作机制说明：已经查到双方资金往来，但判断还需要双方关系信息，就针对相关主体补查关系数据。查谁、查什么、查哪个时间范围，都由当前缺口决定，并通过相应工具参数限定。

补回的信息再用于核验。它可能支持候选，也可能使候选被修正或排除；如果证据仍然不足，就不能确认候选成立。


Q05. 这两个指标怎样评测？能说明哪些效果？

答：评价对象是补证和核验后的最终风险事件，以专家标注为参照。精确率看输出事件中有多少正确匹配标注，召回率看标注事件中有多少被正确识别。

我基于脱敏案件和专家标注构建事件级评测集，按案件划分开发集和测试集。在测试集上使用统一的事件匹配规则，并在相同候选上限和调用预算下比较基线与改进流程。

最终风险事件的精确率从 81.0% 提升到 84.9%，召回率从 85.0% 提升到 87.7%，说明整套流程在这组评测条件下改善了最终识别质量。

这里的召回率属于最终事件阶段，不能代替候选召回率；整体指标也不能单独证明规则、大语言模型或定向补证各自的贡献。
