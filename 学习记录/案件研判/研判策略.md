# 案件研判｜研判策略

## 统一术语

| 名称 | 含义 |
| --- | --- |
| **待核查疑点** | 根据已有事实提出、需要进一步查清的涉嫌违规违纪问题。要说明涉及哪些人、哪段时间，以及什么行为值得核查。 |
| **核查任务** | 为查清疑点而安排的具体工作，例如查询交易明细、核对双方关系和交易背景。 |
| **最终风险事件** | 经过补证和核验，系统认为已有依据支持，并纳入最终报告的具体风险情形。需要说明涉及哪些人、哪段时间、发生了什么，以及判断依据是什么。 |

例如，查到“A 与 B 在某段时间内存在多笔转账，交易频次达到筛查条件”，这是**已经查到的事实**。

根据这些事实提出“这些转账是否缺乏正常业务依据”，这是**待核查疑点**。

接下来安排“查询交易明细，核对双方关系和资金用途”，这是**核查任务**。

任务执行完成后，还要对证据进行集中核验。只有系统认为已有依据支持的风险情形，才会作为**最终风险事件**输出。疑点被排除，或者证据仍然不足，都需要分别记录。

疑点可以写成一个问题，也可以写成“可能存在某种风险，需要进一步核查”。

这里的“最终”指本次系统流程的输出阶段。这些风险判断仍可能有误报和漏报，需要由人工复核，并与专家标注进行评测对照。

> 本条理解状态：已确认。按用户确认的表达要求和补充事实更新。文中的例子用于解释机制。

## 第一阶段：本条理解

这条工作的核心是：**先从案件数据中整理出相关事实，再通过业务规则通道和大模型分析通道发现待核查疑点。随后规划并执行核查任务，对证据进行集中核验，判断疑点是否得到支持；证据不足时，再围绕缺口定向补证。**

下文“大模型”指大语言模型。业务规则通道和大模型分析通道是发现疑点的两条通道，之后共同进入任务规划、补证和核验。这里的业务规则用于发现风险疑点；“风险疑点”仍是待核查的问题，不等于已经确认的风险事件。

要解决的主要问题有两个：一是数据太多，不能全部交给大模型；二是发现可疑情况后，还需要继续核查，才能判断它是正常往来，还是存在违规违纪风险。

### 先弄清数据从哪里来、里面有什么

我接入的是甲方已有平台整理并保存的案件数据，涉及人员、资金、通联和资产等信息。平台按不同业务场景及其对应的数据类别组织并保存这些数据，其中保留了大量明细，例如每笔交易的时间、金额和交易对手。

单个案件内，人员、资金、通联和资产等各类数据的记录总数达到百万级，涉及多个人员，时间跨度也较大。

我先结合数据说明和实际样本，弄清字段含义和记录之间的对应关系，再围绕当前研判问题执行预设的数据库查询（从数据库取得所需记录或计算结果），按需要完成以下处理：

- **筛选记录**（按案件、人员、账户和时间范围等条件，选出需要分析的记录）。
- **关联记录**（依据人员标识、账号等字段及已有的对应关系，把相关记录连接起来）。
- **聚合统计**（将多条记录汇总计算，例如按人员、交易对手或时间段分组，计算交易次数、累计金额等指标）。
- **整理结果**（将相关明细、关联结果和统计指标整理成结构化事实，并保留来源）。

查询可以包含筛选、关联和聚合统计。筛选可以放在子查询中先做，也可以在关联后做；筛选位置会影响保留哪些记录，需要按查询目的安排。聚合是统计中常用的一种计算方式，这里合称“聚合统计”，不另拆成两个固定步骤。

### 第一步，用预先写好的查询和程序整理事实

例如，要分析某个人在一段时间内的资金往来，可以先查出相关账户和交易记录，再统计交易次数、累计金额，并保留对应记录的来源。

把这些结果按照明确字段记录下来，就是**结构化事实**。它说明已经查到了什么、计算出了什么，后面可以据此分析，也可以回到原记录核对。

查询时采用的具体标准，就是简历中的“业务口径”。例如：

- 查哪个人、哪些账户、哪个时间段；
- 人员记录、账户记录和交易记录依据哪些字段建立对应关系（例如，依据人员标识和账户归属信息确定账户属于谁，再按账号连接对应的交易记录）；
- 哪些交易计入统计，金额和次数怎样计算。

人员、资金等是业务数据类别，金额、交易对手等是记录中的字段。这里的“关联”是先找出记录之间的对应关系，再把相关记录中的金额、时间和人员关系等信息放在一起分析。

我根据案件数据结构和研判需求提出这些标准，再与甲方领域人员确认，落实到预设的参数化 SQL 和程序逻辑中。

“参数化 SQL”可以理解为：**查询结构预先写好，执行时再传入人员、账户和时间范围等具体参数。**

我先把预设 SQL 和相关处理逻辑封装成函数，由函数接收查询参数、执行 SQL，并整理返回结果。

然后，为这项功能定义工具名称、用途和参数格式，并在后端注册工具名称与处理函数的对应关系。调用大模型时，后端提供可用工具的说明，让模型知道可以调用什么、需要传入哪些参数。

执行时，大模型提出工具调用请求，给出工具名称和参数；后端检查工具是否允许使用、参数是否符合要求，再找到对应函数执行，将结果交给 Agent 继续处理。

**SQL 是查询语句，函数实现具体处理，查询分析工具把这项能力提供给 Agent 调用。工具调用机制连接模型的调用请求与后端的函数执行，完成请求检查、调用分发和结果返回。** 疑点发现和后续补证，都可以使用这些工具。

### 第二步，通过业务规则通道和大模型分析通道发现疑点

**业务规则通道**按照预先确定的条件筛查。例如，检查单笔金额、一定时间内的累计金额或交易次数是否超过设定阈值。

这些条件需要结合实际业务确定，并与甲方领域人员确认。业务规则命中后，系统生成待核查疑点，并关联触发该规则的事实。疑点和相关事实一起作为后续任务规划的输入。

**大模型分析通道**读取相关事实，把资金往来、交易时间、金额和人员关系等信息放在一起分析，提出需要进一步核查的疑点。

例如，查询结果显示 A 向 C、C 向 B 都发生过转账，时间和金额上存在值得关注的联系。模型可以提出：这两笔交易是否有关联？C 在其中承担什么角色？相关交易是否有正常业务依据？这些问题都需要后续查询验证。

两条通道的作用不同：**业务规则按照预先确定的条件筛查；大模型把多条事实放在一起分析，寻找现有规则可能漏掉的疑点。**

分批分析采用以下方案：围绕当前分析对象，先按单个人员或关联人员组归集相关事实，再在组内按业务数据类别整理，并结合时间范围和单批输入长度上限拆分。每批保留事实摘要、来源及相关人员和账户的标识，便于联系其他批次的结果。各批产生的疑点统一汇总，合并重复疑点并保留对应事实。

这里的“事实包”，就是把相关查询结果、统计结果和来源放在一起，供后续分析使用。

### 第三步，把疑点和相关事实一起交给规划环节，安排核查任务

两条通道发现的疑点需要汇总。如果发现的是同一个问题，就需要合并重复内容，同时保留各自的依据。

一条疑点要讲清楚：怀疑什么、涉及哪些人、哪个时间段、根据哪些事实提出，以及还有什么没有查清。

规划时，把疑点、相关事实、可用工具说明和**任务输出规范（Schema）**交给大模型，让它按规定的字段生成核查任务，说明核查目标、涉及人员、时间范围、所需工具、任务依赖和完成条件。

任务输出规范规定输出包含哪些字段、字段采用什么类型，以及哪些字段必须填写。允许查询的人员、时间范围和可用工具等任务范围要求，也要提前告诉模型。模型提出计划后，后端检查输出结构、任务范围和依赖关系；执行时，再检查调用预算、并发上限和循环停止条件。

**疑点告诉模型要查清什么问题，事实告诉模型已经知道什么、还缺什么。** 因此，规划时仍然需要相关事实，不能只提供一句疑点描述。

一个疑点往往需要多项核查，部分任务还需要前面任务的结果。例如，要核查一组资金往来，可能需要先查出关联账户，再根据这些账户查询交易明细，同时安排人员关系核查。因此，需要先把要查的内容拆成具体任务，明确各项任务的目标、范围和依赖关系，再交给后端执行。

疑点和核查任务都按固定字段记录。疑点记录保存可疑问题、涉及人员、时间范围、已有事实及其来源，以及还缺少哪些证据；任务记录保存对应疑点、核查目标、查询范围、所需工具、依赖关系和完成条件。

疑点描述可以使用自然语言，固定字段便于后端检查、保存，并将任务结果与对应疑点联系起来。

疑点发现和任务规划也可以由同一个大模型完成，但两项工作的目标不同：前者提出值得查的问题，后者安排具体怎样查。

### 第四步，执行核查任务，对证据进行集中核验，再决定是否继续补证

后端检查任务和工具参数后，调用查询分析工具获取信息。相关任务完成后，把查到的证据放在一起，判断疑点是否得到支持、需要修正、可以排除，还是证据仍然不足。

例如，已经发现双方资金往来的金额或频次值得关注，但还不能判断交易是否正常，就继续查询双方关系、交易明细，以及能够获取的资金用途和业务背景。

集中核验发现证据不足时，先明确：**要对这个疑点作出判断，目前还缺哪些信息或证据，下一步怎样获取。** 再据此安排定向补证任务。

这就是“以核验结果驱动定向补证”：核验发现哪里还没有查清，下一步就围绕这个问题补充证据。

补证同时关注支持和反驳疑点的信息。查回的结果可能支持原来的疑点，也可能说明属于正常往来，或者仍然无法判断。没有查到业务依据，也不能直接当作违规的证据。

是否继续补证，需要分清两类条件：

| 需要考虑什么 | 具体含义 |
| --- | --- |
| **数据和工具能查到什么** | 现有数据是否包含所需信息，已有工具是否支持这项查询。缺少数据或工具能力时，需要记录限制，或者由开发者补充相应能力。 |
| **还允许继续查多少** | 分别限制整次研判的模型调用总次数、工具调用总次数和 Token 用量，并检查循环停止条件。各任务和后续补证共同使用全案预算，不能每轮重新计算一份额度。 |

已有依据足以作出判断时，就不需要重复补证。证据仍然不足，但已经达到执行上限时，应停止继续尝试，并说明哪些问题尚未查清。如果调用被预算限制拒绝或程序执行失败，还要记录相应的失败状态。

**核查任务完成，只说明安排的查询和检查已经执行，不等于疑点成立。** 最终判断仍然要根据查到的证据作出。

以上是这套研判策略与流程设计。任务之间怎样安排先后顺序、怎样通过异步调用支持并发，以及整体与局部的执行控制，见[任务编排](任务编排.md)。

### 第五步，分别评价疑点发现和最终输出的效果

评测以专家事先标出的风险事件为对照，按照同一套匹配规则，判断系统结果是否与标注对应。

| 指标 | 看什么 | 结果 |
| --- | --- | --- |
| **疑点阶段召回率** | 专家标出的风险事件中，有多少在疑点发现阶段就被系统提出。此时还不要求完成核验。 | 86.5%→92.4% |
| **最终风险事件精确率** | 系统最终报出的风险事件中，有多少与专家标出的事件对应得上。 | 81.0%→84.9% |
| **最终风险事件召回率** | 专家标出的风险事件中，有多少被系统最终正确找出。 | 85.0%→87.7% |

评测集使用脱敏案件和专家标注，按案件划分开发集、测试集。比较基线和改进流程时，要保持疑点数量上限、调用预算等条件一致。

这些结果说明，在这组评测条件下，整套流程漏掉的风险事件减少了，最终输出中正确识别的比例也提高了。

要判断业务规则通道、大模型分析通道或定向补证各自带来了多少改善，还需要在其他条件一致时，比较加入或去掉某项策略后的结果，也就是进行消融对照。

### 关于个人工作和 AI 的作用

在我负责的部分，我先明确业务需求，结合实际数据的结构和特点，以及可用工具和资源预算，设计研判流程；再编写 SQL、工具函数和流程代码完成实现，最后通过测试和评测检查结果。

验证时分别关注**功能正确性、系统性能和结果质量**：程序是否按要求执行，完成任务需要多久、使用多少资源，以及识别结果是否正确、完整。测试与评测可以交叉，例如质量指标也可以用于回归检查。具体区别与 LangSmith 的作用，见[效果评测的前置学习知识](效果评测.md)。

开发时，我会请 AI 针对当前问题提出建议，再结合业务需求、实际数据和实现条件判断是否适用，并通过测试与评测决定采用、调整还是舍弃。涉及业务口径和判断标准的内容，与甲方领域人员确认。

开发时用 AI 帮助设计，与系统运行时用大模型分析案件，是两种不同的使用场景。

Q01-4. 方案设计、技术方案、技术路线和代码实现有什么区别？

设计可以具体到模块职责和处理步骤，不只是一个大致想法。


Q02. “业务口径”是什么意思？怎样落实到 SQL？

考察重点：能否把业务要求变成明确的查询和统计标准。
回答顺序：口径是什么 → 举例说明 → 怎样确定并实现

答：业务口径就是查询数据时采用的筛选、关联和统计标准，也就是查哪些记录、怎样对应、怎样计算。

例如，统计某个人的交易次数，要先根据账户归属信息找到他的账户，再明确统计哪个时间段、哪些交易计入，以及按人员还是按交易对手分组计算。

我结合数据说明、实际样本和研判需求提出这些标准，与甲方领域人员确认后，再落实到参数化 SQL 和程序逻辑中。


Q02-1. SQL 和查询分析工具是什么关系？补证时怎样复用？

考察重点：是否清楚 SQL、函数、工具定义和调用机制各自做什么。
回答顺序：SQL 怎样放进函数 → 怎样注册为工具 → 调用请求怎样执行 → 补证时怎样复用

答：SQL 是查询语句。我先把预设 SQL 和结果处理逻辑封装成函数，让函数接收参数、执行查询并返回结果。

再为这项功能定义工具名称、用途和参数格式，并在后端注册工具名称与函数的对应关系。调用模型时提供工具说明，大模型据此提出工具名称和参数，后端检查请求后找到对应函数执行，再把结果返回。

这就是通过工具调用机制使用查询能力。疑点发现和补证可以复用这些工具，补证时围绕具体缺口指定人员、账户和时间范围；需要扩展查询能力时，由开发者补充或调整工具。


Q03. 业务规则通道中的筛查条件是怎样确定和实现的？

回答顺序：通道怎样筛查 → 怎样确定条件 → 怎样实现 → 疑点与事实交给谁

答：业务规则通道按照预先确定的条件筛查，用 SQL 或程序判断哪些情况值得进一步核查。

我先结合现有数据和研判需求提出筛查条件，再与甲方领域人员确认，最后编写程序并验证结果。例如，可以检查单笔金额、一定时间内的累计金额或交易次数是否超过阈值，具体阈值要根据业务确定。

规则命中后，系统生成待核查疑点，并关联触发该规则的事实，二者一起交给后续任务规划。规则命中本身不代表已经存在违规行为。


Q03-1. 大模型分析通道怎样发现疑点？输出什么？

考察重点：模型根据什么提出问题，结果怎样交给后续使用。
回答顺序：读取什么 → 怎样分析 → 输出什么

答：大模型分析通道读取相关事实摘要，把资金往来、交易时间、金额和人员关系等信息放在一起分析，提出需要进一步核查的疑点。

例如，查询结果中既有 A 向 C 的转账，也有 C 向 B 的转账，时间和金额上存在值得关注的联系。模型可以提出，这些交易是否有关联、C 在其中承担什么角色，以及是否有正常业务依据。

输出时，用自然语言说明可疑问题，同时记录涉及人员、时间范围、已有事实及其来源，以及还缺少哪些证据。疑点和相关事实一起供后续任务规划使用。


Q03-2. 事实包和待核查疑点有什么区别？

考察重点：能否区分已经查到的信息和需要继续核查的问题。
回答顺序：直接区分 → 对照举例 → 说明两者关系

答：事实包是整理好的查询记录、统计结果和来源，说明已经查到了什么；疑点说明根据这些事实，还有什么风险问题需要核查。

例如，“某段时间内存在多笔转账”是事实，“这些转账是否缺乏正常业务依据”是疑点。

业务规则通道和大模型分析通道都依据相关事实发现疑点，再将疑点与对应事实联系起来，供后续规划和核验使用。


Q03-3. 业务规则通道和大模型分析通道怎样互补？事实怎样分批输入模型？

考察重点：为什么使用两条通道，以及分批分析怎样组织。
回答顺序：各自的作用 → 按什么分批 → 怎样汇总结果 → 怎样验证效果

答：业务规则按照预先确定的条件筛查；大模型把多条事实放在一起分析，寻找现有规则可能漏掉的疑点。

分批方案是先按单个人员或关联人员组归集事实，再在组内按业务数据类别整理，并结合时间范围和单批输入长度上限拆分。每批保留事实摘要、来源及相关人员和账户的标识，便于联系其他批次的结果。

各批产生的疑点统一汇总，合并重复疑点并保留对应事实。实际多发现了多少问题，需要在相同疑点数量上限和调用预算下评测，再通过消融对照判断两条通道各自的作用。


Q03-4. 这些方案是你自己做的吗？你怎样使用 AI？

Q03-5. 发现疑点后为什么还要规划任务？规划时输入什么、输出什么？

考察重点：是否清楚规划的必要性，以及疑点、事实和任务怎样衔接。
回答顺序：为什么需要规划 → 提供哪些信息 → 按什么规范输出 → 后端怎样检查

答：一个疑点往往需要多项核查，部分任务还要使用前面任务的结果。例如，先查出关联账户，才能据此查询交易明细，因此需要先拆分任务、明确依赖关系。

规划时，把疑点、相关事实、可用工具说明和任务输出规范（Schema）交给大模型。事实帮助它知道已经查到了什么、还缺什么；Schema 规定任务包含哪些字段、字段类型和必填要求。

模型据此生成核查任务，说明对应疑点、核查目标、涉及人员、时间范围、所需工具、依赖关系和完成条件。后端检查输出结构、任务范围和依赖关系，再按资源预算等限制执行。


Q04. 定向补证具体怎么做？怎样决定是否继续？

考察重点：能否根据核验结果安排下一步，并说明什么时候停止。
回答顺序：明确作出判断还缺什么 → 安排补证 → 再次核验 → 决定是否继续

答：定向补证就是在集中核验发现证据不足时，先明确要对疑点作出判断还缺哪些证据、下一步怎样获取，再针对这些缺口安排查询。

例如，双方资金往来的金额或频次值得关注，但还不能判断是否正常，就继续查询双方关系、交易明细，以及能够获取的资金用途和业务背景。

查回后再次核验，同时查看支持和反驳疑点的信息。结果可能支持、修正或排除疑点，也可能仍然无法判断。

是否继续，要看证据是否还不足、现有数据和工具能否获取所需信息，以及全案调用预算和循环停止条件是否允许。停止补证后，仍未查清的问题需要明确记录，不能直接当作已经得到支持的风险结论。

如果调用被预算限制拒绝或程序执行失败，还要保留失败状态，不能当作正常完成核验。


Q04-1. 核查任务完成，就说明疑点成立了吗？

考察重点：能否分清任务完成和风险判断。
回答顺序：直接回答 → 举例说明 → 解释最终怎样判断

答：不能。任务完成只说明安排的查询和检查已经执行，是否存在风险还要根据结果判断。

例如，“这些转账是否缺乏正常业务依据”是疑点，“查询交易明细并核对双方关系”是核查任务。即使查询成功，也可能发现这些交易属于正常往来，或者现有信息仍然不足。

因此，一个疑点可能需要多项任务。相关证据经过集中核验后，系统认为已有依据支持的风险情形，才会作为最终风险事件输出。
