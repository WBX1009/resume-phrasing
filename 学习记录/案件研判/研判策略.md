# 案件研判｜研判策略

## 简历条目

> **研判策略：**按业务口径**预设参数化 SQL**，筛选聚合百万级案件记录，形成结构化事实；结合风险识别规则与模型线索生成候选，以核验结果驱动**定向补证**；对照基线流程，最终风险事件：**精确率 81.0%→84.9%**，**召回率 85.0%→87.7%**。

> 本条理解状态：已确认（按用户要求保存本轮最终版本）。

## 第一阶段：本条理解

这条工作的核心是：从甲方已有的业务分析结果中整理案件事实，找出值得排查的疑点，再通过补证和核验，判断现有证据能否支持这些疑点。

系统直接处理的是**上游业务分析模型的结果缓存**，也就是甲方平台已经生成并保存的分析结果。这里的“业务模型”指上游的业务分析功能；后面阅读事实、分析线索的是**大语言模型**，两者承担不同任务。

1. **先明确查什么、怎么算，再用 SQL 整理事实。**

   我根据案件数据结构与研判需求，梳理需要查询哪些信息、怎样关联、按什么条件筛选和统计，再与甲方领域人员确认。这些具体标准，就是简历中所说的“业务口径”。讨论确认是形成标准的过程，“口径”本身指确定后的标准。

   标准确定后，预先编写参数化 SQL；执行时传入人员、账户和时间范围等参数，由数据库完成筛选和聚合。查到的记录和统计结果按明确字段组织，并保留来源，供后续分析与核对。这就是“结构化事实”，例如某个主体在一段时间内的交易次数、合计金额及对应来源。

   “百万级”说明案件记录的处理规模，不代表把全部记录交给大语言模型，也不能直接当作模型缓存的行数。预设查询便于检查和复用，但新的分析需求可能需要补充或调整模板。

2. **规则和大语言模型从事实中发现候选。**

   风险识别规则把值得关注的情况写成明确条件，再由 SQL 或程序检查哪些记录、对象或关系符合条件。我根据可用字段和研判需求提出初步方案，借助 AI 辅助梳理可能的规则，再与甲方领域人员讨论，确定采用哪些规则及具体条件，最后完成实现。

   模型线索是大语言模型阅读整理后的案件事实，结合多条信息，提出的可疑情况或待核查关联。这里要区分：开发时用 AI 辅助设计规则，和运行时用大语言模型分析当前案件，是两个不同的使用环节。

   规则依据明确条件筛查，大语言模型补充可能未被现有规则覆盖的疑点，两者结合的目的是减少候选遗漏。互补效果还取决于输入信息：如果模型只看到规则命中的候选，它发现其他线索的范围就会受到限制。

   **事实说明“查到了什么”，候选说明“哪些情况值得继续查”。**

   规则命中或模型提出疑点，都需要后续查证。查询统计与风险识别按用途区分，部分风险规则也可以用 SQL 实现。

3. **先围绕候选补证，再根据核验发现的缺口继续补查。**

   候选形成后，先围绕疑点补查相关信息，再集中检查证据能否支持候选。如果仍缺少影响判断的关键依据，就明确补查对象和范围，查回信息后再次核验。

   例如，仅用于说明机制：已经查到双方资金往来，但判断还需要双方关系信息，就针对相关主体补查关系数据。“定向”就是围绕当前缺少的依据，决定查谁、查什么、查哪个时间范围。

   补回的信息可能支持候选，也可能使候选被修正或排除。证据仍然不足时，就不能把候选当作已经证实的结论。

4. **用最终事件的评测结果判断整体效果。**

   这里评价的是补证、核验后最终输出的风险事件。精确率从 81.0% 提升到 84.9%，表示输出事件中符合标注标准的比例提高；召回率从 85.0% 提升到 87.7%，表示标注事件中被系统正确识别的比例提高。

   在统一评测标准和可比条件下，这说明整套流程相较基线改善了最终识别质量。这两个数不能代替候选阶段的召回率，也不能单独证明某个环节的贡献。要判断某项策略的贡献，需要在其他条件一致时，比较加入或去掉这项策略后的结果。

理解主线：明确查询标准 → 整理案件事实 → 规则与大语言模型生成候选 → 补证后核验 → 根据缺口继续补查 → 评测最终事件质量。

## 第二阶段：面试问答

```text
Q01. 你是怎样设计这套研判策略的？

答：这个项目面向纪检监察案件研判。我负责的部分以上游业务分析模型的结果缓存为输入，整理案件事实，发现值得排查的疑点，再通过补证和核验形成有依据的判断。

我先根据案件数据结构与研判需求，梳理查询、筛选和统计方式，与甲方领域人员确认后，落实为预设的参数化 SQL。

基于整理出的事实，规则按明确条件筛查，大语言模型分析补充线索，两路共同生成候选。候选经过补证后集中核验；如果关键依据仍然不足，就围绕缺口继续补查，再次核验。

对照基线流程，最终风险事件的精确率从 81.0% 提升到 84.9%，召回率从 85.0% 提升到 87.7%。这是整套流程的对照结果。


Q01-1. 你处理的数据来自哪里？上游业务模型和大语言模型有什么区别？

答：我直接处理的是甲方业务分析平台生成的模型结果缓存，也就是平台已经生成并保存的分析结果。例如，这类缓存可以保存筛选后的记录、统计结果或关系信息，具体内容以实际数据为准。

这里的“业务模型”指平台已有的业务分析功能，例如消费类型统计、资金流向分析，这个称呼本身不说明底层是否采用机器学习。

“大语言模型”则在后续读取整理后的案件事实，分析关联并提出待核查线索。介绍时分别称为“上游业务分析模型”和“大语言模型”，就能区分它们的作用。

规模方面，已确认的表述是“百万级案件记录”。缓存总行数、单案规模和各类别规模需要另行核对；百万级也不意味着把全部记录直接交给大语言模型。


Q01-2. 四类业务模型分别是什么？人员画像用什么字段解释最直观？

答：按已有记录中的示例分类，四类是人员画像、金融画像、电信画像和多维分析。可以各选一个用途解释：

人员画像可以用“人员与银行卡、电话号码的对应关系”说明，帮助理解分析对象及其关联账户、号码。

金融画像可以举消费类型分布或资金流向分析，结合金额、时间、方向和交易对手等信息解释。

电信画像可以用“谁与谁联系、何时联系、联系多少次”说明通联分析的用途。这只是通俗示例；已有记录注明，示例配置未包含话单数据，实际覆盖仍需核对。

多维分析可以举银行转账关系、同日相同金额转向不同对手等例子，说明怎样组合主体、金额、时间和关系进行分析。

这些示例用于理解分类，不能直接当作生产环境全部具备的数据。业务分类之间可能交叉，也不能与人员、资金、通联、资产四种数据领域一一对应。


Q01-3. 面试介绍时，需要先把数据类别、字段和规模全部讲清楚，才能讲设计吗？

答：先交代支撑方案的必要背景即可。开场说明系统处理什么输入、希望得到什么结果、我负责哪部分工作，就可以进入研判策略的主线。

被追问时，再展开数据类别、代表字段、规模和查询细节。

学习时，可以沿着“业务场景与数据基础 → 需求和约束 → 方案设计 → 技术实现与选型 → 效果验证”理解完整逻辑。面试时根据当前问题选取相关内容，不必每次从头介绍整个系统。


Q01-4. 方案设计、架构设计、技术实现和技术选型，分别在回答什么问题？

答：方案设计回答“怎样解决问题”；架构设计明确“各部分负责什么、怎样配合”；技术实现说明“具体怎样做出来”；技术选型解释“为什么这样做，有什么收益、代价和局限”。

在这条工作中，把研判安排为事实准备、候选生成、补证和核验，属于策略与流程设计；明确各环节的输入、输出及依赖，涉及架构设计。

把这些安排落实为 SQL 模板、规则判断、数据结构和工作流节点，属于技术实现。使用 LangGraph 等框架只是实现的一部分。

例如，选择预设 SQL，是为了让查询逻辑便于检查和复用，但新增需求需要维护模板；引入大语言模型，是为了补充线索，同时要处理调用成本和推断不可靠的问题。

这些方面会相互影响，实际开发也会反复调整，不必把它们理解成严格分开的几个阶段。


Q02. 简历里的“业务口径”是什么意思？你怎样据此设计 SQL？

答：业务口径就是查询、筛选和统计数据时采用的具体标准，通俗地说，就是明确要查什么、怎样关联、怎么算。

在项目中，我根据案件数据结构与研判需求提出初步查询方案：已有字段和关联关系决定能够查什么，研判问题决定需要怎样筛选和统计。

随后与甲方领域人员确认具体标准，再落实为预设的参数化 SQL。“口径”强调标准本身，沟通确认是这个项目确定标准的方式。


Q02-1. 为什么采用预设参数化 SQL？执行时怎样使用？

答：主要是为了让查询逻辑可检查、可复用，并让后续分析建立在明确的查询结果上。

我预先写好 SQL 的查询结构和统计逻辑，执行时传入人员、账户和时间范围等参数，由数据库完成筛选和聚合。

这样便于检查查询范围和统计方式，模型也不需要临时生成 SQL。它的局限是查询能力受已有模板约束，新的分析需求可能需要补充或调整模板。


Q03. 风险识别规则是什么？这些规则是怎样确定并实现的？

答：风险识别规则就是把业务上值得排查的情况写成明确条件，再用 SQL 或程序逻辑筛选候选事件。例如，可以围绕金额是否超过阈值、一定时间内交易是否频繁，以及资金路径是否符合特定条件设计规则。这些只是规则类型的示例。

设计时，我先梳理现有数据的字段和关联关系，借助 AI 辅助整理可能的风险模式和识别条件，形成初步方案。

随后与甲方领域人员讨论，结合他们的专业经验，确定采用哪些规则、哪些更重要，以及具体条件怎样设置，再由我完成技术实现。

其中，存在 A→B→C 的资金路径只说明查到了一项关系；是否值得列为风险候选，还需要结合时间、方向、金额等条件判断。


Q03-1. 模型线索是什么意思？为什么需要它补充风险识别规则？

答：模型线索是大语言模型根据初步整理的案件事实，分析后提出的可疑情况或待核查关联。

规则按预先确定的条件检查，依据明确、便于复核，但覆盖范围受已有条件限制。大语言模型可以结合多条事实提出补充线索，同时也可能产生缺乏证据支持的推断。

因此，两者共同用于发现候选：规则筛查明确条件，模型补充可能未被现有规则覆盖的疑点。两路输出都需要后续补证和核验。

这里还有两个不同的 AI 使用环节：开发时，AI 辅助我设计规则；系统运行时，大语言模型分析当前案件并提出线索。


Q03-2. “事实包”是什么？面试中可以换成什么表达？

答：这里的“事实包”指把查询到的记录、统计结果和来源信息组织起来，供后续分析使用的数据。

例如，仅作结构说明：某个主体在一段时间内的交易次数、合计金额，以及这些结果对应的数据来源。

面试中可以直接说“初步整理的案件事实”；需要强调数据形式时，可以说“结构化事实”，不必把“事实包”当作一个必须掌握的技术名词。

还要区分查到或计算出的内容与模型的推测，避免把待核查的关联写成已知事实。


Q03-3. 两条候选通道怎样互补？能保证不漏掉重要线索吗？

答：两条通道都基于整理后的案件事实提供候选，规则负责按明确条件筛查，大语言模型结合多条信息补充疑点，目的是减少候选阶段的遗漏。

互补能发挥多少作用，还取决于输入范围。如果模型只看到规则命中的候选，它发现其他线索的范围就会受到限制。要扩大覆盖，还需要提供与研判相关、但未触发规则的事实。

两路结合也不能保证不漏。上游缺少数据，或者整理事实时遗漏了关键关系，两路都可能受到影响。

实际效果需要在相同候选上限和调用预算下评测；要判断模型或规则分别贡献了多少，还需要结合消融对照。


Q04. “以核验结果驱动定向补证”具体是什么意思？

答：就是把核验发现的证据缺口，转成有明确对象和范围的补查任务。

例如，仅作机制说明：已经查到双方资金往来，但判断还需要双方关系信息，就针对相关主体补查关系数据。查谁、查什么、查哪个时间范围，都由当前缺口决定。

补回的信息再用于核验。它可能支持候选，也可能使候选被修正或排除；如果证据仍然不足，就不能确认候选成立。


Q05. 这两个指标怎样评测？能说明哪些效果？

答：评价对象是补证和核验后的最终风险事件，以专家标注为参照。精确率看输出事件中有多少正确匹配标注，召回率看标注事件中有多少被正确识别。

我基于脱敏案件和专家标注构建事件级评测集，按案件划分开发集和测试集。在测试集上使用统一的事件匹配规则，并在相同候选上限和调用预算下比较基线与改进流程。

最终风险事件的精确率从 81.0% 提升到 84.9%，召回率从 85.0% 提升到 87.7%，说明整套流程在这组评测条件下改善了最终识别质量。

这里的召回率属于最终事件阶段，不能代替候选召回率；整体指标也不能单独证明规则、模型或定向补证各自的贡献。
```
