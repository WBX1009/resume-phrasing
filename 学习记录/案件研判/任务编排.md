# 案件研判｜任务编排

## 简历条目

> **任务编排：**用 **LangGraph** 编排“规划—补证—集中核验—汇总”，按人员关系与时间窗拆分核查任务，按依赖和并发上限调度；对照串行执行，端到端 **p95 耗时 35→27 min**。

> 本条理解状态：已确认。按用户审阅的表达稿更新。文中的例子用于解释机制；实际业务计划与测量记录的待补事项集中列在文末。

## 第一阶段：本条理解

这条工作的核心是：**把核查疑点要做的事情拆成具体任务，安排好执行顺序。需要的信息已经准备好、互不依赖的任务，可以一起推进；依赖其他任务输出的，就等所需结果返回后再执行。之后，对证据进行集中核验，并整理报告。**

一次案件研判需要多次查询案件数据，并请求大语言模型分析相关事实、规划核查任务或核验查询结果。

这些操作中有不少时间花在等待数据库或大语言模型返回结果上。如果所有任务都串行执行，互不依赖的查询也要排队等待。因此，这部分工作的目标是：**在满足任务依赖和资源限制的前提下，让独立任务的等待时间重叠，缩短完整研判流程的耗时。**

### 1. 从疑点出发，规划具体的核查任务

[研判策略](研判策略.md)先整理已有事实，再结合规则和大语言模型发现待核查疑点。任务编排承接这些疑点和相关事实，安排接下来具体查什么、怎样执行。

一个疑点可以对应多个核查任务。每个任务需要说明核查目标、涉及人员、时间范围、可用工具，以及是否依赖其他任务的结果。

按人员关系和时间窗拆分，是为了让每项任务有明确的查询范围：查哪些人之间的关系，查哪段时间的数据，以及这些信息用来核查什么问题。

例如，围绕甲、乙之间的资金往来，可以安排以下任务。这里仅用于解释机制：

| 任务 | 要做什么 | 是否依赖其他任务 |
| --- | --- | --- |
| T1 | 查询甲的关联账户 | 不依赖其他任务 |
| T2 | 查询甲、乙之间的人员关系 | 已知双方身份，可以直接查询 |
| T3 | 根据甲的关联账户查询交易记录 | 依赖 T1 返回的账户列表 |

T1 和 T2 不需要对方的查询结果，可以一起执行。T3 需要 T1 的输出，因此必须等待 T1 成功返回结果。

这也说明：**两项任务在业务上有关联，不代表执行时必须有先后顺序。** 是否需要等待，取决于一项任务是否需要另一项任务的输出。

### 2. 模型负责提出计划，后端负责把计划执行起来

可以借助 Plan-and-Solve 的思路理解这里的分工：先规划要做的工作，再按照计划执行。

大语言模型根据疑点、事实和工具说明，提出任务及其依赖。后端按照预先写好的规则，判断这些任务何时可以启动、结果如何传递、失败后怎样处理。

两者的分工可以具体到字段：

| 内容 | 当前任务结构中的字段 | 谁负责 |
| --- | --- | --- |
| 任务标识 | `task_id` | 规划器提供，后端检查 |
| 核查目标 | `question` | 规划器提出 |
| 人员与时间范围 | `entity_ids`、`time_range` | 规划器提出，后端检查范围 |
| 可用工具 | `allowed_tools` | 规划器在允许范围内选择，后端检查 |
| 依赖哪些任务 | `depends_on` | 规划器提出，后端据此安排执行 |

例如，规划结果写明 T3 的 `depends_on` 是 T1，后端便按这条依赖安排执行。

这里所谓“确定性规则”，依据来自两部分：

- **任务计划中的字段**：例如 T3 依赖 T1。
- **开发者编写的执行规则与配置**：例如依赖任务全部成功后才能启动，活动任务数量不能超过并发上限。

因此，**大语言模型决定这次需要哪些任务、任务之间有什么依赖；后端决定如何按照这些信息可靠地执行。** 后端不会在每次任务完成后，再让模型判断该启动哪个协程。

以上说明已确认的业务设计。当前公开服务的默认规划器读取传入的任务列表，Worker 和核验器使用测试输入；真实的大语言模型规划、工具查询和核验逻辑，可通过 `planner`、`worker`、`verifier` 等回调函数接入。公开源码可以核对计划检查、任务调度和补证循环，默认回调本身不能证明真实业务研判已经接入。

### 3. 变化的任务计划，怎样交给固定的 LangGraph 节点执行

这里最容易混淆的是：**一项核查任务，不必对应一个单独定义的 LangGraph 节点。**

当前实现中，外层图的节点分工预先确定：

| 外层节点 | 负责什么 |
| --- | --- |
| 规划节点 `plan` | 调用规划器，把任务列表写入状态 |
| 调度节点 `dispatch` | 把任务列表交给后端调度器执行 |
| 结果收集节点 `candidate_events` | 收集本轮任务返回的结构化候选结果，交给集中核验 |
| 集中核验节点 `central_verify` | 调用核验逻辑，返回风险判断和证据缺口 |
| 定向补证规划节点 `plan_rechecks` | 根据核验缺口追加任务 |
| 汇总节点 `summarize` | 整理并保存报告 |

这些节点通过工作流状态 State 传递任务计划、执行结果和核验结果。节点读取状态并返回更新，LangGraph 再按定义好的连接和路由函数继续执行；核验后的路由根据证据缺口和补证条件，选择继续补证还是汇总。

节点名 `candidate_events` 表示收集任务返回的候选结果；业务上仍先发现疑点，再规划核查任务。简历中的四个阶段概括的是业务步骤，不要求每个阶段恰好对应一个代码节点。

不同案件可能规划出 3 项任务，也可能规划出 10 项任务。变化的是**任务列表中的数据和执行次数**，外层图仍然经过同一个调度节点。

具体执行过程是：

1. 规划节点得到任务列表，并写入工作流状态。
2. 调度节点读取这份列表，调用自己实现的 `CaseTaskScheduler`。
3. 调度器找出可以启动的任务，在并发上限内分别创建异步任务。
4. 每个异步任务调用同一套补证处理逻辑，但传入自己的任务内容和所需结果。
5. 本轮执行结束后，调度节点返回各任务的结果与状态，外层图再进入集中核验。

因此，规划出 10 个任务，并不需要在图里临时增加 10 个节点。

“复用补证子图”也可以说得更直接：

> 后端预先定义好“怎样执行一项核查任务”的处理流程。执行时，把 T1 的任务内容传进去执行一次，把 T2 的任务内容传进去再执行一次。它们使用相同的处理代码，但各自保存输入、中间状态和结果。

当前补证子图内部只有一个 `worker` 节点，由它调用具体的任务处理函数。它没有为“查账户”“查交易”“查人员关系”分别定义不同节点。

所以，当前实现中，模型无需决定“把任务放到图的哪个节点”。这些任务统一交给调度节点，再调用同一套 Worker；具体查询什么，由任务内容和 Worker 的处理逻辑决定。

图结构固定，也不意味着每次运行都完全相同：任务数量、输入、结果，以及是否进入下一轮补证，都可以变化。如果要增加新的处理阶段，再修改图定义并重新编译即可。LangGraph 也提供 `Send` 等动态分发机制，但当前这部分代码采用的是自定义调度器。[LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/graph-api)

上述实现可对应到仓库中的[工作流](../../项目源码/案件研判/src/case_workflow_graph.py)、[任务调度器](../../项目源码/案件研判/src/case_task_scheduler.py)和[补证子图](../../项目源码/案件研判/src/case_worker_subgraph.py)。

### 4. 后端怎样安排任务，以及它与集中核验的区别

后端安排执行时，主要做三件事：

1. **检查任务计划。** 检查核查人员、时间范围、工具和任务依赖是否符合执行要求。
2. **启动可以执行的任务。** 没有依赖的任务可以先执行；依赖其他任务输出的，等那些任务成功后，再把结果传给它。在此过程中控制活动任务数量。
3. **根据完成情况继续调度。** 某项任务完成后，保存结果，检查是否有后续任务可以启动。某项任务失败时，依赖它的任务不能继续，其他独立任务仍可执行。

例如，假设并发上限为 2，调度器可以先启动 T1 和 T2。T1 完成后，T3 就可以使用它返回的账户列表开始查询，无须等 T2 也完成。

这里的“根据完成情况继续调度”，判断的是：

> 哪项任务已经完成？哪些任务现在可以启动？

集中核验判断的是：

> 这些任务查到的证据，是否支持疑点？是否存在反驳信息？还缺什么？

**任务调度发生在本轮补证执行过程中；集中核验发生在本轮执行结束之后。** 两者处理的问题不同。

另外，当前调度器直接管理展开后的核查任务列表。一个疑点可以拆成多项任务，不同疑点的独立任务也可以一起调度；代码没有要求“每个疑点单独建立一张图，再在图内安排子任务”。

调度器负责检查任务状态、传递结果。返回内容是否满足下一步的需要，还要由任务处理函数检查；查询结果为空和返回内容缺少必要字段，也需要分别处理。

### 5. 异步、并发和并行，在这里分别是什么意思

异步接口设计需要和任务调度一起讲。“多个独立疑点一起执行”，还不足以说明另外实现了一套并行机制。

三个概念可以这样理解：

| 概念 | 直观含义 | 在本项目中的对应 |
| --- | --- | --- |
| 异步 | 等待一个操作返回时，允许程序处理其他工作 | 等待数据库或大语言模型响应时，让其他任务继续推进 |
| 并发 | 多个任务在同一段时间内推进，执行过程有重叠 | 调度器启动多个核查任务，用协程组织执行 |
| 并行 | 多项工作在同一时刻由不同执行资源实际处理 | 是否发生，取决于线程、进程、数据库或大语言模型服务等底层资源 |

在同一个 `asyncio` 事件循环中，一项协程等待尚未完成的 I/O 时，事件循环可以运行其他协程。这已经能够让多个核查任务并发推进。[Python 官方文档](https://docs.python.org/3/library/asyncio-task.html)

例如，T1 已经发出数据库查询，正在等待结果；程序这时可以推进 T2，发出另一个请求。两个任务都处于“已启动、尚未结束”的状态，但不代表两个协程正在同一个线程上同时执行 Python 代码。

因此，**并发上限限制的是已经启动、尚未结束的核查任务数量，其中也包括正在等待数据库或大语言模型返回的任务。**

并发上限来自配置，由后端检查；大语言模型提出任务和依赖，不能自行提高这个上限。

当前代码中的异步支持也有具体实现：

- 使用 `asyncio.create_task` 启动可以执行的核查任务。
- 使用 `asyncio.wait(..., FIRST_COMPLETED)` 等待任务完成，再及时安排后续任务。
- 大语言模型调用通过异步接口等待结果。
- 工具本身支持异步时直接等待；工具是同步阻塞函数时，通过 `asyncio.to_thread` 放到线程中执行，避免阻塞事件循环。
- 大语言模型请求和数据库查询还分别设置并发限制，控制共享资源压力。这些限制在单个服务进程内生效。

这部分主要是自己编写的调度与调用逻辑。`asyncio` 提供协程运行能力，LangGraph 负责外层阶段衔接。

还需要分清任务之间的并发与任务内部的执行方式：**一个任务使用异步接口，不等于它内部的多个操作已经并发执行。** 如果先等待查询 A 完成，再调用查询 B，那么这两个查询在该任务内部仍是顺序执行。只有显式地把两个独立操作组织起来共同运行，才形成任务内部的并发。

当前代码可以确认任务之间的并发，以及调用层的异步支持；补证子图本身没有展示单个任务内部自动并发执行多个工具。因此，这一层暂时不写成已经实现的能力。

本条更准确的因果关系是：

> **异步调用让等待时可以推进其他工作；任务调度把互不依赖的工作组织起来，让这些等待真正重叠。**

这两个方面应该一起讲，不能仅强调“用了异步”，也不能只说“让任务同时跑”。

### 6. 集中核验发现证据不足后，怎样补证

这里统一使用“证据不足”和“定向补证”。“证据不足”适用范围更广；“证据链断裂”适合描述某条关联链缺少关键环节，不宜代替所有证据不足的情况。

**集中核验发现证据不足时，针对缺少的证据安排定向补证，补证后再次核验。后端通过资源预算和补证轮次上限限制执行规模；停止补证后，仍未解决的证据缺口需要明确保留。补证结果既可能支持疑点，也可能修正或排除疑点。**

这里采用“补证轮次上限”，比“补证次数上限”更准确：一轮补证可能包含多个核查任务，每个任务又可能调用多次工具。

相关概念统一如下：

| 名称 | 限制或说明什么 |
| --- | --- |
| 工具能力 | 现有工具能够查询哪些数据、完成哪些分析 |
| 工具调用预算 | 整次研判允许累计调用工具多少次，具体配置可以称“工具调用次数上限” |
| 资源预算 | 对大语言模型调用次数、工具调用次数和 Token 等资源额度的统称 |
| 补证轮次上限 | 最多允许进行多少轮“核验发现缺口后，再安排补证”的循环 |
| 并发上限 | 同一时间允许有多少项任务或请求处于进行中 |

**工具能力属于补证能否完成的条件，资源预算和轮次上限属于执行控制。** 两者应分别说明。

现有工具无法取得所需信息时，继续增加调用次数也不一定能解决问题，应保留证据缺口。正常停止补证后，可以汇总已有判断和未解决的缺口；调用被预算限制拒绝或程序异常，则可能使任务或整次运行失败，需要保留失败状态。

### 7. 35→27 分钟说明什么，怎样理解评测中的质量检查

端到端耗时衡量一次完整研判流程需要多长时间。仓库现有计时口径是：从后端接收有效请求开始，到必需研判步骤完成、报告保存并可读取为止，包含请求后的事实准备、规划、补证、集中核验和报告生成。

p95 可以理解为：约 95% 的统计样本耗时不超过这个值。

从 35 分钟降到 27 分钟，减少 8 分钟，降幅约为 22.9%。它说明这组对照中，完整流程的高分位耗时下降了，不代表每个案件都快了 8 分钟。

质量检查在性能对照里也有必要：

- 完成情况用于检查任务是否正常结束。
- 实际核查内容用于检查两组是否完成了可比的工作。
- 输出质量用于检查提速是否伴随研判效果下降。

这里的目的，是确认耗时下降发生在完成可比核查工作的前提下。本条仍然以耗时优化为主，不额外宣称精确率或召回率因并发而提升。

另外，**异步调用与依赖调度共同支撑受控并发；35→27 分钟体现的是整套执行方式相对串行执行的结果。** 如果对照只改变任务并发上限，就不能进一步拆出“异步接口贡献多少分钟、独立任务一起执行又贡献多少分钟”。

### 8. LangSmith 在这里做什么

LangGraph 负责运行流程。LangSmith 可以记录和分析运行过程，帮助查看调用耗时和错误，也可以保存评测结果、比较不同版本的效果。[LangSmith 官方文档](https://docs.langchain.com/langsmith/observability)

“LangSmith 上传”指把运行记录或评测结果发送到 LangSmith 服务。仓库中的评测适配器通过 `upload_results` 控制是否上传实验结果；现有公开验收依据是关闭上传的本地接口测试，不能据此认定已完成托管实验或真实调用追踪。

计时时需要按操作实际发生的位置区分：

- 报告完成后的评分和实验结果上传，不属于生成报告所需的时间。
- 如果运行过程中的追踪操作实际延长了报告生成时间，这部分开销已经处在端到端计时范围内，不能人为扣除。
- 串行与并发对照应保持相同的追踪配置。

主口述答案没有必要专门提“LangSmith 上传”。讲清计时起止点，以及两组配置一致即可。

## 第二阶段：面试问答

Q01 按 STAR 组织；其余按具体考察内容安排回答顺序。方括号和“回答顺序”仅用于记忆，不需要念出来。

```text
Q01. 介绍一下你做的案件研判任务编排。

考察重点：面对什么问题、个人负责什么、关键做法怎样带来结果。
回答顺序：S 串行等待 → T 我的任务 → A 规划、异步调度、集中核验 → R 耗时结果

答：
[S] 一次案件研判需要多次查询案件数据，并请求大语言模型分析相关事实、规划核查任务或核验查询结果。如果全部串行执行，互不依赖的任务也要依次等待。

[T] 我负责设计和实现任务编排，在满足任务依赖和资源限制的前提下，减少这些等待，缩短整体耗时。

Q02. LangGraph、大语言模型和你写的调度器，分别负责什么？

考察重点：能否区分业务规划、框架能力和自己实现的执行逻辑。
回答顺序：模型提出计划 → LangGraph 连接阶段 → 调度器执行计划

答：大语言模型负责根据疑点和已有事实提出核查任务，说明查什么、涉及哪些人和时间范围，以及任务之间有什么依赖。

LangGraph 负责连接规划、补证、集中核验和汇总这些阶段，传递任务计划与执行结果，并根据核验情况决定是否进入下一轮补证。

具体任务由我编写的异步调度器安排执行。它读取依赖关系，判断任务能否启动，控制并发数量，并保存结果、传给后续任务。协程的运行和切换由 asyncio 提供支持。


Q02-1. 每次规划出来的任务都不同，固定的 LangGraph 节点怎么适配？

考察重点：是否理解图节点与运行时任务的区别，能否说清实际实现。
回答顺序：计划作为数据 → 固定调度节点 → 多次调用同一 Worker → 返回执行结果

每项任务包含 task_id、question、人员与时间范围，以及 depends_on 等字段。调度器读取这些字段，找出可以启动的任务，再分别创建异步任务。

这些任务调用同一套补证处理逻辑，但传入各自的任务内容和所需结果。当前补证子图内部是一个 Worker 节点，所以规划出三项任务，就是按依赖和并发限制调用它三次；规划出十项任务，就安排十次调用。

Q03. 为什么按人员关系和时间范围拆分任务？

考察重点：任务拆分是否服务于实际核查目标。
回答顺序：明确范围 → 结合疑点拆分 → 集中核验相关结果

答：这样可以让每项任务明确查哪些人、查哪段时间的数据，以及查询结果用来回答什么问题。

例如，核查甲、乙之间的资金往来，可以分别安排人员关系查询、关联账户查询和交易记录查询。它们围绕同一个疑点，但各自承担明确的查询工作。

执行时根据是否需要其他任务的输出安排顺序，完成后再把相关证据放在一起核验。拆分是为了组织核查工作，最终判断仍要结合相关结果。


Q04. 任务依赖和并发上限怎样控制执行？

考察重点：任务什么时候启动，完成或失败后怎样继续。
回答顺序：检查计划 → 判断依赖 → 控制活动任务数量 → 完成后继续调度

答：后端先检查任务计划，再找出没有依赖，或者依赖任务已经全部成功的任务。在并发上限允许的范围内启动它们，并把所需的上游结果传进去。

例如，查询甲的关联账户，与查询甲、乙的人员关系，可以独立执行；根据账户查询交易记录，则要等账户查询完成。

并发上限限制的是已经启动、尚未结束的核查任务数量，包括正在等待数据库或大语言模型返回的任务。某项任务完成后，调度器保存结果，再检查哪些任务可以接着执行。如果某项任务失败，依赖它的任务不能继续，其他独立任务仍可推进。

这里检查的是执行状态；证据是否支持疑点，要在后面的集中核验阶段判断。


Q04-1. 这里的提速是靠异步、并发，还是并行？

考察重点：是否理解异步的作用，能否准确解释提速机制。
回答顺序：项目机制 → 异步与调度配合 → 并行的边界

答：这部分主要通过异步调用支持任务并发，减少数据库查询和大语言模型调用之间的串行等待。

调度器用 asyncio 启动多个可以执行的核查任务。一项任务等待接口返回时，事件循环可以推进其他任务。对于同步阻塞的工具调用，则通过线程执行，避免阻塞事件循环。

异步接口提供了等待时处理其他工作的条件，依赖调度决定哪些任务可以一起推进，两者配合才形成实际的提速。

这里说多个任务一起推进，指任务并发。底层是否在不同资源上真正同时执行，还取决于数据库、大语言模型服务和线程等条件。仅仅使用协程，不能据此宣称实现了多核并行。


Q05. 为什么要集中核验？证据不足后怎样处理？

考察重点：是否区分执行完成与疑点成立，补证是否有方向和停止条件。
回答顺序：核验目的 → 检查支持与反驳信息 → 定向补证 → 限制与停止

答：集中核验要结合相关任务查到的证据，判断疑点得到支持、需要修正、可以排除，还是仍然证据不足。任务执行成功，只说明安排的查询和检查已经完成。

核验时既要看支持疑点的信息，也要看反驳信息和矛盾。发现证据不足后，针对具体缺口安排定向补证，补证完成后再次核验。

整个过程受资源预算和补证轮次上限控制。资源预算包括大语言模型调用、工具调用和 Token 等额度。现有工具无法取得所需信息，或者达到执行限制时，需要保留未解决的缺口，不能反复查询直到得到支持疑点的结果。

正常停止补证后，可以汇总已有判断和缺口；调用被预算限制拒绝或程序异常时，还要保留失败状态。
```
